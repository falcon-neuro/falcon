# Pipeline designer

The part of the UI in which a user builds a graph: places processors on cores, connects them and sets their options. This file is its spec followed by its open questions: a question that is settled moves up into the spec. A section named here without a file, and not found in this one, is in [engine.md](engine.md). What becomes of the graph is in [generator.md](generator.md). It comes after the generator (see **Order of work** at the top of beyond_prototype.md).

## Decided
- **The UI never freezes** (decided by the user on 22 November 2026: "no freeze at any point of ui's lifecycle, never"). Whatever can take time that a user would notice, e.g. compiling a pipeline, runs beside the UI's thread, and the window stays usable and says what is going on meanwhile.
- **The UI is held to the standard of the best commercial software** (the user, 23 November 2026: "pls keep things as if they are developed in silicon valley, high level ui ux, maximum user satisfaction"). Claude's reading, not confirmed: a screen shows first what is needed first and the rest on demand, as the path under a pipeline's name does; nothing on it moves because something else appeared; and what the user is told stands beside what it is about.
- **No free placement** (decided by the user). The editor is not an empty canvas on which nodes are moved about, as the old Dart GUI's was, which made placing nodes more complex than it needed to be. Each processor and each connection is drawn at a place that follows from the graph alone, so no coordinates are kept anywhere.
  - **CPU cores are areas.** Which cores are Falcon's is what the machine's setup isolated (see **A core that isn't isolated is marked**); choosing them, ideally leaving the OS a core outside the large-L3 CCD, e.g. core 15 on a 9950X3D, is that setup's task (see task A.1 under **Tasks** in beyond_prototype.md). The user drags a processor from the panel and drops it into a core's area, which gives it its core.
  - **Dragging only brings a processor into existence**: the user drags it from the panel and drops it into a core's box, where it sits unconnected. A drop never makes a connection.
  - **Every connection is made with two clicks**: on an output of one processor and on an input of another, in either order (decided by the user), on the same core or on another. Between two cores the generator makes of it what crosses cores, a ring or a cross-core state value (see **Rings** and **State values** in engine.md).
  - **The layout follows the connections**, top to bottom: once two processors of one core are connected, the one that takes the input is drawn under the one that gives the output. A chain is what comes of that; the user never builds or marks one (see **Chains are detected automatically** in generator.md).
    - **An output read by several processors** of its core fans out: they are drawn side by side under it.
    - **A processor with inputs from two processors** sits in the middle under both, which are drawn with room between them.
    - **A processor not yet connected** sits at the top of its core's box, beside the top of the chains already there.
    - **A state value's connection places nothing** (decided by the user): only connections of samples and events place the blocks, and a state value's is a line drawn beside them. State values can run in a circle on one core, which a layout from top to bottom couldn't hold; one that comes from further down is read one pass late (see **Order** under **Per-core loop** in engine.md).
    - **A connection between cores** leaves the core of the processor that gives it at the bottom of that core's box and enters the reading core's box from the top, so its line has the shape of an S. The processor that reads it has nothing above it in its own core and sits at the top.
  - **Every core from 0 up to the highest one in use has a box** (decided by the user on 17 November 2026, in place of a box for the cores in use only): a core among them that holds no processor is an empty box, never hidden. An empty pipeline has the boxes up to the first core offered. While a processor is dragged, the next core after them appears as one more place to drop it, and stays only if the processor is dropped there.
  - **A core's box is as tall as what it holds** (decided by the user on 17 November 2026), not as tall as the window. A core that holds no processor keeps the room of one drop place, so its box doesn't grow when a processor is dragged over it.
  - **A drag shows drop places in the core under the mouse** (decided by the user on 17 November 2026), and in no other: one left of each of its chains and one right of the last. So where a processor is dropped decides its place among the core's chains, which is their order in the core's loop (see **A core's chains run from left to right**). The place nearest the mouse is marked, and a drop anywhere in the box goes to it.
  - **Nothing moves during a drag** (decided by the user, who found boxes that grew under the mouse hard on the eyes; since 23 November 2026 this holds once a drag is on: at its start the cores that aren't in use get their boxes, which moves the boxes right of a core that was hidden between two in use, and the block under the mouse hides its ports; both follow from decisions of that day, and the user took the one shift at a drag's start ("yes")): a drop place is a thin bar in the gap that is there anyway between two chains and at the box's two ends, from the top row to the box's bottom. Only a core that holds no processor shows an empty box with a dashed outline and "Drop here", for which its box has the room. Not chosen: every box making room for dashed places from the start of a drag to its end.
  - **A core that isn't isolated is marked** (decided by the user). The editor reads from the kernel which cores are isolated from the OS. A box of one that isn't has a warning colour and says "not isolated", with a tooltip: the OS and its interrupts run there, so a processor on it can be held up at any moment; one that isn't realtime, such as a recorder, is fine there. A line above the boxes names the isolated cores, and its tooltip the others. It warns and doesn't forbid. Isolated cores are offered first, lowest number first, then the others.
  - **The cores' area scrolls sideways during a drag** (decided by the user) when the mouse nears its left or right edge, so that a core beyond the window's width can be reached.
  - **A processor that exists can't be dragged about** (decided by the user). A drag does one of two things: left or right, it moves the whole chain the processor belongs to among the chains of its core, which sets the order they run in; into another core's box, it moves that one processor there. Its connections stay as they are, and those that now cross cores become rings or cross-core state values. A drag released anywhere else puts everything back where it was.
  - **A core's chains run from left to right**: that is their order in the core's loop, and the one thing about the layout that the connections don't give, so it is kept with the graph.
  - Every place is one of a fixed set inside a core's box, so nothing has coordinates.
  - The editor can be simple and fairly static rather than smooth and Figma-like. Adding a processor by clicking it instead of dragging is fine.
- **A processor's options are shown and edited in a panel, never on its block** (decided by the user on 23 November 2026: "remove options from nodes, they should be visible only at panel"; built that day, checked by the tests of the UI and a picture). A block holds its name and type and, for a processor that starts a stream, that stream in one line, which is no option. The panel at the right, opened by a click on the block's name, shows and edits every option. It replaces the decision of 17 November 2026, by which the block also listed every option as a line of text, its name and its value: the values were then seen at a glance, where now each is hidden until its block is clicked, and the blocks were tall and uneven.
- **A block's type stands before its name** (the user, 23 November 2026: "type is more important than name, dont you think?", and of Claude's proposal to swap them: "yes", "swap now"; built that day, checked by the tests of the UI and a picture). The type is bold on top, e.g. SpikeDetector, and the name faint under it, `spike_detector`; the head of the panel at the right has the two in the same order, which Claude added for the match. The reason: a name is made from the type and can't be changed yet (see **Names that are used twice** in the open questions), so the two say one thing and the type is the one that says what the block does. For later, proposed by Claude and not answered: once a name can be the user's own, e.g. `ripple_filter` for an IirFilter, it says what the block is for and tells two processors of one type apart, and a name that is still the one made from the type need not show at all.
- **What the designer does comes first, its look after** (decided by the user on 17 November 2026): the designer is first made to do all it should, and only then redesigned. What the redesign is to do, each decided by the user that day:
  - **A block's type is its largest text**, so that a scientist reads the screen as "a filter that outputs to a ripple detector". Its name comes second: it is needed only to debug. Its options and its ports come last. Today the name is the bold one and the type is grey under it.
  - **Icons** are the ones merged into the UI's fonts (`src/ui/common/icons.cpp`, `icon_list.cpp`), made in another session.
  - **Falcon draws its own window bar**, with menu items in it, in place of the desktop's, which is wasted room, as VSCodium does.
  - **A connection between cores is drawn another way than one inside a core**: each core has a port of its own, the connection leaves the one core through its port and enters the other through that one's, and it is not a line from processor to processor. Not chosen: rows lined up across cores, so that a processor stands under what it reads on any core, which is what the user's picture of the look showed.
  - **A samples connection is drawn as lanes of a highway, not as a thin line** (idea of the user, parked on 17 November 2026), to show that its channels flow side by side, as the processors compute them. Hundreds of lanes can't be drawn, so it has a few, e.g. 8, with the channel count written in their middle: the user sees that 400 samples flow in parallel in this stream.
  - The picture the user gave for the look, which is not in the repository, showed: a bar on top with "Falcon", a dot and "Running", and at its right what the line colours mean; the panel as a field that filters the processors over three plain lists; each core a light grey box with rounded corners, its name at the left and its load in percent at the right; a block a white card with rounded corners and a thin border, the selected one with a blue border; a port a small ring on the block's edge; lines in the colour of what they carry.
- **Written in Dear ImGui**: Drop the UI written in Dart, rewrite it in Dear Imgui. The processors and their options for the node editor come from the list a script makes from their source (see **The processors are read from their source by a script** in generator.md), not from C++26 reflection, which clang won't have soon.
- **Cache view**: A cache miss costs ~100 ns versus a few ns for a hit, so a graph that outgrows the CPU cache gets much slower without any visible sign. Show per-core L1/L2/L3 usage (ring buffers + processor state on that core, against cache sizes read from the CPU) in the graph editor while the user designs the graph, before running it. Sizes are calculated, not measured, so users see when their graph stops fitting.
- **Bypass toggle**: for processors with the same input and output type (signal passes through unchanged). Only while the graph is not running.
- **Order of processors**: inside a chain it follows from the connections, and between a core's chains the user sets it by dragging a chain left or right (see **A core's chains run from left to right**).

## Done
- **The main page is the pipeline designer** (`src/ui/pipeline_designer/pipeline_designer.cpp`), with the ephys viewer hidden for now, its code untouched; tabs between the two come later (decided by the user).
- **The panel of processors** at the left (`processors_panel.cpp`) shows every processor of `all_processors.cpp` (see **Done** in generator.md), grouped as inputs, operators and outputs (decided by the user; see **Three kinds, by their connections** in engine.md): opened, its description, its file, its options with type and default, and its connections with direction and kind. The "(i)" beside an option or connection shows its description.
- **A box for each core shown**, side by side, with the next core's box shown during a drag (see **Every core from 0 up to the highest one in use has a box**). A processor dragged from the panel into a box comes into existence there: it is added to the graph (see **The graph as code** under **Done** in generator.md) and drawn at the top of the box, beside those already there, with its name and its type. The box is marked while a processor is dragged over it.
- **Ports on a block**: its inputs on top, its name and type in the middle, its outputs at the bottom, as the data flows. Each port is a row with its name, fainter when it may stay unconnected, and a line in the colour of what it carries (samples blue, events orange, a state value green, a port with slots grey). What a port is, the panel at the left explains, not the block. Since 23 November 2026 a block shows its ports only under the mouse, or with every port switched on (see **A port's name shows only while a connection is made** in the open questions).
- **Which cores are isolated** is read from `/sys/devices/system/cpu/isolated` (`cpu_cores.cpp`), and the number of cores from `present` there, not from the cores the program may run on, which leaves the isolated ones out.
- **Connecting**: a click on a port, an output or an input, picks it, and a line follows the mouse from it; the ports of the other direction that it fits are marked, and every other port, of either direction, is greyed and can't be clicked (decided by the user); a click on a marked one makes the connection. A second click on the picked port, Escape, a right click anywhere, or a click anywhere but on a marked port lets it go (the last two decided by the user). A greyed port's tooltip says why it doesn't fit the picked one (decided by the user, who had taken an input that already had its one connection for a fault): the same processor, another kind, already connected to it, an input that has its one connection, or a port of the picked one's own direction. While no port is picked, a right click on an input removes its connections, a first way to do that and not yet decided. A line leaves its output's block at the bottom and reaches its input's block from above, in the colour of what it carries, so between two cores it has the shape of an S.
- **A click on a port's row** picks or connects the port. Once a connection's line ended bare at the edge: a dot there, which did nothing, made the user take connecting for broken. Since 23 November 2026 a circle lies there again, by the user's wish (see **Every port has a circle** in the open questions). Until 23 November 2026 a row began with a dot in its port's colour, 1.4 text lines high, which the user had decided as the port's one dot; the port's line took its place (Claude's, after the drawing the user confirmed that day, which has no dot; not asked).
- What "fits" checks so far: that the two ports carry the same kind, samples, events or a state value, that the input is free or has slots, and that the two are ports of different processors. Not yet: a stream's channels and rate or an event's type (see **Types across the graph** in generator.md).
- **Rows of a core** (`core_layout.cpp`): a processor is drawn one row under the lowest processor of its core that it reads samples or events from, and in the top row when it reads from none; a row is as high as its tallest block, with room under it for the lines.
- **Places inside a row** (`core_layout.cpp`): a processor stands under the one it reads from in the row above, the first in the core's list when it reads from several there. Those that stand under one processor are side by side in the order of the core's list, a first way and not decided, and it is centred over them. Those that stand under none are side by side from the left in the order of the core's list, which is the chains' order. A place is counted in blocks, with halves, so nothing has coordinates.
- **Drop places** (see **A drag shows drop places in the core under the mouse** and **Nothing moves during a drag**), which the user ran and found easy to aim at. Which box the mouse is over is told from where the boxes were drawn the frame before. A processor from the panel goes into the core's list in front of the top of the chain at the drop place's right, or at the list's end.
- **A first pass over the look**, seen by Claude in its own pictures: a core's box with rounded corners and no rule under its name, which is bold; a block as a white card with rounded corners and a thin border, thicker and blue when selected, its name bold; a port's dot as a ring; softer colours for the lines and for a row under the mouse; the panel as plain rows under small grey titles; an option's long name cut on a block so that its value stays in sight. The redesign replaces it (see **What the designer does comes first, its look after**).
- **Streams** (see **Types across the graph** in generator.md), checked by the tests of the UI and not yet confirmed by the user. A processor that starts a stream shows it as a line on its block, above its options ("stream: 32 ch, 30000 Hz"), and its panel has a section above the options with two number boxes: the channel count, 1 at least, and the rate in Hz, above 0. A processor after it shows no stream on its block: the tooltip of a samples port says the stream it carries, or that it isn't known yet while no processor that starts one is connected before it.
- Built. Claude sees the app in pictures of it at rest (see **Guidelines** in CLAUDE.md), with an example pipeline that the environment variable `FALCON_EXAMPLE_PIPELINE` puts into the designer; what happens under the mouse only the user sees. Not there yet: moving and removing a processor; its options.
- Its lint needs one build first, since it includes the file the build generates.
- **The window's title bar** was missing under GNOME on Wayland, where an app draws its own through libdecor: the library was installed but not the plugin that draws the bar (the app says "No plugins found, falling back on no decorations"). `scripts/setup/install_deps.sh` now installs `libdecor-0-plugin-1-gtk`.
- **The window's title names the open pipeline** (asked for by the user on 23 November 2026, when the title bar of Falcon's own was put off: "show open pipeline in the title at least?"; built that day and checked by a test of the UI, which reads the title the app gave its window; not seen on the desktop's bar by anyone yet). While a pipeline is open the title is its name and the app's, e.g. "Memory impairment - Falcon", the name being the one in the designer's top bar, so the folder's for a pipeline without one; on the welcome screen it is "Falcon". The order and the hyphen are Claude's, and fine with the user that day ("its ok").
- **A connection's line lay over a tooltip** (reported by the user on 22 November 2026, fixed that day): the lines were drawn in front of every window, since the blocks are windows inside the cores' area and that area's own drawing lies under them. They are now drawn in a window of their own that lies over the cores' area and takes no mouse, so they stay over the blocks and a tooltip covers them.
