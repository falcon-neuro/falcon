# Release

How Falcon is packed and how it reaches a user's machine, and the whole state of that work: what is decided, what is done and what is open. Every task on releases is tracked here. Of the release itself nothing is made yet; the script that fetches the compiler is (see **The compiler is GCC** under **Decided**).

## Goal
Set by the user on 17 November 2026: the archive of a release, put on a fresh install of the latest stable Debian with no network, makes Falcon work flawlessly. So the archive carries everything Falcon needs that such a Debian lacks, and `install.sh` fetches nothing. The one exception is the realtime kernel (see **Decided**). **Taken back by the user on 21 November 2026**: the destination machine needs the internet, since Falcon needs its dependencies there, CMake and more. What of **Decided** below still holds is to go through (see **After the network is required** in the open questions).

## Why a release carries its own compiler
The UI compiles each pipeline on the user's machine (see generator.md). Every lab on one version of Falcon must compile with the same compiler, and a system update must never change it between two sessions. So the compiler is neither the system's nor installed into it: it sits in a folder of Falcon's, fetched as one exact version.

## Decided
By the user on 17 November 2026, unless a date is given.
- **One archive per release**: a GitHub release of Falcon is one `.tar.gz` that holds the UI's program, Falcon's repository as a zip, the compiler with what a pipeline's build needs of the system (see **What the archive holds, exactly** under **Open questions**), and `install.sh` in its main folder. So one version number fixes everything a lab runs.
- **Two ways to install, one script**. With the network: `curl falcon-neuro.org/install.sh | bash`, a short script on the website that finds the latest release, downloads its archive and runs the `install.sh` inside it. Without the network: the user downloads the archive on another machine, extracts it and runs that same `install.sh`. No Debian package.
- **The UI builds every pipeline against the installed repository**, reusing what a first build made, so that a build after the first takes milliseconds, not 10 s (the user's aim).
- **The realtime kernel is not in the archive**: the UI has a setting, "Switch to realtime kernel", that installs Debian's realtime kernel (preempt_rt) for the user, so that a user who isn't technical needs no terminal. It is the one step that needs the network. Until the user has switched, Falcon runs a pipeline on Debian's standard kernel with a warning.
- **The compiler is GCC** (18 November 2026), for its C++26 reflection, which clang lacks (see **Boundaries** in engine.md). It is Debian's own build of one exact version, GCC 16.2.0 as the packages of version 16.2.0-4, since GCC's project publishes source only and the one official binary is a distribution's. `scripts/setup/fetch_gcc.sh` fetches the 19 packages (72 MB) from snapshot.debian.org, which keeps every version of every Debian package for good, checks each against a checksum the script holds, and unpacks them into a folder in the repository's root, without installing them. So nothing of the system changes and no system update can change the compiler. Though built to sit in `/usr`, that GCC finds its own parts from the folder; the script proves it by compiling and running a small program before it calls the folder done. These packages need no newer C library than Debian 13 has. Unpacked they take 249 MB.
- **A release needs no clang** (18 November 2026). On a user's machine the compiler does one job, building a pipeline; the check of a processor's options, when it is built, asks the same compiler (see **The compiler checks a processor's options** in generator.md). Clang stays where Falcon is developed and where a release is made: the formatter, the lint, and the script that lists the processors, whose list is compiled into the UI's program. Needing clang to develop is fine, since few people will write a processor of their own and many more will only use Falcon. The one case that brings it to a lab: a lab that wants its own processor shown in the UI builds the UI again, which runs that script (see what follows **Its test** in generator.md).
- **`~/falcon/` is what the user sees, and the repository is hidden** (21 November 2026). `~/falcon/` holds what a user works with: the pipelines, each with its runs (see **Every pipeline has a directory of its own** in generator.md). The repository the engine lives in is on the machine only so that pipelines can be compiled there, and lies in one central place that is more hidden, not in `~/falcon/`.
- **The UI fetches the repository, into a folder at the machine's root** (21 November 2026). `install.sh` doesn't: the UI does it once it runs, as one of the chores it does to set a machine up anyway, such as isolating cores and switching off a network card's buffering (the two the user named from memory). The folder is at the machine's root and not in a user's home, so that every user of the machine can use Falcon. It is a shared folder, which every user may read and write, without a group of its own (decided by the user that day).
- **The UI is never built on a user's machine** (21 November 2026): a user's machine builds pipelines only, and gets the UI's program built. So the build of a pipeline is apart from the UI's and needs none of the UI's libraries (see **A pipeline's build without the UI's libraries** under **Open questions**). The one exception is a processor developer's machine: the list of processors stays baked into the UI's program, with no file in between, so a lab that wants its own processor shown in the designer builds the UI again (see **A release needs no clang**). Fine for the first prototype and its pilot users (decided by the user that day); what comes after is **Extensions that users download** under **UI** in beyond_prototype.md.
- **The UI looks for its own update when it starts** (21 November 2026): it checks Falcon's releases on GitHub for a newer version of itself, and does so before it brings the engine to its version (see **The UI's version must match the engine's** in generator.md). Parked by the user that day, with the engine's update: what the UI does when it finds one (proposed by Claude: it tells the user and offers a button, and never updates by itself, since an update changes the engine too), and what it does without a network.
- **Not chosen**: a UI that fetches the repository and the compiler itself (the user's first plan: three downloads to keep matching, and no install without the network); a Debian package depending on Debian's own compiler (years older than the one Falcon is written with); a disk image of Debian with everything in it (the most work, and the lab gives up its own installation); GCC installed with apt from Debian testing (it replaces the system's C++ runtime libraries, about 12 packages, for every program of the machine, takes them out of the stable release's security updates, and with a wrong priority for testing's packages lets the next upgrade take the whole system to testing); and our own build of the compiler from its source (official and exact too, but about 10 minutes of building, not measured, and a build to keep working).

## Open questions
- **After the network is required** (see **Goal**), to go through one at a time; everything under **Decided** that rests on an install without the network is open again:
  - The repository is a git clone, which follows from the engine being brought to a version by `git checkout` of its tag (see **The UI's version must match the engine's** in generator.md).
  - Which dependencies the install fetches (CMake, git and more), and how.
  - Whether a release is still one archive, and what is left of the way to install without the network.
  - Whether the compiler stays one exact fetched version: its reason, the same compiler in every lab, doesn't depend on the network.
- **Where the repository lies, exactly** (see **The UI fetches the repository** under **Decided**), not settled: the folder's path, e.g. `/opt/falcon/`. With it, Claude's points of 21 November 2026 on a folder that everyone writes, none decided: a file that one user makes there, by a build or by git, must stay writable by the others; git refuses to work in a repository that another user owns unless the machine's git settings name it as safe; and what a folder that anyone writes means for security, which is in [security.md](security.md). Also: an update of Falcon must keep the extensions that lie in it (see **Extensions** in engine.md).
- **What the archive holds, exactly**, a detail to settle when it is made (said by the user). Beyond the 19 packages: what the fetched GCC takes from the system today, which a fresh Debian may lack. That is the assembler and the linker (binutils), the C library's headers and startup files (`libc6-dev`), and the few libraries the compiler itself loads (`libisl`, `libmpc`, `libmpfr`). To check on a fresh install.
- **Cutting the compiler down to what a pipeline's build needs**, parked by the user on 18 November 2026 as a task of the release: of the 249 MB, the C compiler and the link-time optimiser, about 80 MB, are likely not needed (not tried).
- **A pipeline's build without the UI's libraries**, parked by the user on 18 November 2026, not urgent: users build pipelines over and over, and that build must not fetch and compile what only the UI needs (GLFW, Dear ImGui, glad), as the one `CMakeLists.txt` does today. Proposed by the user, not designed: a `CMakeLists.txt` of its own for pipelines, or an argument to CMake that leaves the UI's libraries out.
  - Raised again by the user on 21 November 2026: one `CMakeLists.txt` builds the UI and a pipeline as the same program, which suits neither: the UI needs no disassembly, and a pipeline needs no Dear ImGui. Proposed by Claude that day, not decided: two programs in the build, each built by its name, the UI with its libraries and without the disassembly, and the pipeline from the fixed place a `pipeline.cpp` is copied to (see **Every pipeline is built by the one repository** in generator.md), without the UI's libraries and with the disassembly; that also ends naming the program by hand. Still open then: configuring the one build fetches the UI's libraries even where only a pipeline is built, which two separate builds would avoid.
- **How fast a build gets**, not measured. The reused part is the precompiled header, made once on the user's machine by the compiler the archive carries (see **The compiler checks a processor's options** in generator.md). A new pipeline is still instantiated, optimised and linked each time: likely seconds, not milliseconds. Only a pipeline built before can be skipped, by keeping its engine program.
- **Switching to the realtime kernel, what is open**:
  - The switch needs root and a restart of the machine (see **Privileges** in beyond_prototype.md).
  - A machine that never has the network.
- **A test of the goal**, not designed: install the archive on a fresh Debian without network, e.g. in a virtual machine, then build and run a pipeline.
- **Installing a version other than the latest**, e.g. to repeat an earlier experiment: an argument to the website's script.
- **What `install.sh` does**: where it puts Falcon, whether it needs root, and whether two versions can sit side by side (see **Paths on Debian** and **Privileges** in beyond_prototype.md).
- **The licence texts** of GCC and of whatever else the archive carries must go with it.
