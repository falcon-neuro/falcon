# Generator

The part of Falcon that turns a graph into `pipeline.cpp`, the file an engine program is compiled from. This file is the generator's spec followed by its open questions: a question that is settled moves up into the spec. A section named here without a file, and not found in this one, is in [engine.md](engine.md). The node editor that hands it the graph is in [pipeline_designer.md](pipeline_designer.md).

## Decided
- **Where it is built** (decided by the user): in `src/ui/pipeline_designer/`, with the pipeline designer, the graph, the list of processors and its script. `src/core` holds the engine and nothing else: the engine runs without a designer or a generator, on a `pipeline.cpp` written by hand, so neither belongs to it. It is built first with no editor around it: C++ that turns a graph held in memory into `pipeline.cpp`.
- **What it writes** is the engine's `pipeline.cpp` (see **pipeline.cpp** in engine.md, for its layout, its loops and its names). Until it exists, `pipeline.cpp` is written by hand (see **Prototype plan** in engine.md).
- **UI and engine are separate programs** (see **Boundaries** in engine.md). The UI is the frontend. It generates `pipeline.cpp`, compiles it with the bundled clang into an engine executable, and runs that as a child process.
- **Graph definition** is a generated .cpp file (`pipeline.cpp`), compiled with the bundled clang (JIT plan).
  - The generator is simple drag-and-drop editor logic: after each edit to the graph in the UI, it regenerates `pipeline.cpp`. Users only place and connect processor nodes; they never write `pipeline.cpp`.
  - The UI re-opens a saved graph by reading `pipeline.cpp` back, so the file follows a fixed generated format. It holds no positions: where a processor is drawn follows from the graph alone (see **No free placement** in pipeline_designer.md).
- **Chains are detected automatically** by the generator each time it regenerates `pipeline.cpp` (see **Chains** in engine.md). The user never marks chains.
- Only processors placed on a core are written to the generated `pipeline.cpp`; everything else does not run. Empty cores stay idle, which lowers heat.
- **A file is only imported from** (decided by the user). The UI offers "import from file" for an option such as a filter's coefficients: when a file is picked, its values are read at once and shown to the user as imported, and from then on the option holds those values. A graph knows no file: `pipeline.cpp` holds the values as it holds any option's, and the generator never opens a file. Not chosen: keeping a link to a copy of the file in the project's folder and reading it each time `pipeline.cpp` is written.
- **The processors are read from their source by a script** (decided by the user). Clang won't have C++26 reflection any time soon, so a script reads each processor's definition, its options, its connections and its template parameters, from `src/processors/`. Proposed by the user as its language: Python.
- **The script reads clang's syntax tree, not the text** (decided by the user). Clang prints what it parsed of a processor's file as JSON, and the script takes the processor's definition from that, so it parses no C++ itself and a declaration it doesn't expect can't be skipped or misread without notice. Checked on RippleDetector: the tree holds its options with their types and default values, its template parameters, every member of its `Connections` with its type as written (e.g. `StateInput<float, 6.F>`, `std::optional<StateOutput<bool, false>>`) and its initializer (`UNCONNECTED`, `nullopt` or none), and, when clang is asked to keep all comments, the comment above each of them, which can serve as its explanation in the UI.
- **The script is a step of the build** (decided by the user). CMake runs it first: it reads the processors' folder and writes one C++ file, `all_processors.cpp` or a name like it, which the UI and the generator are then compiled with. So a processor added to the folder shows in the UI's panel after the next build, with nothing else to edit.
- **The compiler checks a processor's options, and nothing else does** (decided by the user). Neither the script nor the generator understands a rule, so there is no graph compiler of our own to keep right. The UI has clang check without building: the one processor being edited, asked for as that type with its options and its stream (`template struct SignalGenerator<Stream, {...}>;`), so that the error belongs to its node, and the whole `pipeline.cpp` before a run. What clang reports is the processor's own `static_assert`, with its message. To make it fast, the engine and every processor are parsed once into a precompiled header when Falcon is built. Measured over 5 runs each: 210 to 217 ms for one processor whatever the graph's size, and 240 to 330 ms for a whole pipeline, where a check took about 1 s. Of the 210 ms, nearly all is loading the precompiled header, 34 MB; starting clang takes 7 ms.
  - Parked: a checker that stays running with everything parsed in memory, as an editor's language server does (clangd, which comes with clang), for an answer in tens of ms. It adds a program to ship and its protocol to speak, and is not measured.
  - Not chosen: reading the `static_assert`s out of the source so that the UI evaluates them, which means rewriting a condition that names the stream as a type; one `check` function per processor, where a rule written elsewhere stays unseen; and rules in the options' types (`Positive<double>`), which cover only a rule about one option alone. The last stays possible where the UI wants a control's range before the user types.
- **Every `static_assert` about an option carries a message** (decided by the user), since that message is what the UI shows the user (see **The compiler checks a processor's options**). The script enforces it when Falcon is built: in clang's syntax tree a `static_assert` with a message has a text as its second part, and one about an option refers to `options` in its condition, so the script stops the build and names the file and line of any that has no message. Checked against a search of the text: both find the same 15 in `src/processors/` and the test processors; 3 more are in the Ripple Neuromed extension.
- **Every option has a doc comment, written for the user** (decided by the user), since the UI shows it as the option's description. It is strict: the script stops the build and names any option that has none. A doc comment is one that starts with `///`, on the lines above the option. Clang's syntax tree holds it with its option, checked on three options structs. The same comment then shows on the API website, since Doxygen reads doc comments and nothing else: that is why no option has a description there today. The code holds no doc comment at all, and the 246 comments in the processors are ordinary ones (`//`), which Doxygen ignores by design and clang gave only when told to keep every comment.
  - **The standard** (agreed by the user). In this order: what the option is, in one plain sentence in the user's words; its unit; which values are allowed and what the special ones mean; and what changing it does, where that isn't obvious. No names from the code and no types. RippleDetector's two options are written to it, as the sample for the rest.
  - **Every connection has one too** (decided by the user): each member of a processor's `Connections`, whatever it carries, samples, events or a state value. The UI shows it when the user hovers the port's info button. An input's says what it must be given and what the processor does with it; an output's says what it gives, on which sample, and what one event or the state's value means; a state input's also says what a change does. The script requires it as it requires an option's.
  - An ordinary comment stays what it is: a note for whoever reads the code (see the rules on comments in `.claude/CLAUDE.md`), never shown to a user.
  - One comment per option, above it: an option with a comment above and another at the end of its line came out with only the second (`ripple_frequency` in SignalGenerator).
  - **Every processor has one too** (decided by the user), above its struct: what it does, in the user's words, and what it needs, e.g. a core of its own. The UI shows it with the processor's entry.

## Done
- **The texts.** Every processor in `src/processors/` and the two under `custom/` has its description, and each of its options and connections a doc comment to the standard; every check about an option in its struct has a message. EventGenerator got a check it lacked, that its rate is above 0. The wording is for the user to review.
- **The script**, `src/ui/pipeline_designer/list_processors.py`: it asks clang for the syntax tree of each processor's file and writes `all_processors.cpp`. It stops the build, naming file and line, for a processor, option or connection without a doc comment, a check about an option without a message, a member of `Connections` of a type it doesn't know, and a file clang can't compile. A file with no processor in it is left out with a note (the Neuropixels input).
- **The script lists the values of an option whose type is a fixed list of values** (an enum), each as written in `pipeline.cpp`, e.g. `Waveform::Sine`: it asks clang about the option's type by its name, wherever the processor's file takes it from. The pipeline designer offers them as a list to choose from (see **A list to choose from for an option with a fixed list of values** in pipeline_designer.md).
- **What it writes**: one `ProcessorDescription` per processor (`src/ui/pipeline_designer/processor_list.cpp`): its name, its file, its description, its template parameters as written, its options (name, type, default as written, description) and its ports (name, direction, kind, whether optional, whether it has slots, type as written, description).
- **Two things it got wrong at first**, now right and noted in its code: an option's default is taken from the source's text, since rebuilding it from the tree's nodes lost the minus of SpikeDetector's `-50`; and a position in the tree counts bytes, not characters, since a `µ` in a comment shifted every position after it.
- **The build step**: `CMakeLists.txt` runs the script before the program is compiled and again when a file in `src/processors/` or `src/core/` is added or changed; the file goes to `build/generated/`. It takes about 8 s for the 12 processors.
- **A first panel in the UI** lists them (see **Done** in pipeline_designer.md).
- **The graph as code**, `src/ui/pipeline_designer/pipeline_graph.cpp`: a pipeline holds its cores, its processors and its connections. A processor has an id, its type, its name, its core and its options' values; a connection names a processor's output and another's input; a core keeps its processors in a list whose order gives its chains' places from left to right. It can add a processor to a core, with a name from its type's file (`ripple_detector`, then `ripple_detector_2`), and connect an output to an input, whose two ends are two types so they can't be given the wrong way round. The editor uses it. It has no streams: see **Types across the graph**.

## Open questions
- **Reflection in place of the script**, raised by the user on 18 November 2026, not designed: the script that reads the processors exists because clang has no reflection (see **The processors are read from their source by a script**), and Falcon is now built with GCC, which has it (see **No reflection soon** in the open questions of engine.md). Until it is replaced, the build keeps clang for the script alone, beside GCC. Checked on a small test: reflection gives an options struct's names with their default values, the names of the members of a `Connections`, and the values of an enum. It does not give a doc comment (see **Every option has a doc comment**), nor whether a `static_assert` has a message (see **Every `static_assert` about an option carries a message**), so both need another way first, e.g. the description as an annotation that reflection reads, which the API website then doesn't see. The formatter and the lint stay clang's either way.
- **A doc comment for each value of a fixed list**, e.g. what `SpikeTrain` gives against `RippleBursts`: none is written or asked for today, so the UI shows a value by its name alone. Whether the script should require one, as it does for every option.
In the order they block the work: the first three are the generator itself and are not designed. What is being built first is the editor: see **Next** in pipeline_designer.md.
- **What a graph is while held in memory**, shared with the pipeline designer: the node editor fills it and the generator reads it. Its first form is in code (see **The graph as code** under **Done**), without streams. The list of its components it grew from, proposed and not confirmed as a whole: The old Dart GUI (`falcon_gui/lib/model/falcon_graph.dart`) had the first five in some form; what it lacked is marked new.
  - **Processor type**: what a kind of processor is, apart from any graph: its C++ name and file, its template parameters, its options and its ports. The old GUI kept these as templates written by hand in Dart, a second copy of the C++ that could drift from it.
  - **Option**: a name, a type (whole number, number, yes or no, one of a list, text, file) and a value, written into `pipeline.cpp` as a compile-time constant. As in the old GUI, without its YAML kinds. A file is only a way to fill an option (see **A file is only imported from**).
  - **Port**: one member of a processor's `Connections`: its name, its direction, and its kind. New: the kind is samples, events or a state value, where the old GUI had one kind of port plus a flag for states, never validated, so it had no live change of a state either. New too: whether the port must be connected, and whether it has slots, so takes several connections.
  - **Processor**: one node of a graph: its name, which is its variable's name in `pipeline.cpp`, its type and its options' values. New: the core it sits on and its place in that core's order, which is also where it is drawn, so it has no position of its own.
  - **Connection**: from one processor's output port to another's input port, of the kind its ports have. New, and worked out, not set by the user: whether it stays on a core (a buffer or a state value) or crosses cores (a ring or a cross-core state value), and its name. New, set by the user: a ring's number of slots.
  - **Chain**, new, and worked out, never built by the user: processors of one core that feed one another in a row, drawn one under the other (see **The layout follows the connections** in pipeline_designer.md).
  - **Core**, new: its number, whether it is realtime, the processors dropped into it, and the order of its chains from left to right, which the user sets and which is their order in the core's loop. The old GUI had none, since Falcon 1 ran a thread per processor.
  - **Stream**, new: what a sample connection carries, a channel count, a rate and a sample type. It starts at an input processor and follows the connections, so that only matching ports connect and the types can be written. The old GUI compared two type names as text.
  - **Pipeline**: the whole graph and its name, which names its runs' directories.
  - Later, with the bridge to the UI (see **Order of work** in beyond_prototype.md): a state input that the UI writes during a run.
  - Worked out by the generator from these, never edited: buffers, rings, cross-core state values, each core's loop, the includes and the type names.
- **Types across the graph**, not designed. Each connection's type follows from what is upstream, as the compiler works it out; the generator must work it out too, so that only matching ports connect and the types can be written. From the processors as they are, five things: a stream taken from the input; a stream an input processor starts, which the user sets (channel count and rate); an event's type and capacity taken from the input; an options struct sized by what it holds (a filter's taps or sections, Recorder's slots); and one kind per slot of a port with slots.
  - **A stream's values are set on the input processor that starts it** (decided by the user on 17 November 2026), and nowhere else: not once for the whole pipeline, since two inputs can differ, e.g. a probe's two bands at two rates, and not on a connection, whose two ends could then disagree with the processor that gives the data. What follows from it, not designed: an input whose device fixes a value offers no free choice of it; a stream is no option of the processor, since in the engine it is part of the processor's type, so the designer would show it apart from the options; and what a processor gives downstream has to be worked out, since it can differ from what it takes. The user sets its channel count and its rate there and nothing else: every stream is float32 (decided by the user on 17 November 2026; see **Sample type** in engine.md), so the generator writes `float` for each.
  - **Which processor starts a stream, and which stream an output carries, is read from two names** (decided by the user on 17 November 2026), the ones the processors already use (see **Template parameters have descriptive names** in engine.md). A processor with a template parameter `OutputStreamInfo` starts a stream, so it is where the user sets one: today SignalGenerator, later a hardware input, and also a processor that changes the stream, such as a decimator, which has both names. A sample output written `SampleOutputBuffer<OutputStreamInfo>` carries the stream its processor starts, and one written `SampleOutputBuffer<InputStreamInfo>` the stream of its processor's input, unchanged; a sample input is `SampleInputBuffer<InputStreamInfo>`. The script stops the build for a samples connection written any other way, and for an output that carries `OutputStreamInfo` on a processor without that parameter. Not chosen: asking the compiler for each connection's type.
  - Done of it: the script writes, for each port, which of the two streams it carries, and for each processor whether it starts a stream; a processor of the graph that starts one holds its channel count and rate, 32 channels at 30000 Hz when it is added (Claude's choice; the user, asked, said only that the question concerns SignalGenerator alone); the graph gives the stream any output carries and any processor takes, followed back through the processors that pass theirs on (`stream_of_output`, `stream_taken_by` in `pipeline_graph.cpp`). The pipeline designer shows and sets it (see **Streams** under **Done** in pipeline_designer.md).
  - **Only SignalGenerator has a stream that the user sets** (said by the user on 17 November 2026). A hardware input's rate is fixed by its device: there is no choosing it for Blackrock, Neuropixels or Ripple Neuromed. Such an input can give two streams at two rates from two outputs, e.g. a probe's AP and LFP bands, which is fine. What follows, Claude's reading, not designed and not built, since no hardware input is in the list of processors yet: a stream belongs to an output, not to a processor, so `OutputStreamInfo` as the one name for "a stream this processor starts" covers SignalGenerator and not an input with two outputs; and a fixed stream's values would be read from the processor's source by the script and shown, not typed. A hardware input's channel count is chosen by the user (said by the user on 17 November 2026), so of its stream the rate is shown as given and the channel count is set. The packer (see **Channel selection** in beyond_prototype.md), which copies chosen channels of its input into a smaller stream, e.g. channels 5, 67 and 199 of 200, is a processor in the middle of a graph whose output's channel count follows from what the user picks on it; the user will say more on it later.
  - **An event connection's capacity is the giving processor's, never a setting** (confirmed by the user on 17 November 2026; see **Capacity** under **Events** in engine.md): no connection needs more room than its producer can fill in one pass. The processor that gives the events fixes it in its source, 1 on all five event outputs of today, and one that takes them has it as the template parameter `Capacity`, which the generator fills from the output connected to it. So the designer has no field for it. Trigger's input is written with 1, so it fits only an output of capacity 1.
  - **An event connection that doesn't fit is refused in the UI before it is made** (decided by the user on 17 November 2026), e.g. spikes into the Recorder: the second of the two ways below, not built. What an input takes is a rule of C++ in the processor's source, which neither the script nor the designer reads: Trigger takes only events that name channels (spikes, level crossings), LatencyBenchmark only events that come from a stream, Recorder only events that come from a stream and have no fields of their own (a ripple, a trigger, but not spikes or level crossings, whose channels it couldn't write; see **One file that describes itself** under **Recorder** in engine.md), and EventLogger and PCIeParallelOutput any event. The two ways that were weighed:
    - The compiler says it, after the connection is made: the designer lets any event output be connected to any event input, and the compiler's check of the pipeline shows the error on the processor (see **The compiler checks a processor's options, and nothing else does**). Nothing new to build, and always exact; but a wrong connection can be made first and is refused afterwards, where a port of the wrong kind is greyed beforehand.
    - The build works it out beforehand: for each event input, the script asks clang which kinds of event it takes and writes that into the list, so the designer greys the ports that don't fit and says why, as it does for a wrong kind. The build takes longer, a check per pair of event kind and input, and what depends on the stream, e.g. spikes of another stream than the one a Trigger works on, is still the compiler's to refuse.
    - **How the script asks clang**, not decided (weighed on 18 November 2026; the facts are read from the source, not tried). What an input takes is written in two forms today. As the constraint of a template parameter: EventLogger and PCIeParallelOutput (`std::derived_from<Event>`), LatencyBenchmark (`StreamEvent`), Trigger (`ChannelMaskEvent<InputStreamInfo>`). As a `static_assert` inside a type: Recorder's refusal of an event with fields of its own (in `RecorderSlotFormatOf`), behind its constraint `RecordableKind`, so asking that constraint about spikes stops the compiler with an error where it should answer no. The two ways:
      - The constraint alone: the script reads from the syntax tree which constraint guards the template parameter that the input's type names, and writes one file that asks it about each kind of event, compiled once. It needs no options and no other template parameter. It sees only what is written as a constraint, so Recorder's `static_assert` would move into its constraint and lose its message, and a processor's writer gets a rule: what an input takes is said in that constraint. What it misses, the designer lets through and the compiler refuses afterwards.
      - The whole processor: one small file per pair of event kind and input declares the processor with that kind, and the pair fits when it compiles. It sees every check, and clang's message could be the reason shown. It needs valid values for all else the processor takes, and a failure for another reason reads as "doesn't fit": Recorder's default options fail its own check, their slot names being empty. What it gets wrong, the designer refuses with no way around it.
    - To raise after that, one at a time: where the reason in a greyed input's tooltip comes from; which stream stands in for `InputStreamInfo` when a kind of event depends on one (`Spikes<InputStreamInfo>`, `LevelCrossings<InputStreamInfo>`); and how a kind of event is named to the user.
  - Not done of **Types across the graph**: an event's type and capacity taken from the input; an options struct sized by what it holds; one kind per slot of a port with slots; and refusing a connection whose stream differs from the one a processor already takes, which no processor of today can meet, since none has two samples inputs.
- **Writing `pipeline.cpp` and reading it back**, not designed: its fixed form (see **pipeline.cpp** in engine.md). It needs nothing beyond what the engine compiles, since a graph holds neither positions nor files, so reading it back gives the whole graph.
- **Its test**, proposed, to confirm: it writes an existing hand-written pipeline again, e.g. `ripple_detector_pipeline.cpp`, text for text after formatting.
- **Importing from a file**, what the rule under **Decided** leaves open:
  - Exact values: the import must read each value, and the generator write it, so that the compiled number is bit for bit the one in the file, or a comparison with Python or MATLAB differs in the last digit.
  - **Experiment files** in beyond_prototype.md, parked, still has each resource copied into the experiment's zip: to bring in line with a graph that knows no file.
  - A reader per kind of file (IIR sections, FIR taps, later an IMRO table), in the UI now and not in the generator, and what it checks when a file is picked, e.g. its `type` and `sampling_rate` (see **IirFilter** in engine.md).
- **The compiler's check**, what the rule under **Decided** leaves open:
  - What only the compiler tells a user, from the checks in today's processors (listed on 17 November 2026): a value outside what its option allows (a threshold of 0, a pin other than 2 to 9, a negative amplitude); a value against the stream (a frequency at or above half the rate, a filter designed for another rate, a smoothing time shorter than one sample); two options against each other (bursts so frequent that they overlap, a burst's peak below its background); what a list holds (no tap or section, an unstable section, a tap that is no number); and a text that isn't a plain name (a file name with a `/`, a name with other characters than letters, digits, `_` and `-`). The designer answers for the rest: that two ports carry the same kind, that an input has one connection unless it has slots, that a number is one, that a value of a fixed list is one of its values, and a stream's bounds; an event its input doesn't take is to be the designer's too (see **An event connection that doesn't fit is refused in the UI before it is made**).
  - The precompiled header is not made yet: one more step of the build, next to the script's. Without it a check takes about 1 s, not 0.2 s.
  - A whole pipeline's error and its node: clang names the line of `pipeline.cpp` that declares the processor, which the generator wrote.
  - Which clang does the checking on a user's machine: the bundled one, which compiles `pipeline.cpp` anyway.
- **The script**, what is left of it (see **Done** for what it does):
  - The processors under `custom/` are not listed: the script is given `src/processors/*.cpp` only, and an extension's file needs that extension's include paths.
  - It finds the structs to ask clang about by a search of the file's text, and asks once for each, which is most of its 8 s. A struct declared in a way that search misses is left out of the list, not misread.
  - An enum option's values, for a control that offers them, and what a struct inside an option holds (an IIR filter's section) are not listed.
  - To confirm, since they were Claude's choices: that it stays Python (the generator is C++, so the list crosses from one language to the other, as C++ the script writes); and the name `all_processors.cpp`, which could be read as the processors themselves when it holds their descriptions.
  - A lab's own processor (see **Extensions** in engine.md) shows in the UI only after the UI is built again, so that lab needs Falcon's source and build tools, not only the installed program.
- **Doc comments**, what the rule under **Decided** leaves open:
  - How much of the standard the script can enforce beyond a doc comment being there.
  - Each processor's file still starts with an ordinary comment that says what it does, for whoever reads the code, now beside the doc comment for the user: whether both stay.
