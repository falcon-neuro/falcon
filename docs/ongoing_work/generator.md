# Generator

The part of Falcon that turns a graph into `pipeline.cpp`, the file an engine program is compiled from. This file is the generator's spec followed by its open questions: a question that is settled moves up into the spec. A section named here without a file, and not found in this one, is in [engine.md](engine.md). The node editor that hands it the graph is in [pipeline_designer.md](pipeline_designer.md).

## Decided
- **Where it is built** (decided by the user): in `src/ui/pipeline_designer/`, with the pipeline designer, the graph, the list of processors and its script. `src/core` holds the engine and nothing else: the engine runs without a designer or a generator, on a `pipeline.cpp` written by hand, so neither belongs to it. It is built first with no editor around it: C++ that turns a graph held in memory into `pipeline.cpp`.
- **What it writes** is the engine's `pipeline.cpp` (see **pipeline.cpp** in engine.md, for its layout, its loops and its names). Until it exists, `pipeline.cpp` is written by hand (see **Prototype plan** in engine.md).
- **UI and engine are separate programs** (see **Boundaries** in engine.md). The UI is the frontend. It generates `pipeline.cpp`, compiles it into an engine executable with the compiler a release carries, GCC (see release.md), and runs that as a child process.
- **Graph definition** is a generated .cpp file (`pipeline.cpp`), compiled with that compiler (JIT plan).
  - The generator is simple drag-and-drop editor logic: after each edit to the graph in the UI, it regenerates `pipeline.cpp`. Users only place and connect processor nodes; they never write `pipeline.cpp`.
  - The UI re-opens a saved graph by reading `pipeline.cpp` back, so the file follows a fixed generated format. It holds no positions: where a processor is drawn follows from the graph alone (see **No free placement** in pipeline_designer.md).
- **Chains are detected automatically** by the generator each time it regenerates `pipeline.cpp` (see **Chains** in engine.md). The user never marks chains.
- Only processors placed on a core are written to the generated `pipeline.cpp`; everything else does not run. Empty cores stay idle, which lowers heat.
- **A file is only imported from** (decided by the user). The UI offers "import from file" for an option such as a filter's coefficients: when a file is picked, its values are read at once and shown to the user as imported, and from then on the option holds those values. A graph knows no file: `pipeline.cpp` holds the values as it holds any option's, and the generator never opens a file. Not chosen: keeping a link to a copy of the file in the project's folder and reading it each time `pipeline.cpp` is written.
- **The processors are read from their source by a script** (decided by the user). Clang won't have C++26 reflection any time soon, so a script reads each processor's definition, its options, its connections and its template parameters, from `src/processors/`. Proposed by the user as its language: Python. Kept by the user on 18 November 2026, though Falcon is now built with GCC, which has reflection (see **The compiler is GCC** under **Boundaries** in engine.md): the script gives what reflection can't. Reflection sees no comment, so no description; it knows a template's arguments once the template is used, never its list of parameters as written; it gives an option's type after the template is filled in and its default after it is computed, never either as written; it can't tell whether a `static_assert` has a message; and to see inside a processor it needs one valid example of it with every template parameter filled in, where some processors refuse their own default options. So the build keeps clang beside GCC, for the script as for the formatter and the lint.
- **The script reads clang's syntax tree, not the text** (decided by the user). Clang prints what it parsed of a processor's file as JSON, and the script takes the processor's definition from that, so it parses no C++ itself and a declaration it doesn't expect can't be skipped or misread without notice. Checked on RippleDetector: the tree holds its options with their types and default values, its template parameters, every member of its `Connections` with its type as written (e.g. `StateInput<float, 6.F>`, `std::optional<StateOutput<bool, false>>`) and its initializer (`UNCONNECTED`, `nullopt` or none), and, when clang is asked to keep all comments, the comment above each of them, which can serve as its explanation in the UI.
- **The script is a step of the build** (decided by the user). CMake runs it first: it reads the processors' folder and writes one C++ file, `all_processors.cpp` or a name like it, which the UI and the generator are then compiled with. So a processor added to the folder shows in the UI's panel after the next build, with nothing else to edit.
- **The compiler checks a processor's options, and nothing else does** (decided by the user). Neither the script nor the generator understands a rule, so there is no graph compiler of our own to keep right. The UI has the compiler check without building: the one processor being edited, asked for as that type with its options and its stream (`template struct SignalGenerator<Stream, {...}>;`), so that the error belongs to its node, and the whole `pipeline.cpp` before a run. What it reports is the processor's own `static_assert`, with its message. To make it fast, the engine and every processor are parsed once into a precompiled header when Falcon is built. Measured over 5 runs each: 210 to 217 ms for one processor whatever the graph's size, and 240 to 330 ms for a whole pipeline, where a check took about 1 s. Of the 210 ms, nearly all is loading the precompiled header, 34 MB; starting clang takes 7 ms. These were measured with clang, the compiler then; with GCC, the compiler since 18 November 2026 (see **Boundaries** in engine.md), they are to measure again.
  - **A Compile button builds the whole pipeline into its executable, and the UI shows the compiler's errors** (decided by the user on 21 November 2026, for the prototype). The Run button is enabled only while the executable was built from the graph as it stands: any change to the graph disables it until the next Compile (confirmed by the user on 21 November 2026). How that is told: the `pipeline.cpp` the executable was built from is kept beside it, as `.last_compiled_pipeline.cpp`, a copy made just after a compilation that succeeded (the name is the user's note of that day, "probably"; it lies in the pipeline's directory), and Run is enabled while the generator would write the same text now, which also holds after Falcon is closed and opened again. Nothing is checked while a value is typed: rules that the UI itself runs at once are parked (see **Options validated while they are typed** under **UI** in beyond_prototype.md). Claude's reading, not yet confirmed: the build is then the prototype's one check, and the check without building, above, is not part of it. What is open of the button: see **The Compile button** under **The compiler's check** in the open questions.
  - Parked: a checker that stays running with everything parsed in memory, as an editor's language server does (clangd, which comes with clang and so not with the compiler a release now carries), for an answer in tens of ms. It adds a program to ship and its protocol to speak, and is not measured.
  - Not chosen: reading the `static_assert`s out of the source so that the UI evaluates them, which means rewriting a condition that names the stream as a type; one `check` function per processor, where a rule written elsewhere stays unseen; and rules in the options' types (`Positive<double>`), which cover only a rule about one option alone. The last stays possible where the UI wants a control's range before the user types.
- **Every `static_assert` about an option carries a message** (decided by the user), since that message is what the UI shows the user (see **The compiler checks a processor's options**). The script enforces it when Falcon is built: in clang's syntax tree a `static_assert` with a message has a text as its second part, and one about an option refers to `options` in its condition, so the script stops the build and names the file and line of any that has no message. Checked against a search of the text: both find the same 15 in `src/processors/` and the test processors; 3 more are in the Ripple Neuromed extension.
- **Every option has a doc comment, written for the user** (decided by the user), since the UI shows it as the option's description. It is strict: the script stops the build and names any option that has none. A doc comment is one that starts with `///`, on the lines above the option. Clang's syntax tree holds it with its option, checked on three options structs. The same comment then shows on the API website, since Doxygen reads doc comments and nothing else: that is why no option has a description there today. The code holds no doc comment at all, and the 246 comments in the processors are ordinary ones (`//`), which Doxygen ignores by design and clang gave only when told to keep every comment.
  - **The standard** (agreed by the user). In this order: what the option is, in one plain sentence in the user's words; its unit; which values are allowed and what the special ones mean; and what changing it does, where that isn't obvious. No names from the code and no types. RippleDetector's two options are written to it, as the sample for the rest.
  - **Every connection has one too** (decided by the user): each member of a processor's `Connections`, whatever it carries, samples, events or a state value. The UI shows it when the user hovers the port's info button. An input's says what it must be given and what the processor does with it; an output's says what it gives, on which sample, and what one event or the state's value means; a state input's also says what a change does. The script requires it as it requires an option's.
  - An ordinary comment stays what it is: a note for whoever reads the code (see the rules on comments in `.claude/CLAUDE.md`), never shown to a user.
  - One comment per option, above it: an option with a comment above and another at the end of its line came out with only the second (`ripple_frequency` in SignalGenerator).
  - **Every event type has one too** (decided by the user on 18 November 2026), above its struct: what an event of that kind says and when it is made, in the user's words, so that a user can read what e.g. a Spikes event is. The UI shows it where it names the event's kind, the API website prints it, and the script requires it as it requires an option's. Done on 18 November 2026: the script reads it and stops the build, naming the event type and its line, when one is missing (tried); and today's five event types (`Ripple`, `Spikes`, `LevelCrossings`, `TriggerEvent`, `ScheduledEvent`) each have a text, written by Claude and to review with the other texts. Not done: the UI showing it.
  - **Every processor has one too** (decided by the user), above its struct: what it does, in the user's words, and what it needs, e.g. a core of its own. The UI shows it with the processor's entry.
- **`pipeline.cpp` is read by a reader of our own, for its fixed form alone** (decided by the user on 21 November 2026). It takes only what the writer writes, keeps an option's value as the text it is written with, as the UI holds it, and refuses anything else, naming the line. So it needs nothing installed, and each construct the writer gains gets its reading in the same step (see **Writing `pipeline.cpp` and reading it back** in the open questions). Its costs, accepted: a `pipeline.cpp` edited by hand outside the form can't be opened, and the form is held twice, by the writer and by the reader, which only the round trip keeps alike (see **Its test** in the open questions).
  - Not chosen: the compiler's syntax tree, as the build's script reads the processors, which reads any valid C++. The tree is clang's and a release carries GCC alone (see release.md), so clang would ship too, and the engine would be parsed each time a pipeline is opened. Nor the graph saved as data beside `pipeline.cpp`, two files that can disagree.
- **Every pipeline has a directory of its own**, `~/falcon/pipelines/<pipeline name>/` (decided by the user on 21 November 2026), made when the user creates a new pipeline, empty or from a template pipeline chosen from a list. It holds `pipeline.cpp`, the compiled executable and `runs/`, with a directory for each of the pipeline's runs, so that each pipeline owns its runs (see **Each run writes into a directory of its own** in engine.md), all at its top: no `src/` and no `bin/` folder, which the user first had and dropped that day. And nothing else: no `resources/` folder, since a graph knows no file (see **A file is only imported from**), and no `CMakeLists.txt`, since the UI builds every pipeline against the installed repository (see **Decided** in release.md), so that no build setting is copied into a pipeline. `~/falcon/pipelines/` is where a new pipeline is made; a pipeline's directory that lies anywhere else can be opened too, and nothing may depend on where it lies (decided by the user that day). What is open: see **A pipeline's directory** in the open questions.
- **A pipeline's description is a marked comment block at the top of `pipeline.cpp`** (decided by the user on 21 November 2026): the lines between a start and an end line, each a comment, something like `// falcon-pipeline-description-start` and `// falcon-pipeline-description-end`; the exact spelling is settled when it is written. The reader keeps the description in the graph, the writer writes it back, and the list of templates can show it. The block also holds the pipeline's name, which is free text for people and not its directory's name (decided by the user that day), e.g. `Name: Memory Impairment Experiment` and `Description: Using gamma oscillations and bursts...` for a pipeline that lies in `memory_impairment/`. The UI shows the name; the directory's name only says where the pipeline lies. **It is one block for everything about the pipeline** (decided by the user on 21 November 2026): the name, the description, the version of Falcon that generated it (see **In `pipeline.cpp`: the version alone** below), and whatever is added later, each as a line of the form `Key: value`. So the version has no line of its own outside the block, and the block's marker lines name the whole block, not the description; they are `// falcon-pipeline-header-start` and `// falcon-pipeline-header-end` (Claude's proposal, confirmed by the user that day).
- **Every pipeline is built by the one repository, as its build's target** (decided by the user on 21 November 2026). Falcon's repository lies in one central, hidden place on a machine (see **`~/falcon/` is what the user sees, and the repository is hidden** in release.md), and Compile runs that repository's own build with the pipeline at hand as what to build. How the build gets the pipeline (the user's idea of that day): the UI copies the pipeline's `pipeline.cpp` to one fixed place in the repository, which is what the build always compiles, and puts the executable into the pipeline's directory afterwards. So only that file's content changes from one compilation to the next, never the build's settings, and the build doesn't configure itself again when another pipeline is compiled (not chosen: handing the build the pipeline's path as a setting, which does). So a pipeline's directory holds no build file, the build's intermediate files lie with the repository, and one build serves all pipelines in turn. That is fine because a machine compiles one pipeline at a time (Claude's reading of the user's "once per machine", not confirmed). A lab's own processors lie in that repository as extensions, each a git repository of its own (see **Extensions** in engine.md), and show in the designer once the UI is built again there (see **A release needs no clang** in release.md).
- **A pipeline says which version of Falcon generated it, and an executable which engine it was built from** (decided by the user on 21 November 2026), so that it can be told for certain whether an executable is the output of a given `pipeline.cpp` and engine.
  - **In `pipeline.cpp`: the version alone, as a comment at the top**, something like `// Generated by Falcon: v26.7.27`, which the generator fills in from the UI's own version; it is a line of the one block at the top (see **A pipeline's description is a marked comment block** below). No commit hash, and no text in the code: the user's first form of that day, a hash written as a text in the code, was replaced by this one the same day. A generated `pipeline.cpp` is never tracked by git, and may even lie in the build's folder.
  - **A `pipeline.cpp` without that comment is read all the same** (decided by the user on 21 November 2026), e.g. the repository's hand-written pipelines, which nobody generated: it counts as never compiled, and the comment is put in at once. Claude's reading of "at once", to confirm: when the designer opens the file, not only at the next Compile.
  - **The UI's version must match the engine's**, so the UI's version is also that of the engine a pipeline is compiled with. When they differ, e.g. after the UI was updated, the UI says so and offers one button that brings the engine to the UI's version, by `git checkout` of that version's tag in the repository; until then Compile is disabled (decided by the user on 21 November 2026).
  - **The version** is written by hand in one place, the project's version in the root `CMakeLists.txt`, outside the source files, as an extension's is in its own (see **Versioning** under **Extensions** in engine.md), and is set before a release; the release's tag is that version with a `v` in front, e.g. `v26.7.27` (decided by the user on 21 November 2026, in place of asking git for it, e.g. by `git describe`, which was agreed earlier that day). The build gives it to the compiler as `FALCON_VERSION`, one for the engine and the UI. A version is the date of its release, not a semantic version (the user, that day): year, month and day, as the repository's tag `v26.7.27` has it, which the project's version in `CMakeLists.txt` can hold as three numbers. It stands at 26.11.21 (the user's choice on 21 November 2026, no release being cut that day). The writer reads it itself: it is no argument of `write_pipeline`, which writes a graph, and the version is not the graph's (the user).
  - **In the executable: the engine's own version and commit hash**, which the engine writes into the log at the start of every run (see **The engine writes its own version into the run's log** in the open questions of engine.md) and a plain command such as `strings` finds. `pipeline.cpp` hands the engine nothing, which the user rejected as runtime injection.
  - No compilation is needed only while the pipeline's version is today's. It takes the place of any check by a file's time. What is open: see **What an executable was built from** under **A pipeline's directory** in the open questions.
- **`pipeline.cpp` holds as few comments as possible** (decided by the user on 21 November 2026): the one block at the top, with the name, the description and the version (see **A pipeline says which version of Falcon generated it** and **A pipeline's description is a marked comment block** above), and no other. No marks around its sections, and not even the `// Processors` and `// Connections` lines of today's pipelines: the reader tells a processor from a connection by the type a line declares. It skips every other comment, e.g. a hand-written pipeline's note on a ring's size, which has no place in a graph and is lost once the designer writes the file again. Considered and dropped that day as too verbose: marks with a fixed spelling around each section, e.g. `// falcon-processor-section-start`.
- **The writer names every option, and the reader takes a file that leaves some out** (decided by the user on 21 November 2026). A generated `pipeline.cpp` is descriptive: each processor is written with all of its options, also those that have their default value. A hand-written one may leave out an option, which the reader then gives its default. So a generated pipeline keeps its values when a later version of Falcon changes a default.
- **The writer has a plain layout of its own, and the reader ignores layout** (decided by the user on 21 November 2026). No formatter runs on a generated `pipeline.cpp`: a release carries GCC and so no clang-format (see **A release needs no clang** in release.md). The reader reads tokens, not lines, so it reads a file that a person or a formatter laid out just as well. To take up again if Falcon ships clang one day in place of GCC (the user).
- **A core's function is named by its core's number** (decided by the user on 21 November 2026): the writer writes `core4` for core 4. The reader takes a core's number from the list given to `run_on_cores` and accepts any name for the function, since hand-written pipelines differ here (`core1` on core 4 in `spike_detector_pipeline.cpp`, `core4` on core 2 in `filter_comparison_pipeline.cpp`).
- **A stream is named after the processor that starts it** (decided by the user on 21 November 2026), by that processor's name in the pipeline and not its type: `signal_generator` gives `SignalGeneratorStream`, a second one, `signal_generator_2`, gives `SignalGenerator2Stream`, and one renamed to `probe_a` gives `ProbeAStream`. Processor names are unique in a pipeline, so the streams' names are too. The reader accepts any name, hand-written pipelines choosing theirs freely (`TestStream`, `LatencyStream`), and doesn't keep it.
- **A connection that crosses cores holds its ring's number of slots, which the user can change in the UI** (decided by the user on 21 November 2026). The graph keeps it, the writer writes it and the reader reads it back; hand-written pipelines set it from 4 to 16384. Not in code. Its default is 64, or 16384 where the reading core isn't realtime, as today's recorder pipelines have (confirmed by the user that day). Open: where in the designer it is changed (see **What follows from a fixed layout** in the open questions of pipeline_designer.md).
- **The writer spells out every processor's full type, and the reader refuses a type that is named once and used for several** (decided by the user on 21 November 2026), e.g. `using PassThroughFilter = FirFilter<...>;` for the seven filters of `fir_chain_latency_pipeline.cpp`: a graph has no such shared type. The reader names the line, so that pipeline opens in the designer only once it is rewritten.
- **The reader refuses an option's value that names a stream** (decided by the user on 21 November 2026), e.g. `.design_rate = LatencyStream::rate` in `fir_chain_latency_pipeline.cpp`: the writer renames the stream (see **A stream is named after the processor that starts it**), so the value would no longer compile. The reader names the line and says that a plain value is expected; the value is written out by hand, e.g. `40000.0`.
- **A buffer is named by its upstream processor and its output, a ring also by the core that reads it** (decided by the user on 21 November 2026, not in code): `<processor>_<output>_buffer`, e.g. `signal_generator_output_buffer`, with no `_to_` and no reader in it, so the name is short, unique, and stays when a reader is added or removed. An output has one ring for each core that reads it, and a ring's name is what the log shows when the ring is full, so a ring's name adds that core: `<processor>_<output>_ring_to_core<number>`, e.g. `signal_generator_output_ring_to_core5`; the core is always written, also where only one core reads the output (confirmed by the user that day), so a ring's name doesn't change when a second core starts to read. The reader accepts any name, a name following from the graph. A state value follows the same rule (decided by the user that day): `ripple_detector_is_ripple_ongoing_state`, where today's name has both ends; Claude's reading, to confirm: one that crosses cores keeps its ending, `_cross_core_state`. It replaces the names of **Buffer names** under **pipeline.cpp** in engine.md, which the hand-written pipelines still have.
- **Any folder with a `pipeline.cpp` that starts with the comment block is a Falcon pipeline** (decided by the user on 21 November 2026): that is how a pipeline is recognised, wherever the folder lies (see **Every pipeline has a directory of its own** and **A pipeline's description is a marked comment block** above). The block is what makes a folder show as a pipeline; a `pipeline.cpp` without it, e.g. a hand-written one, can still be opened on request and then gets its block (confirmed by the user that day), as **A `pipeline.cpp` without that comment is read all the same** says of the version's line.
- **A template is a ready pipeline of the repository** (decided by the user on 21 November 2026): one of a handful of Falcon pipelines kept there, each with its name and description. Choosing one for a new pipeline copies it into the new pipeline's directory, and the designer opens the copy, never the template.

## Done
- **The texts.** Every processor in `src/processors/` and the two under `custom/` has its description, and each of its options and connections a doc comment to the standard; every check about an option in its struct has a message. EventGenerator got a check it lacked, that its rate is above 0. The wording is for the user to review.
- **The script**, `src/ui/pipeline_designer/list_processors.py`: it asks clang for the syntax tree of each processor's file and writes `all_processors.cpp`. It stops the build, naming file and line, for a processor, option or connection without a doc comment, a check about an option without a message, a member of `Connections` of a type it doesn't know, and a file clang can't compile. A file with no processor in it is left out with a note (the Neuropixels input).
- **The script lists the values of an option whose type is a fixed list of values** (an enum), each as written in `pipeline.cpp`, e.g. `Waveform::Sine`: it asks clang about the option's type by its name, wherever the processor's file takes it from. The pipeline designer offers them as a list to choose from (see **A list to choose from for an option with a fixed list of values** in pipeline_designer.md).
- **What it writes**: one `ProcessorDescription` per processor (`src/ui/pipeline_designer/processor_list.cpp`): its name, its file, its description, its template parameters as written, its options (name, type, default as written, description) and its ports (name, direction, kind, whether optional, whether it has slots, type as written, description).
- **Two things it got wrong at first**, now right and noted in its code: an option's default is taken from the source's text, since rebuilding it from the tree's nodes lost the minus of SpikeDetector's `-50`; and a position in the tree counts bytes, not characters, since a `µ` in a comment shifted every position after it.
- **The build step**: `CMakeLists.txt` runs the script before the program is compiled and again when a file in `src/processors/` or `src/core/` is added or changed; the file goes to `build/generated/`. It takes about 8 s for the 12 processors.
- **A first panel in the UI** lists them (see **Done** in pipeline_designer.md).
- **The graph as code**, `src/ui/pipeline_designer/pipeline_graph.cpp`: a pipeline holds its cores, its processors and its connections. A processor has an id, its type, its name, its core and its options' values; a connection names a processor's output and another's input; a core keeps its processors in a list whose order gives its chains' places from left to right. It can add a processor to a core, with a name from its type's file (`ripple_detector`, then `ripple_detector_2`), and connect an output to an input, whose two ends are two types so they can't be given the wrong way round. The editor uses it. It has no streams: see **Types across the graph**.
- **The writer, its first step**, `src/ui/pipeline_designer/pipeline_writer.cpp` (21 November 2026): `write_pipeline(graph)` gives the text of a `pipeline.cpp`, or the reason why the graph can't be written, and never a guess. It writes the header block, the includes, each core's function (processors, buffers, loop) and `main`, in the form under **Decided**. What a processor's type is given follows from the graph alone: its options, all named, and for every other template parameter what the output connected to its input has at the same place of its type, e.g. EventLogger's `EventType` and `Capacity` from `EventOutputBuffer<ScheduledEvent, 1>`. A core's processors are called so that each comes after those of its core it reads from, a chain from its top to its bottom. The graph as code holds a description for it.
  - In this step it wrote pipelines of events on one core, e.g. EventGenerator into EventLogger, and refused the rest by name (the second step, below, lifts some of it): a processor that starts a stream, a connection of samples or of a state value, a connection between two cores, an input that takes several connections, an option that is a list, a name or description of more than one line, a processor's name that is no variable's name or is used twice.
  - Run by its test (see **Tests of the pipeline's writer and reader** in test_suite.md). The app doesn't call it yet.
  - Whether what it writes compiles and runs isn't tried. Nothing known stands against it: `main` and `run_on_cores` have the engine's form (see **`main()` hands its arguments to `run_on_cores`** in engine.md), and its includes, named from `src/`, resolve, the build pointing the compiler at that folder.
- **The reader, its first step**, `src/ui/pipeline_designer/pipeline_reader.cpp` (21 November 2026): `read_pipeline(text, processor_types)` gives the graph that the text of a `pipeline.cpp` says, or the line and the reason why it can't be read, and never a guess. It reads what the writer's first step writes (see **The writer, its first step** above): the header block, each core's function with its processors, buffers and loop, and `main`. It reads tokens, so layout and comments don't matter to it, and it skips the includes.
  - What it takes beyond the writer's own form, as decided: a file without the header block; a core's function of any name, its core's number being read from `main`; options that are left out, which get their defaults, and an options type written in front of the braces; buffers of any name; and whatever stands in front of the cores in `run_on_cores`, `main`'s arguments or a run's name in an older file, none of which a graph holds.
  - What it refuses, each with its line: anything outside a core's function and `main`, e.g. a ring or a `using`; a type that is no processor of this Falcon's list and no buffer; a processor that starts a stream; an option that is a list; an option the type doesn't have, or one named twice; a processor whose name in quotes isn't its variable's; two processors of one name; a processor that is declared and never called, or called twice; a port its type doesn't have; a buffer that isn't declared, has two writers or none; a connection that isn't of events or doesn't fit; a port given several buffers; a function that `main` doesn't name, or names twice.
  - Run by the same test. The app doesn't call it yet.
- **The writer and the reader, their second step** (21 November 2026): streams, connections of samples, and rings between cores, so that a pipeline such as `spike_detector_pipeline.cpp` is written and read. Run by their test (see **Tests of the pipeline's writer and reader** in test_suite.md).
  - A stream: the writer writes `using SignalGeneratorStream = StreamInfo<32, 30000.0, float>;` for every processor that starts one (see **A stream is named after the processor that starts it** under **Decided**), with a rate that is a whole number written with `.0`, and gives the name to that processor's type; the processors after it get it from their connections, as they get an event's type. The reader takes a stream of any name, or one written out in a processor's type, and refuses an option's value that names a stream.
  - A ring: the graph's connection holds its number of slots where the user set one (see **A connection that crosses cores holds its ring's number of slots** under **Decided**); the UI has no way to set it yet. The writer declares a ring for every output and every other core that reads it, in front of the cores' functions. An output with one ring and no reader on its own core writes straight into the ring; any other gets a buffer, which is given its rings. The reader takes rings and buffers of any name, and gives a connection the ring's number of slots only where it isn't the usual one.
  - Refused by the reader besides: a `using` that names anything but a stream; a ring that is read on two cores, or written and never read.
  - Still refused by both after this step: a connection of a state value, an input that takes several connections, and an option that is a list, which the third step, below, lifts.
  - A limit: a core's list comes back in the order of its calls. Its chains keep their order from left to right; the list itself may not be the one the graph was written from.
- **The writer and the reader, their third step** (21 November 2026): an option that is a list, e.g. a FirFilter's `taps` and an IirFilter's `sections`. Run by their test (see **Tests of the pipeline's writer and reader** in test_suite.md).
  - The graph holds a list as one text, its elements between one pair of braces, e.g. `{0.5, 0.5}`, like any option's value.
  - The writer counts the elements and writes the options' type with that length in front, since the type is sized by its list: `FirFilterOptions<2>{.design_rate = 30000.0, .taps = {{0.5, 0.5}}}`. It writes every list between two pairs of braces: a `std::array` of structs, such as the sections, doesn't compile with one pair, and one of numbers takes two as well. The type's name is read from the template parameter that takes the options.
  - The reader ignores the written length. It puts every option's value on one line, so a list laid out over many lines is held as the UI could have written it, and takes a list with one pair of braces or two.
  - Refused by both, by name: a processor whose type takes an argument for each of its connections, which today is the Recorder; it also has an input that takes several connections. Refused by the writer besides: a list that isn't in braces, two lists in one processor, and options with a list whose type's name isn't written in the processor's template parameter.
  - Of the repository's nine hand-written pipelines the reader now reads five (the monotonous event, the two spike detectors, the filtered spike detector and the filter comparison), each of which the writer writes again to the same graph. It refuses the three with a Recorder, and `fir_chain_latency_pipeline.cpp` for its `using PassThroughFilter`.
