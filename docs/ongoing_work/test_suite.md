How Falcon is tested, and the whole state of that work: what is decided, what is done and what is open. Every task on the tests is tracked here, not in the engine's files. The engine's spec is in [engine.md](engine.md); work after the prototype is in [beyond_prototype.md](beyond_prototype.md). ## Tests as whole runs
Paused, with no choice made yet between the plan below and existing tools. Its place in the order of work is not set (see the top of beyond_prototype.md). No unit tests. Each folder under `src/tests/` gets a `run.py` that builds its test pipelines, runs them and judges each run from outside: by its log lines, by a comparison with SciPy, or by a file the run wrote (e.g. a recording). `src/tests/run_tests.py` runs every folder's `run.py` as a process of its own and reports which passed.
- Agreed: Python, not bash, whose checks on numbers and log lines are fragile; the IirFilter test's comparison is Python already.
- Agreed: one Python environment for all tests, in `src/tests/` (`pyproject.toml`, `uv.lock`), not one per folder. So the lint must skip that environment's folder, and `__pycache__` must be git-ignored. Not done yet; `pyproject.toml` and `uv.lock` are still in `iir_filter/`.
- Open: existing tools instead of our own. pytest already does what `run.py`, `run_tests.py` and the shared helper would (finding tests, skipping, selecting, reporting, with the helper as a `conftest.py`); CTest, which comes with CMake, runs a test per build target and judges it by exit code or a pattern in its output. LLVM's FileCheck matches log lines against expected lines written as comments in the test's `.cpp`, but can't check a sum. Only the test pipelines, the checks and a small helper that knows Falcon (build, run, stop, find the run's directory, read its log) would be ours. Leaning to pytest, starting with the two folders that exist.
- Agreed: an extension's tests live in it, in `custom/<extension name>/tests/`, like its pipelines (see **Extensions** in engine.md), since a public test can't include a private processor.
- To design: whether `run_tests.py` also runs the tests of every extension it finds.
- To design: how a test's program gets built, since the build has one `falcon` target whose source is set by hand in `CMakeLists.txt`. Three ways, leaning to the first:
  - One CMake target per test program, with each extension declaring its own in its `CMakeLists.txt`. Nothing is edited to switch tests, the `falcon` target stays the developer's, and the lint gets each test's real compile flags. But `CMakeLists.txt` must be restructured, since every option hangs on `falcon`, and a naming rule must tell a test program from a helper file.
  - The single target, with its source passed as a CMake variable. A few lines, but every switch re-runs CMake and changes what `falcon` is.
  - The helper calling the compiler directly, as the UI will for a generated `pipeline.cpp`. No CMake change, but the flags then live in two places, and an extension's libraries must be passed by hand.
- To design: a helper the `run.py` files share (build, run, stop after some seconds, find the run's directory, read its log).
- To design: how a check deals with what differs between runs: times, the run's directory, and counts that depend on timing.
- To design: what a test needs from the machine (isolated cores, hardware, root), so a test that can't run is skipped, not failed.

## Processor tests
Was parked for after the prototype; a candidate to pull into the prototype, not confirmed yet (see **Parked too early** in the open questions of engine.md).
- The first: IirFilter against SciPy, in `src/tests/iir_filter/`. Its `README.md` describes the test, its results and what is still to test.
- Each test runs both versions of the processor, AVX512 and AVX2 (see **One processor per stream** under **Processors** in engine.md). An AVX2 build runs on any supported CPU; an AVX512 build needs an AVX512 CPU or an emulator (e.g. Intel's SDE).
- Every processor gets tests. They catch mistakes the processor interface doesn't prevent, e.g. a sample processor that never calls `set_header`, so its output is always empty and everything downstream stays silent (see **Operations a processor uses** under **Buffers** in engine.md).
- Each processor is also run with every optional connection left out, since using a missing one compiles and is undefined behaviour (see **Required and optional connections** under **Processors** in engine.md).
- The tests also matter for linting: clang-tidy analyzes a processor's code only where something instantiates its template, so a processor that no pipeline and no test instantiates is never checked.

## How we judge that the engine works
- Correct triggers: Ripple's software (Trellis) records the same session alongside Falcon. A reference script applies the same filter and threshold to that recording. At least 99% of the triggers Falcon logged must match the sample numbers it detects. Checked with an offline Python analyzer: it works well (the numbers are not recorded here).
- Latency inside Falcon: for each trigger, LatencyBenchmark (see **Trigger and outputs**) logs the time from packet arrival to the trigger decision, using the CPU's timestamp counter (TSC). The pin write itself counts outside Falcon: a PCIe I/O write, which the card acknowledges before `outb` returns, timed on its own by a loopback test (an output pin of the card wired to one of its input pins). The arrival time is read on the input core and the decision time on the processing core, so the TSC must be invariant and synchronised across cores; to be checked on the target CPU.
- Latency end to end, from a signal at the electrode to the TTL pulse leaving the PCIe card (how to measure it: see **How to measure the round trip** under **Latency measurement**). The round-trip graph: a test square wave on the headstage, the same on every channel from one voltage divider → Ripple input reading one channel → LevelCrossingDetector → PCIeParallelOutput on a DeLock PCIe parallel port card (SUNIX chip), which pulses on each crossing, so no Trigger. The input runs on a core of its own, with a 32-slot ring to the rest (see **Input processors**). Nothing runs between the input and the detector, so its round trip is the least any graph adds to. It has no LatencyBenchmark, since an oscilloscope on the square wave and the pin measures the round trip and can't pair its edges with a log's rows. A benchmark variant reads all 32 channels, puts 8 IirFilters in series before the detector, each with one pass-through section (b0 = 1, gain 1: their cost counts, the signal passes unchanged), a Trigger after it that waits for every channel, and LatencyBenchmark right before the output, for Falcon's part.

## Latency measurement
**How to measure the round trip.** What matters is the round trip a clinic gets with Falcon and the Ripple system: from a signal at the electrode to the TTL pulse leaving the PCIe card. Three ways:
1. Ripple's clock: the TTL output is wired back into a digital input of the Ripple system, which records the raw channels and the digital input, so each round trip runs from the edge in the recorded ephys data to the TTL in the recorded event data. A run counts only if the event data hold one TTL per rising edge: a missing TTL means a lost sample or a missed trigger. One independent clock, but 33 µs resolution, the digital input's own capture delay inside the result, and a function generator, a recording and an offline script for every run.
2. Falcon times both ends with the TSC: a stimulus pin of the PCIe card, attenuated, feeds a headstage channel; the round trip runs from the TSC of that pin write to the trigger decision, plus the output pin write timed once by a loopback test. Nanosecond resolution, nothing recorded, runs for hours; but both ends share the PC's clock and its PCIe writes, so a systematic error at both ends wouldn't show. Needs one new processor that toggles the stimulus pin on a schedule without blocking its core and exposes the TSC of each write.
3. An oscilloscope on the test edge and the TTL pin: independent of both systems, but manual.

In use: 3, with the round-trip graph (see **How we judge that the engine works**), which serves 1 as it is too; 2 would add the stimulus processor to it. Leaning to 2 later as the standard, repeatable test, checked against 3.
- First oscilloscope run, a 2 Hz square wave split to the scope and, through a 1000:1 attenuator Ripple supplies, to all 32 channels of the Micro2 headstage: the TTL came about 250 µs after the edge, sometimes more than 2 ms, sometimes not at all. Suspected first: Trigger waits for every one of the 32 channels, and LevelCrossingDetector compares the raw signal, offset and LFP included, with an absolute 100 µV, so a channel without the wave, or with an offset above the level, holds the trigger back until noise or drift makes it cross. Suspected second: the ring drops under **Input processors**. Since every channel carries the same wave, the round-trip graph now reads one channel and has no Trigger, which removes the first suspect.
- Second oscilloscope run, the one-channel graph: the TTL came 250 to 600 µs after the edge, spread evenly. The network card that receives Ripple's data (`atlantic` driver) batched its interrupts by default (`rx-usecs 256`, `tx-usecs 1022` in `ethtool -c`). With batching off (`ethtool -C <nic> rx-usecs 0 rx-frames 1 tx-usecs 0 tx-frames 1`), the TTL came 200 to 320 µs after the edge; any `rx-usecs` above 0 widened the spread again. Still unknown: where the remaining 120 µs of spread comes from (of it, up to 33 µs is where the edge falls between two samples). Turning off the CPU sleep states C2 and C3 (18 and 350 µs to wake) on all CPUs didn't change it. The Summit's 2 or 3 samples per datagram account for about 100 µs of it: up to two sample periods of waiting in the Summit, plus where the edge falls between two samples (see **Input: Ripple Neuromed**). Also unknown: what makes up the 200 µs floor. Candidates: the headstage's analog filters, the Summit's sampling and processing, and the path through the PC. A filter's share depends on where the level sits within the filtered step: a level just above the step's bottom is crossed as the rise starts, a level near its middle about a group delay later. If the headstage removes the wave's offset (not verified), 100 µV sits near the middle for any step well above 200 µV, so changing the amplitude barely moves it; sweeping the level would separate the filter's share from the rest. The investigation is paused here. If it resumes, the next steps are that level sweep and measuring the PC's share: from a datagram reaching the PC to the pin write.

### Latency tests for the paper
For the Falcon 2 paper. The prototype's round-trip graph (see **How we judge that the engine works**) checks the engine but measures too little for a paper.
- **The 2017 paper's test** (Ciliberti & Kloosterman, J. Neural Eng. 14 045004): a square wave into 128 channels (32 tetrodes) at 32 kHz; m parallel chains (1 to 32), one per tetrode, each of n serial stages (1 to 8): n − 1 all-pass FIR stages, then a threshold detector; an EventSync that fired once every chain had an event. Round trip measured on the acquisition system's clock, internal from packet arrival to just before the TTL, external as their difference; medians, 99% intervals and worst cases over 7 min and 1 h. Internal latency of its 32 × 8 graph: median 0.26 ms, 99% interval 0.15–0.45 ms, worst 2.64 ms.
- **Its work repeated in Falcon 2**, in the FIR chain latency pipeline: SignalGenerator alone on one core, with a phase step of 0 so every channel crosses on the same sample; on a second core, one chain on the whole stream: 7 FirFilters with one tap of 1, so each passes the signal unchanged (see **FirFilter** in engine.md), a LevelCrossingDetector, a Trigger, and LatencyBenchmark. More cores only if one can't finish each pass within the sample period.
  - One chain, not 32: Falcon 1 needed a chain per tetrode to run them in parallel (a thread each); Falcon 2 runs the tetrodes in the SIMD lanes of each processor, and per-tetrode logic belongs there too (see **One processor per stream** in engine.md). Trigger waits for every channel where EventSync waited for every tetrode; with the square wave on every channel, both fire on the same sample.
  - Rejected: splitting the stream into 32 tetrode streams. Each would be padded to 16 channels, so the stages would compute 512 lanes for 128 channels, and a split on the input's core would need 32 rings.
- **Measured**, from arrival to decision:
  - 128 channels at 32 kHz, 521 triggers (about 11 s): median 0.32 µs, 99th percentile 0.35 µs, maximum 0.63 µs. In the machine code the stages still do their work: clang, the compiler then, turned each FirFilter's multiplication by the tap of 1 into an addition of +0.0 (which keeps a −0.0 input's sign right), so each stage still widens, stores its history, adds, narrows and stores every channel vector. FirFilter's `process()` was not inlined (see **Inlining every `process()`**); LevelCrossingDetector's, Trigger's and LatencyBenchmark's were.
  - 10,000 channels at 40 kHz (a 25 µs sample period), 1120 triggers (about 24 s): median 15.74 µs, 99th percentile 16.17 µs, maximum 18.13 µs, leaving out the first trigger, at 26.68 µs, the only one with cold caches. Every trigger sample stayed within the sample period, every rising edge triggered, no ring dropped a sample, and SignalGenerator, with one `std::sin` per channel, kept the rate.
  - Where that time goes, measured at 10,000 channels by leaving parts out: without the 7 FirFilters, median 8.34 µs, so the 7 stages take about 7.4 µs (about 1 µs each). With the generator moved into the processing core's loop as well, so no sample crosses a ring, median 8.74 µs at 40 kHz: the ring hop is below the run-to-run spread. The remaining 8.5 µs is mostly LevelCrossingDetector pushing 10,000 events (400 KB) and Trigger looping over them (see **Detection events are channel masks** in engine.md), shown by spreading the channels' rising edges over S samples, so the trigger sample carries about 10,000 / S events, everything else unchanged: median 8.72 µs at S = 1 (10,000 events), 1.43 µs at S = 10 (about 1000), 0.92 µs at S = 100 (about 100) and 0.90 µs at S = 800 (about 12). So about 0.9 µs is the rest of the pass, and each event costs about 0.8 ns at 10,000 events and 0.5 ns at 1000, whose 40 KB still fits in L1.
  - With channel masks (see **Detection events are channel masks** in engine.md), the same graph with every channel crossing on the same sample: median 0.85 µs (99th percentile 1.01 µs, maximum 1.16 µs, 375 triggers) instead of 8.72 µs, below even the 0.90 µs it took with about 12 per-channel events. The whole graph, 7 FirFilters included: median 7.71 µs, 99th percentile 8.39 µs, maximum 10.07 µs leaving out the first trigger (11.97 µs, cold caches), 480 triggers, instead of 15.74 µs.
  - The same core-2-only graph at 100 Hz, where the core sleeps inside the generator nearly all the time between samples: median 16.07 µs instead of 8.74 µs. The clock dropping while idle, or deep idle emptying L1 and L2, or both (see **Machine setup** under **Agreed** in engine.md, and **Waiting for data** in engine.md); not told apart, which needs the core's clock during the run.
- **Still to do**: runs as long as the paper's (7 min and 1 h), with the realtime cores' clock checked during the run (see **Machine setup** under **Agreed** in engine.md); the round trip on the Ripple system; what the paper claims, hence what the tests vary, and whether Falcon 1 runs the same tests on the same machine.

## Detector tests
RippleDetector is designed, written and runs (see **RippleDetector** in engine.md). Still open about testing it:
- Its test pipeline and test signal. SignalGenerator's steady sine never crosses the threshold: its mean square swings between 0 and twice its mean, and the threshold lies further above the mean than that (6 × MAD is about 1.9 times the sine's squared amplitude). So the test signal is SignalGenerator's ripple bursts (see **Ripple bursts** under **Agreed**), as Falcon 1's test bench had a train of ripples. The pipeline is written (`src/pipelines/ripple_detector_pipeline.cpp`): SignalGenerator's ripple bursts, an IirFilter with the IirFilter test's Chebyshev II band-pass (150 to 250 Hz), RippleDetector with its default options and an EventLogger. First run, 20 s: the burn-in ended with a mean of 326 and a MAD of 483 (µV²), then every burst was detected, 47 ms after its start at first and 45 ms once the statistics had settled for 4 s. From the ninth burst on, each burst gave two events, the second 30.2 ms after the first, 7 samples after the 30 ms lockout ended (from the recorded events and filtered signal, plotted with `src/tests/plot_recording.py`). The filter delays the burst by about 20 ms, so it is still above the threshold, which has sunk by then, when the lockout ends; and the mean square of 4 channels a phase step apart keeps a ripple at twice the oscillation's frequency, which crosses the threshold again on its way down (Falcon 1's ripple graph used a lockout of 50 ms). The bursts are a sixth of this signal and ten times its background, so they dominate the statistics, which is why the first detections come only near a burst's peak. Open: whether the test signal gets rarer bursts and the test a longer lockout, and what the test checks.
- Its reference script (see **Judging a detector with running statistics** below).
- Seeing a signal before the viewer exists: Recorder (see **Recorder** under **Decided**), in `ripple_bursts_recording_pipeline.cpp` and in `ripple_detector_pipeline.cpp`, which records the filtered signal and the Ripple events. It works: a 20 s run of the ripple detector pipeline put 599,343 samples and 32 events into one file, none lost, and the plot from that file shows the same detections as the plot from its first form's two files. Parked: every loop stops at once when the run ends, so the last few ms a slow core hadn't yet read from its rings are not recorded (see **The end of a recording** under **Slow readers** in beyond_prototype.md).
- **Judging a detector with running statistics.** The trigger check (see **How we judge that the engine works**) compares Falcon's triggers with a reference script that runs the same rule. The papers judged their detectors against an offline detection instead, which sees the whole recording (fklab's `detect_ripples`: the Hilbert envelope of the 140–225 Hz band, smoothed over 7.5 ms, two thresholds, events at least 30 ms long), by sensitivity, false detections and the delay from the event's start. Does a ported detector's test need both?

## Tests of the UI
Tests in Python that click, drag and type in the pipeline designer with no window on the screen, so that the UI's behaviour is checked without anyone watching it (asked for and decided by the user on 17 November 2026). They check what [pipeline_designer.md](pipeline_designer.md) specifies, never how the UI looks: no test depends on a colour, a size in pixels or a widget's style. How it looks is judged from pictures (see **Guidelines** in CLAUDE.md).
- **The app plays the mouse and the keys itself** (`src/ui/ui_driver/ui_driver.cpp`). With the environment variable `FALCON_UI_DRIVER` set, Falcon draws into a window that isn't shown and, whenever it has nothing left to play, waits for a command on its standard input, one a line: `frames <count>`, `mouse_move <x> <y>`, `mouse_down <button>`, `mouse_up <button>`, `key <name>` (e.g. `Escape`, `Ctrl+A`), `text <text>`, `picture <file>`, `targets`, `state`, `quit`. It hands each to Dear ImGui as if it came from the mouse or the keyboard, one frame for each step, and answers once the frames are drawn with one line on its standard output: `FALCON_UI_DRIVER ` followed by JSON, which tells an answer from whatever else Falcon prints. The end of its input quits it, so a test that dies leaves no Falcon running.
- **A run gives the same result every time**: a frame lasts 1/60 s for Dear ImGui whatever it really took, and the real mouse can't interfere, since the backend reads it only for a window that has the focus.
- **What can be clicked has a name** (`ui_driver_targets.cpp`). While the driver is on, the designer notes where it drew each such thing in the frame, and `targets` lists the names with their rectangles: `panel/<type>`, `core/<number>`, `drop/<place>` (the drop places from the left, shown only while a drag is over a core), `block/<processor>`, `block/<processor>/handle`, `block/<processor>/remove`, `block/<processor>/option/<option>`, `port/<processor>/input/<port>`, `port/<processor>/output/<port>`, `options_panel`, `options_panel/close`, `options_panel/input/<option>`, `options_panel/default/<option>`. A name has a note where a test needs more than the place: why a port can't be clicked while another is picked, and `marked` for the drop place a drop goes to.
- **`state` hands over what the designer holds** as JSON (`src/ui/pipeline_designer/designer_state_json.cpp`): the processors with their type, core and option values, each core's list and its rows with every processor's column, the connections, the selected processor, the picked port, and the cores shown and offered. A processor is called by its name, which is unique.
- **The Python side** is in `src/tests/ui/pipeline_designer/`. `designer_driver.py` starts Falcon with a time limit, sends the steps and reads the answers, and makes a click, a drag and a typed text of those steps. `run.py` runs every function named `test_...` in the files named `test_...`, each against a Falcon of its own, and writes a picture of the window to `build/ui_test_failures/` for a test that fails. Both use Python's standard library only, so they need no environment; pytest would find the same tests (see **Tests as whole runs**).
- **To run them**: build Falcon (`sh scripts/make.sh`), then `python3 src/tests/ui/pipeline_designer/run.py`, or with part of a test's name after it to run only those. All of them take about 8 seconds. The exit code is 0 when no test failed that wasn't expected to.
- **A test that shows a defect stays, marked** with `known_failure` and its reason (`known_failures.py`), and the defect goes to the open questions of pipeline_designer.md. `run.py` reports such a test apart, and reports it too once it no longer fails, so that the mark is taken away. The designer is never changed to make a test pass.
- **What the 71 tests cover**, by file:
  - `test_adding.py`: the panel's three groups; a processor dragged from the panel sitting unconnected; a drop outside every core; the next core's box during a drag; a box for every core up to the highest in use; the drop places, the marked one, and that nothing moves during a drag; which cores are offered first.
  - `test_connecting.py`: connecting in either order and across cores; one output to several inputs; an input with slots; every way a picked port is let go; which ports can't be clicked while one is picked and what each says; removing an input's connections by a right click.
  - `test_moving_and_removing.py`: a block dragged into another core, to a chosen place there, or released outside every core; a chain moved inside its core by one of its blocks; the remove icon.
  - `test_options.py`: the option lines on a block; opening and closing the options panel; a text option; a number option, its step buttons and its default; what a number box takes; an option chosen from a list of values.
  - `test_streams.py`: the stream a processor starts, on its block and in its panel; its channel count and rate and the bounds they keep; the stream the processors after it take, and none while nothing that starts one is connected.
  - `test_layout.py`: the rows and columns of a chain, a fan-out, a reader of two with and without room, an unconnected processor, a circle, a state value's connection and a reader of another core.
  - `test_driver.py` and `test_picture.py`: the driver's own answers, and a picture written on demand.
- **What they don't cover**: what is only seen (a tooltip showing, a line's path, a colour), the cores' area scrolling sideways during a drag, the mark of a core that isn't isolated, and whatever depends on the real desktop, such as the window's title bar.
- Not chosen: a program that moves the real mouse, which needs the window on the screen, takes the mouse from the user while it runs, and needs a permission under Wayland; and Dear ImGui's own test engine, whose tests are written in C++ and whose licence has conditions.

- **What they don't cover**: whether what the writer writes compiles and runs, which isn't tried (see **The writer, its first step** in generator.md).

## Done
What exists and has run. No test of the engine has a `run.py` yet: each is judged by hand, from its log, against what its first comment says to expect.
- **How a run is made by hand**: once, with `timeout --preserve-status -s INT <seconds> ./falcon`, so it ends by the signal Ctrl+C sends and reports the program's own exit code. Without `--preserve-status` the code is `timeout`'s own, 124.
- **IirFilter against SciPy**, in `src/tests/iir_filter/` (see **Processor tests**).
- **The logging tests** in `src/tests/logger/` show these parts at work: a tour that stops cleanly (setup and teardown lines, the throttle's counts, every kind of argument, a data ring that drops samples) and one for each way a run fails (`fail()` in `process()`, `fail()` in a constructor, an exception that isn't a `std::exception`, two processors with one name). No test shows a core's message ring filling up, or a core raising more kinds than it has warning counters for.
- **The state values test**: `src/tests/state_values/state_values_closed_loop_test.cpp`, whose first comment states what is expected and what a failure looks like. `gated_detector`'s `is_in_lockout` crosses to DetectionPauser, a test processor on another core, which switches its `is_detection_enabled` off for 750 ms from the start of each lockout, across cores again. `free_detector`, with no state value connected, reads the same samples as the control. Run for 40 s, 10 s of them burn-in, and judged from its log: `free_detector` 97 events, at least one in every burst; `gated_detector` 30 events, one a second, 29,934 to 30,000 samples apart; DetectionPauser saw 30 lockouts begin and 30 end; no warning, and a clean stop. The 30 lockouts lasted 30.031828 to 30.031908 ms as timed on DetectionPauser's core, 80 ns apart, so a change of the state arrived equally late each time to within 80 ns, against a sample period of 33 µs. That shows how steady the crossing is, not how long it takes, since a constant delay cancels out. The few gaps of about 29,940 samples fall on the same events in every run, so they come from the detector's arithmetic on a signal that repeats. Not captured in any run: the program's exit code.

## Open questions
- **Moving the tests out of `src/`, to a `tests/` at the top**, asked by the user on 22 November 2026 and parked by the user that day, not decided. Claude's answer: for it, `src/` would then hold only what a pipeline includes and what a release ships; against it, a wide mechanical change, to the lint's and the formatter's scripts, `CMakeLists.txt`, the tests' includes, the paths in the Python drivers, the docs and CLAUDE.md, which says that what tests the UI goes to `src/tests/ui/`.
- **Where the tests of the UI stand in the plan of whole runs**: they have their own `run.py`, as that plan gives each folder, but no `run_tests.py` runs it, and the choice between that plan and pytest is still open (see **Tests as whole runs**).
**A state across cores in a test.** A change of such a state isn't seen on the same sample in every run (see **Across cores a reader gets the latest value, without waiting** under **Buffers** in engine.md), so a test can't expect its effect on an exact sample. Open: whether such a test accepts a range of samples, or keeps the state's producer and reader on one core. The first such test, `src/tests/state_values/state_values_closed_loop_test.cpp`, needs neither: it is judged by its Ripple events coming a second apart, where a few samples either way don't show. It has no `run.py` yet: its first comment states the limits, and its log is checked against them by hand.

**The FIR chain's latency.** From the runs after the engine's split (see **Done**). 10,000 channels at 40 kHz gave a median of 9.37 µs (99th percentile 10.31, maximum 13.41) where **Latency tests for the paper** records 7.71 µs (8.39, 10.07) for the same graph. One 10 s run doesn't say whether that is the conditions of the run or a change in the code; of the day's changes only the 128 bytes between cores (see **Per-core loop**) lie on that graph's path. To tell them apart: the same pipeline built with 64 bytes and with 128, run one after the other.
- **GCC against clang**, on 18 November 2026, when GCC became the compiler (see **The compiler is GCC** under **Boundaries** in engine.md): the same source built with each under the build's flags and run one after the other, GCC first, 25 s and 1173 triggers each, at 10,000 channels and 40 kHz. GCC 16.2: median 6.68 µs, 99th percentile 6.96, maximum 9.88, leaving out the first trigger, at 11.36. Clang 23: median 9.25 µs, 99th percentile 9.98, maximum 10.30, its first trigger at 9.99. Both stopped cleanly, with no warning and no dropped sample, and every trigger within the sample period. A second pair right after, clang first: clang median 9.33 µs, 99th percentile 10.14, maximum 10.55, its first trigger at 12.66; GCC median 6.73 µs, 99th percentile 6.98, maximum 7.07, its first trigger at 7.37. So the order doesn't matter, a compiler's two runs lie within 0.1 µs of each other at the median, and GCC's median is about 2.6 µs, a good quarter, below clang's on this graph. One graph on one day. The two builds differ in more than the compiler: GCC's had its C++ library's run-time checks on, where clang's library has none of them (see **Hardening** in beyond_prototype.md), and GCC fused plain arithmetic more freely, by its default, which the build has since overridden (see **Arithmetic across processors** there). Measured again with that flag, one pair the same day, GCC first: GCC median 6.61 µs, 99th percentile 6.85, maximum 9.75, its first trigger at 11.25; clang median 9.46 µs, 99th percentile 10.36, maximum 11.16, its first trigger at 9.51. So the flag cost GCC nothing here. Why GCC's is faster is not looked at.

**Sanitizer builds.** Deferred with the rest of **Hardening** in beyond_prototype.md: for testing only, never the realtime build: ASan + UBSan (memory errors and undefined behaviour, including misaligned SIMD loads and signed overflow), and TSan (data races between cores, e.g. in rings).
