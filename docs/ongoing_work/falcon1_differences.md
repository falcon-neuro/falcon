# Differences from Falcon 1

Where the new engine departs from Falcon 1 (the old `falcon/` engine, its extensions and its Dart UI). Anything not listed works as in Falcon 1, or will: the new engine must do everything Falcon 1 could. Falcon 1 was used only by its authors, so no user habits or existing graphs constrain the new engine. Each entry says what Falcon 1 did and what replaces it, and points to the section that decides it and gives the reasons. A new decision in [engine.md](engine.md) or [beyond_prototype.md](beyond_prototype.md) that departs from Falcon 1 gets an entry here too.

## Different for good
Decided; Falcon 1's way is not coming back.

- **Graph definition**: Falcon 1 built the graph at run time from a YAML file (processors with their options, connection rules, linked states), and checked the options while building it. Now the UI generates `pipeline.cpp` and compiles it into the engine program, so every option is a compile-time constant and changing one means compiling and spawning a new program (**Boundaries**, and **Every option is a compile-time constant** under **Processors**, in engine.md; generator.md).
- **Threads**: Falcon 1 ran each processor in its own OS thread, optionally pinned to a core and given a realtime priority (its `thread_core` and `threadpriority` options), and each processor's `Process()` ran its own `while` loop; a phase such as RippleDetector's burn-in was a loop of its own. Now each core runs one pinned thread that calls each of its processors once per pass; `process()` never loops or waits, and a phase is state inside the processor (**Per-core loop**, and **`process()` never loops and never waits** and **All logic lives inside the processor** under **Processors**, in engine.md).
- **Processor lifecycle**: Falcon 1 processors derived from `IProcessor` and overrode a virtual method per stage: `Configure`, `CreatePorts`, `Prepare` and `Unprepare` (graph build and destroy), `Preprocess` and `Postprocess` (each run's start and end), and `Process`. Now a processor is a struct with an `Options` template parameter, a constructor, a destructor and `process()`, with no virtual functions (**A processor is a struct with an `Options` struct** under **Processors** in engine.md).
- **Processor granularity**: Falcon 1 graphs had one processor per channel or tetrode, hundreds in all (one YAML entry such as `tetrode(1-16)` expanded into many). Now one processor handles a whole stream with hand-written SIMD, and per-group settings are arrays inside it (**One processor per stream** under **Processors** in engine.md).
- **Samples per call**: Falcon 1 processors handled packets of several samples and could take several packets in one call (`RetrieveDataN`, `RetrieveDataAll`). Now each `process()` call handles at most one sample (**One sample per pass** in engine.md).
- **Data between processors**: Falcon 1 gave every output its own disruptor ring buffer of preallocated `TimeSeriesType` packets (256 slots by default, set per output with the `buffer_sizes` option), read by every input connected to it. Now there is one generic stream type in float32 µV, plain buffers within a core, and a ring, as small as possible, with one writer and one reader only where a connection crosses cores (**Goal**, **Buffers**, **Rings** and **Sample type** in engine.md).
- **Full rings**: in Falcon 1, a writer whose ring was full waited for its slowest reader, so a slow processor stalled everything upstream of it; a reader warned when its backlog passed 85% of the ring. Now the writer never waits: a sample that doesn't fit is dropped and counted, and the run goes on (**A full data ring is a failure, but the run goes on** under **Rings** in engine.md). The UI showing ring fill levels is planned (**Ring fill levels** under **UI** in beyond_prototype.md).
- **Waiting for data**: Falcon 1 let each output choose how its readers wait: blocking (the default), sleeping, yielding or busy spinning (`falcon/portpolicy.hpp`). Now realtime cores spin and non-realtime cores may block (**Waiting for data** in engine.md).
- **Data types**: Falcon 1's data types were a class hierarchy with virtual functions, and each stream's parameters and rate were set when the graph was built, with each input checking the parameters against what it accepted. Now a stream's facts form a compile-time `StreamInfo` type, so a mismatch is a compile error (**Stream type** under **Processors** in engine.md).
- **Sample numbering**: Falcon 1 numbered packets in the order each output produced them, so a packet lost before the input didn't show. Now the input derives each sample's number from the device's clock, so a lost sample shows up as a gap (**Each sample has a header** under **Buffers** in engine.md).
- **Serialization**: Falcon 1's data types each had hand-written serialization code (binary, YAML and FlatBuffers), used to save and stream data. Now there is no serialization code: whatever saves or shows events reads their fields through reflection (**No serialization code** under **Events** in engine.md).
- **Shared states**: Falcon 1 linked states across processors in the YAML's `states` section: atomic values that several processors could read and write, each with read/write permissions for its owner, the other processors and clients. Now a state value is a connection with one producer and is a plain value within a core (**State values** under **Buffers** in engine.md); across cores it is one atomic value, of which each reader copies the latest right before its call (**Across cores a reader gets the latest value, without waiting**, in the same place). Client access is under **Runtime control** below.
- **Errors during a run**: in Falcon 1, an exception in any stage of any processor, `Process` included, ended the run with an error. Now errors are expected only in constructors, and then the graph doesn't start. A `process()` that can't go on calls `fail()`, a cold helper that throws, so its `process()` stays small enough to inline; the run then ends, as in Falcon 1 (**An error is an exception** under **Processors** in engine.md).
- **Logging from processors**: Falcon 1 processors logged text from their own threads (g3log). Now a processor calls `warn()` or `log()` with a format string and plain values; in the loop, a cold call copies the values into its core's ring, throttled per kind, and the main thread formats the line and hands it to one central logger. Whatever must be kept for each occurrence is an event (**Logging** in engine.md). Where the logger writes is under **Log destinations** below.
- **Resource paths**: Falcon 1 resolved paths in options through prefixes (`resources://`, `filters://`, `graphs://`, `run://`, `test://`) pointing to folders on the machine. Now a file option is a plain path, and the experiment file holds a copy of every resource it uses (**A file option is only its path** under **Processors** in engine.md, **Experiment files** in beyond_prototype.md).
- **Extensions**: Falcon 1 compiled every extension listed in the build into the `falcon` program and registered each processor in one global list by its class name. Now an extension lives in `src/processors/custom/<extension name>/` and its folder name is its C++ namespace (**Extensions** in engine.md).
- **Event kinds**: Falcon 1's events were one data type carrying a name, and processors picked theirs by name (e.g. a `target event` option). Now each kind of event is its own type, so connecting the wrong kind is a compile error (**One type per kind of event** under **Events** in engine.md).
- **Deciding on an output**: Falcon 1 combined events in EventSync (a target event on every input) and EventFilter (how many inputs within a sync time, and blocking events that veto for a while), and its DigitalOutput mapped named events to actions on digital lines and timed the pulses itself. Now a Trigger processor makes the decision and emits trigger events, and the output processor times the pulse: PCIeParallelOutput, as Falcon 1's did, but checking the time on every pass instead of waiting out each pulse, so events during a pulse are ignored instead of queued into back-to-back pulses (**Trigger and outputs** in engine.md).
- **Spike threshold**: Falcon 1's spike detection took a positive threshold plus an "invert signal" option. Now the threshold's sign gives the direction (**The prototype's SpikeDetector** under **Events** in engine.md).
- **Filter kinds**: Falcon 1 had one filter processor, MultiChannelFilter. Its only option was a coefficients file whose header named the filter's kind (`# type = biquad`, `fir` or `slope`), and a virtual filter class picked the implementation at run time. Now each kind is its own processor and its own UI node: `IirFilter`, `FirFilter` and `SlopeFilter` (**FIR filter** in beyond_prototype.md).
- **Filter arithmetic**: Falcon 1 filtered in double, in Direct Form II. Now still in double, in Transposed Direct Form II, while samples between processors are float32 (**IirFilter** in engine.md).
- **Filter design rate**: Falcon 1's coefficient files stated their sampling rate only in free text, so a file designed for another rate ran without an error. Now a coefficients file states it in a machine-readable header line, checked against the stream's rate at compile time (**IirFilter** in engine.md).
- **Open Ephys input**: Falcon 1's OpenEphysZMQ took data from the Open Ephys GUI over ZeroMQ. Not ported: that stream is too slow for high-density realtime processing, and Falcon replaces Open Ephys rather than reading from it.
- **Temporary processors**: SignalPlotter and WebsocketSink, late additions to Falcon 1 for viewing a stream, are not ported (**Live viewer** under **UI** in beyond_prototype.md).
- **RunningStats**: Falcon 1's RunningStats output the running mean and MAD of a stream's first channel as a two-channel stream on every sample: the statistics the detectors keep inside, with an optional outlier protection that the detectors left off. No example graph or paper used it, and no commit since the first public one of 2017 states its purpose. Not ported: the detectors' own optional outputs will expose their statistics (**RippleDetector's design** in the open questions of engine.md).
- **Ports with slots**: a Falcon 1 processor had named ports, and a port had slots, so one port took a variable number of connections, chosen when the graph was written, and a port could accept any data type. FileSerializer, ZMQSerializer and LatencyBenchmark each had one `data` port for any type with 1 to 256 slots; Rebuffer had 0 to 256 slots on its input and on its output; MUAEstimator took 1 to 64 SpikeDetectors on one port. The range of slots was each port's own, set by the processor's author, and exactly one unless stated; the slot number was 16 bits wide, so 64 and 256 were the authors' round numbers, on ports whose connections grew with the number of tetrodes, each tetrode having its own processors. An output slot owned a ring, and an input slot was one more ring that the processor's thread waited on. How many inputs read one output slot was never limited, and any of them could stall its writer (**Full rings** above). Now a port's slots are fixed when `pipeline.cpp` is compiled: the processor is a template over the kinds of its connections, one instance sees them all, each with its own type, and their number has no limit (**A port with slots** under **Processors** in engine.md). An output is read by any number of consumers on any core, and none of them can hold up its writer (**A buffer that feeds rings** under **Rings** in engine.md).
- **UI**: Falcon 1's UI is written in Dart. The new one is written in Dear ImGui and reads processors and their options from a list a script makes from their source (see **The processors are read from their source by a script** in generator.md).

## Not yet in the new engine
Falcon 1 could do these; the prototype can't. Each entry gives its status: planned, deferred, open, or not discussed yet.

- **Engine between runs** (deferred): Falcon 1 was a server that stayed alive. Clients (keyboard, command line, a ZeroMQ socket) sent commands to build, start, stop and destroy graphs, and a built graph could run several times. Now each run is one engine program, spawned by the UI and stopped by a signal (**Start, stop and config** in engine.md); a program that stays alive between runs is **Engine states** in beyond_prototype.md.
- **Runtime control** (open): Falcon 1 clients could, during a run, read and write processor states their permissions allowed (`update`, `retrieve`), call methods a processor exposed (`apply`), and export the running graph with its state values (`yaml`). Now no client can change anything during a run, since every option is a compile-time constant (**Runtime control** in beyond_prototype.md). The published experiments relied on it: in the 2017 paper the burst threshold's multiplier was raised from 4 to 8 and back during a recording, while a client plotted the detector's mean, deviation and threshold to guide the choice; and the detectors' threshold, lockout and smoothing time, the MUA bin size and the stimulation mode (see **Processors to port**) were all states a client could write.
- **Run folders** (not discussed yet): Falcon 1 created a folder for every run (run group, then run name or start time, then one folder per processor), into which processors wrote their output files, kept a `_last_run` link to the newest one, and could hand a processor a previous run's folder as a template. How the new engine records is not designed yet (**Experiment files** and **Slow readers** in beyond_prototype.md).
- **Test mode** (open): Falcon 1 had a test flag, set per run or per processor, under which processors ran extra steps (`TestPrepare`, `TestFinalize`) and saved test data, such as source timestamps for latency tests, into a test folder. Separately, a processor could record its own timing (cycles spent waiting and working) to a file. The prototype logs each trigger's latency (**How we judge that the engine works** in test_suite.md); measuring every processor's timing is open (**Runtime performance measurement** in beyond_prototype.md).
- **Log destinations**: Falcon 1 logged to a file, to the screen and to a ZeroMQ socket that clients such as the UI subscribed to, with debug messages behind a flag. Now one central logger writes every line to the console and a log file, with no debug level (**The central logger** under **Logging** in engine.md); a feed to the UI is not discussed yet.
- **Realtime thread setup** (not discussed yet): Falcon 1 locked all its memory in RAM (`mlockall`), gave processor threads the `SCHED_FIFO` realtime priority, and could log a processor thread's involuntary context switches. engine.md covers core isolation only (**Machine setup** under **Agreed**).
- **A processor ending the run** (not discussed yet): a Falcon 1 processor could end the run itself (`Terminate()`), and a run also ended once every processor's `Process()` had returned. Now only the stop signal ends a run (**Start, stop and config** in engine.md).
- **Option units and checks** (not discussed yet): Falcon 1 options carried units (e.g. Hz, ms, samples) and checks (e.g. positive, within a range), applied when the graph was built. Now an option is a plain value; only some processors check their own at compile time (e.g. **IirFilter** in engine.md).
- **Option descriptions and processor documentation** (decided, and written for today's processors): Falcon 1 gave every option a description and every processor a `doc.yaml`, which clients fetched with the `documentation` command. Now every option, every connection and every processor has a doc comment in its source, which the UI shows as its description and the API website prints (**Every option has a doc comment, written for the user** in generator.md). A command that fetches them has no counterpart.
- **Extension tools** (not discussed yet): a Falcon 1 extension could bring its own libraries and tools, built by its own `CMakeLists.txt`. Libraries still come through the extension's own `CMakeLists.txt` (**Extensions** in engine.md); tools have no place yet.
- **Decimator** (deferred until a graph needs one): Falcon 1 had a Decimator processor, whose anti-aliasing was one second-order Butterworth low-pass at the new rate's Nyquist frequency: only 3 dB down there, so frequencies just above it fold back at almost full strength. Its filter files include ripple filters designed for 2 and 4 kHz next to an anti-aliasing filter for 32 kHz. It was a temporary processor and is not ported: the new engine has no decimator until a graph needs one, and designs it anew then (**Decimator** in beyond_prototype.md).
- **Slope filters** (planned): besides biquad cascades and FIR filters given as taps (e.g. Neuralynx's 32-tap spike filter, the one Neuralynx's own acquisition uses; now FirFilter, **FirFilter** in engine.md), Falcon 1 ran slope filters: Savitzky–Golay derivatives built from a window size, a polynomial order and a derivative order (**FIR filter** in beyond_prototype.md).

## Processors to port
Falcon 1's processors that the new engine lacks. When each is ported follows the order of work at the top of beyond_prototype.md. None is designed yet: each entry says only what Falcon 1 did, with Falcon 1's default values. An entry's status is in brackets; an entry without one is not discussed yet. Read from `falcon-fklab-extensions`, `falcon_behavior_processors`, the fklab Python packages (`fklab-python-core`, and the `dataanalysispython` fork, which holds the decoding libraries) and the two papers: Ciliberti & Kloosterman 2017 (J. Neural Eng. 14 045004) and Ciliberti, Michon & Kloosterman 2018 (eLife 7:e36275). The open points from this reading are under **Porting Falcon 1's processors** in the open questions of engine.md.

- **RippleDetector** (to port): takes a stream already filtered to the ripple band, up to 256 channels, and reduces each sample to one value: the mean over channels of the squared values (the default; not smoothed, for speed, at the price of false detections from single outliers) or the plain mean. It keeps that value's mean and mean absolute deviation (MAD) as exponential moving averages over a smoothing time (10 s), updating the mean first and the MAD from the new mean, and emits a ripple event when the value's distance from the mean rises above a multiple of the MAD (6; 12 to 14 in its example graph). The first smoothing time only fills the statistics (burn-in). During a lockout after each detection (30 ms), and while its `detection enabled` state is false, samples are neither tested nor added to the statistics. A second output streams the value, the threshold and the MAD to a viewer. From its source: during burn-in, sample n weighs alpha + (1 − alpha) ÷ n, so the statistics start as plain averages; a detection needs the previous tested distance at or below the threshold and the current one above; the detected sample is still added to the statistics; the distance is absolute, so a value far below the mean is detected too, in BurstDetector as well and since the oldest version at hand (2020), where the 2017 paper states the rule as signal − µ > factor × mad; the threshold, the mean and the MAD were states a client could read; and its `ripple` state was never set true. The 2017 paper reports ripples detected 30 ms after their start on average, with 80% sensitivity.
- **MUAEstimator and BurstDetector** (BurstDetector to port; MUAEstimator, its only input, not discussed yet): MUAEstimator adds up the spikes of up to 64 tetrodes' SpikeDetectors in each bin (10 ms) and outputs their rate in Hz, the multi-unit activity (MUA). BurstDetector applies RippleDetector's statistics, threshold and lockout to it, one value per bin. In the 2017 paper it detected population bursts a median 40.5 ms after their start, of which 0.37 ms came after the last sample the detection needed.
- **Spike amplitudes**: Falcon 1's SpikeDetector ran on one tetrode (up to 8 channels). After any channel crossed the threshold (60 µV on the inverted signal), it searched every channel for its next peak for up to 8 samples, detecting nothing new meanwhile, then emitted one spike: the crossing's timestamp and each channel's peak amplitude, which are the marks the decoder reads. A channel without a peak got its value from the sample before the crossing, though the code's comment says the crossing's. The new SpikeDetector only reports which channels crossed (**Richer spike events** in beyond_prototype.md).
- **Event logic** (not now): no Falcon 1 processor that combines, delays or converts events is ported for now: EventDelayed and EventFilter (the next two entries), Event2State and EventConverter (**Small processors**). Trigger alone decides (**Trigger and outputs** in engine.md). Processors from which the user builds complex logic by drag and drop are a design area of their own, to enter with care; one such as an event delayer may come later (**Trigger rules** in beyond_prototype.md).
- **Stimulation trigger** (EventDelayed): turned each detection into a stimulation in one of three modes, switched during a run: on time; delayed by a random time drawn from a range (150 to 250 ms), the control condition of ripple-disruption experiments; or not at all (detection only). A lockout after each stimulation limited the stimulation rate (250 ms in the ripple graph). For a period after each stimulation (50 ms, from one or more start times, e.g. the start and the end of a light pulse) it held RippleDetector's `detection enabled` false, so the stimulation's artifact was neither detected nor added to the statistics. It timed all of these on a clock, where Trigger counts samples (**Trigger only decides** under **Trigger and outputs** in engine.md).
- **Veto by a second detector** (EventFilter): the ripple graph ran a second RippleDetector on a cortical channel, where no ripples occur, so a detection there marks an artifact (chewing, bumping). EventFilter dropped a hippocampal detection that came within a block duration (40 ms) after a cortical one, and held every other detection back for a wait time (4 ms) in case the cortical one came second, which adds that time to every trigger (**Trigger rules** in beyond_prototype.md).
- **Neuralynx input** (NlxReader, to port; its two-processor variant not discussed yet): read the Digilynx's raw UDP stream, one datagram per sample at 32 kHz: a 64-bit timestamp in µs, the 32 digital input bits of the device's parallel port, one 32-bit value per channel (128 by default) and a checksum. It converted the values to µV, counted invalid, duplicated, out-of-order and missed datagrams, could hold the stream back until a digital input bit was set, and split the channels into one stream per tetrode by a channel map. A two-processor variant (NlxPureReader, NlxParser) also output the digital input bits as a stream, and could put copies of the last samples in the place of lost datagrams, where the new engine counts lost samples (**No lost packets** under **Principles** in engine.md).
- **Other inputs**: test sources that play arrays from files.
- **Position tracking**: VideoTrackReader read Neuralynx's video tracker records (x, y and head angle, 25 per second), and BehaviorReader turned them into a position along the maze and a speed (shape 5 in graph_shapes.md).
- **Decoding**, the main use case, as the 2018 paper ran it on 14 tetrodes at 32 kHz. Per tetrode: a 600–6000 Hz Bessel filter, SpikeDetector (60 µV), and a likelihood processor that evaluates, for each spike, the encoding model at the spike's four amplitudes on every position of a grid along the maze (2.15 cm apart). A population decoder multiplies the tetrodes' likelihoods into a probability for each position every 10 ms. A classifier fires when, over the last three bins, the MUA and the sharpness of that probability (its share within about 14 cm of its peak) exceed thresholds and all three peaks lie on the same maze arm; the output then locks out for 75 ms. The encoding model is a compressed kernel density: a Gaussian mixture with one component per training spike, in which components closer than a compression threshold are merged. It was built offline from the first run's spikes and positions and loaded during a pause of 5 to 15 min. Decoding took under 1 ms per spike and added a median 1.1 ms to a detection that comes about 50 ms after a burst's start.
  - These processors' source is not at hand. The model's arithmetic is in fklab's `gmmcompression` library. `falcon_behavior_processors` holds processors that build the model while the graph runs (Encoder, OccupancyEstimator) and estimate the position from the decoder's output (BehaviorEstimator), without the libraries they need.
- **Recording and streaming** (recording: Recorder, in a format of its own, see **Recorder** in engine.md; streaming: not discussed yet): FileSerializer wrote any stream to disk, as binary or YAML, and could drop packets progressively when the disk fell behind (off by default). ZMQSerializer sent any stream to client programs such as viewers (**Slow readers** in beyond_prototype.md, **Live viewer** under **UI** there).
- **Other outputs**: DigitalOutput drove an Advantech USB digital I/O module, the output of both papers. SerialOutput sent each event's name over a serial port, e.g. to an Arduino, about 1 ms slower (2017 paper).
- **Small processors**: Rebuffer (keeps one sample in N, with no anti-aliasing filter), Distributor (splits a stream's channels into several streams by a channel map; **Channel selection** in beyond_prototype.md), Event2State (a chosen event sets a bool state value, any other event clears it) and EventConverter (renames an event).
- **Test bench**: the `nlxtestbench` tool sent a recorded Neuralynx file, or a generated sine, square wave, noise or train of ripples, as the Digilynx's own UDP datagrams, so a whole graph, input included, ran without the hardware. SignalGenerator has no file playback (**SignalGenerator for testing without the Ripple system** under **Agreed** in engine.md).

## Not yet compared
The Dart UI (`falcon_gui/`: graph editor, live view, log panel, starting and stopping the engine) and the layout of the files Falcon 1's recordings held.
