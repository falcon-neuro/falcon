# Prototype spec

The new Falcon engine is in `src/core`. A processor includes one file, `engine.cpp`, which includes the engine's five parts, each building on the one before: `samples.cpp` (the instruction set, stream types and sample buffers), `events.cpp` (events, event buffers and channel masks), `connections.cpp` (state values, `In` and `Out`), `rings.cpp` (passes, rings and `next_pass()`) and `run.cpp` (a run's cores, names, directory, reporting, start and stop). They build on `logger.cpp` (see **Logging**), and all on `common.cpp` (processor names, clocks and the flag that keeps the loops running). Beside them stands `event_fields.cpp` (an event's fields as a list, see **Events**). It replaces the old `falcon/` engine (disruptor ring buffer, heap-allocated `TimeSeriesType` packets).

This file is the minimum spec for the prototype. Later work is in [beyond_prototype.md](beyond_prototype.md). The graph shapes the engine must support are in [graph_shapes.md](graph_shapes.md). The fundamental words these docs use are defined in [glossary.md](glossary.md). How Falcon is tested is in [test_suite.md](test_suite.md).

## Goal
One generic multichannel stream type. Every input processor produces it; every other processor and the UI viewer consume it. Hardware-specific structures (e.g. Neuropixels' `electrodePacket`) exist only inside their input processor.

## Priorities
These two guide every design decision, from the sample format to the graph as a whole:
- **Scientific accuracy**: every value a processor receives or outputs is the correct physical quantity (e.g. µV). No precision loss, overflow or rounding may change a detection or a trigger without an error message. So floating-point arithmetic keeps the order it is written in: no `-ffast-math` or other flag that lets the compiler reassociate it, not even for processors that opt in (see **Arithmetic across processors** in beyond_prototype.md).
- **Embedded-systems approach**: the data the hot loop touches stays in the caches of the core that uses it (see **Principles**), and values stay in CPU registers from one processing step to the next instead of being written to memory and read back (see **Vector chains** in beyond_prototype.md).

## Principles
- **Everything fits in cache.** All rings and all processor state on a core must fit in that core's cache.
  - Hot data is what is touched for every sample: rings, and processor state such as filter coefficients and history. It is sized against L1/L2 per core and the shared L3.
  - Cold data, such as stream metadata, is decided on compile time. Processors can have the few values they need into their own compact state (e.g. an input's 384 µV-per-bit scales, 1.5 KB).
  - Channels are padded to a multiple of 16, one AVX512 vector of float32, so a sample fills whole 64 B cache lines and SIMD loops have no leftover channels.
  - Ring bytes = samples × padded channels × bytes per sample. One float32 sample is 256 B (4 cache lines) at 64 channels and 1.5 KB at 384 channels (NP1). A 64-sample ring at 384 channels is 48 KB as int16 and 96 KB as float32.
- **Every sample as soon as possible**: one sample per pass (see **One sample per pass**), and the smallest rings everywhere.
- **No lost packets.** Rings start as small as possible. If packets get lost, the user makes them bigger: a bigger ring survives a short stall (see **Rings**). A graph too slow to keep up is spread over more cores (see **Heavy processors** in beyond_prototype.md). A lost sample means the setup is failing, and the user fixes the setup. Processors learn of a loss from each sample's lost-sample count (see **Each sample has a header** under **Buffers**), and IirFilter restarts after one (see **IirFilter**).
- **Deterministic replay**: replaying a recording should give about the same triggers as the live run; 99% matching is enough. For the same input, most processors give exactly the same output anyway, so no extra effort goes into making replays exactly identical (see **Exact replay** in beyond_prototype.md).
- **Low channel count first** Design and optimise for ~32-64 channels now. +2000 channels come in the future (see **Scaling to +2000 channels** in beyond_prototype.md).

## Prototype plan
Goal: a first engine that runs a real graph end to end. The basics are defined, and later optimisations stay possible.

### Agreed
- **No generator.** We write `pipeline.cpp` by hand to test the engine. In the product, users never write it: the UI generates it from the processor nodes they drag and drop (see generator.md).
- **Input: Ripple Neuromed, 32 channels**, read through Ripple's C library (`xl_cont_raw` in xipplib). Its documentation confirms: the raw stream is 30 kHz (a compile-time constant in `pipeline.cpp`, see **Rates**), electrode data is float in µV, each call returns as many points as requested plus one 32-bit timestamp for the first point. There is no separate sample number: the timestamp counts 30 kHz ticks, one per sample, so the input widens it to 64 bits (32 bits wrap after about 40 hours) and uses it as the sample number (see **Buffers**). The library runs a thread of its own to receive the packets, kept off the realtime cores (see **Start barrier** under **Per-core loop**). The Summit sends the raw stream as UDP broadcasts of 2 or 3 samples each, about 85 µs apart, so a sample can wait up to two sample periods in the Summit before it leaves. Measured with tcpdump: datagrams alternate between 228 and 152 bytes, about 11,700 a second; counted as 3 and 2 samples, that gives 29,990 samples a second. Still to verify:
  - how soon a point is available through the library after its datagram arrives (see **One sample per pass**);
  - whether a Trellis or Summit setting makes it send each sample on its own, which would remove that wait.
- **SignalGenerator for testing without the Ripple system**: an input processor that stands in for it, giving a sine wave, a square wave, a train of spike-shaped pulses (a sharp trough of the given depth and a smaller rebound, within 2 ms) or bursts of a ripple-band oscillation (see **Ripple bursts** below) in µV on every channel at the stream's rate, optionally on top of a slow LFP sine, so a filter's effect on spikes and LFP can be seen. It runs alone on its core, like any input, so it may block that core's thread: it sleeps until shortly before each sample is due, then busy-spins to the exact time, on a fixed schedule from its first pass. Sleeping alone wakes too late for a 33 µs period, and spinning alone keeps the core at 100%. The spin adapts to how late the sleeps wake: it lasts a minimum (10 µs by default) plus the worst recent wake-up delay, which jumps up at once after a late wake-up and halves every second. So after a late wake-up it sleeps less for a while, and it stops sleeping altogether while wake-ups take a whole period. Its constructor sets its thread's timer slack to 1 ns, since Linux otherwise lets a normal thread's sleep end up to 50 µs late. Its device timestamp counts samples, as Ripple's does. It stamps a sample's arrival time only once all its channels are computed, as a hardware sample arrives only once its packet is complete, so the latency log counts none of the generation. No file playback.
  - **Ripple bursts**, the test signal for RippleDetector: an oscillation at the ripple frequency (180 Hz by default) that never stops, whose amplitude swells as a raised cosine from a background level (10 µV) to the burst's peak and back within each burst (80 ms), so a burst starts and ends smoothly and at a known sample. A burst comes on every channel at once, as a ripple does; the per-channel phase step shifts only the oscillation inside it. The background is there because RippleDetector's threshold follows the signal between ripples: with silence between bursts, only the bursts themselves would set it.
- **Graph**: the Ripple input alone on its own core (see **Input processors**), a ring to one processing core that runs IirFilter → SpikeDetector → TTL output, and the start/stop signal. This is shape 1 (chain) of graph_shapes.md. The processor interface must not rule out any other shape.
- **Machine setup** by hand: one core handles the OS and interrupts and all other cores are isolated for Falcon. Falcon runs on any number of cores, even one, but the advice for low latency is at least 4: two realtime cores, one for the input and one for the rest of the graph, and two non-realtime ones, one for Falcon's UI and one for the rest of the OS. Also by hand: interrupt batching is turned off on the network card that receives Ripple's data (when built, an input that receives over the network reports for every network card whether its receive interrupts are batched, as a warning if they are, since it can't tell which card receives the data; `src/core/misc.cpp`); the UDP receive buffer limit is raised so a short stall doesn't drop packets in the kernel. Automating these is tasks A.1, A.4 and A.5 in beyond_prototype.md.
  - The boot CPU (CPU 0) never runs a realtime loop: even when isolated, the kernel removes it from `nohz_full` and keeps its tick for timekeeping, so it takes a timer interrupt every 1 to 4 ms (the kernel's tick rate). Isolated, it still keeps OS processes off the cores that share Falcon's L3.
  - A network card has receive queues, often one per CPU, isolated ones included, and a packet interrupts the CPU of the queue the card's hashing (RSS) picks for it. The hash covers the sender's port, which a sender may pick anew at each start, so any queue can get the acquisition data. So every queue's interrupt must run on OS cores: interrupts a driver sets itself can be moved through `/proc/irq/<n>/smp_affinity_list`; interrupts the kernel manages can't be moved off isolated cores, and then RSS must send packets only to queues of OS cores. Measured on the card that receives Ripple's data (`atlantic` driver): one queue per isolated core, each queue's interrupt set by the driver to that core alone, despite `irqaffinity=` (and a single-core set leaves `managed_irq` nothing to move to). All of the Summit's datagrams went to the queue on the round-trip graph's processing core. Writing `8-15` (the OS cores) to each queue's `smp_affinity_list` worked: the kernel put each interrupt on one OS core, and the Summit's now runs there. Moving it back and forth between the processing core and the OS cores made no difference the oscilloscope could show, in a graph whose processing core does almost nothing; in a heavier graph, each interrupt delays the pass it hits. It doesn't survive a reboot (automating it is task A.7 in beyond_prototype.md).
  - The realtime cores' clock must stay at its maximum while a graph runs. An idle isolated core drops to its lowest clock (600 MHz on a CPU that boosts to 5.7 GHz), where a pass takes about 9 times longer, and changing the clock mid-run stalls the core. On a `nohz_full` core, with no tick, a governor that adjusts the clock at the scheduler's updates may raise it late (to verify while a graph runs). Measured with a core that slept between samples: the same work took about twice as long (see **Latency tests for the paper** in test_suite.md). The latency log stays correct at any clock, since the TSC ticks at a constant rate; only the work gets slower.
- **No live viewer.** The path for the viewer's data from the engine process to the UI process is not needed yet (see **Live viewer** in beyond_prototype.md).
- **How we judge that it works**: see **How we judge that the engine works** in test_suite.md.
- **How to prioritise**: decide now what is expensive to change later, and build the simplest version of everything else.
  - Expensive: what processor code sees, i.e. the `process()` signature, the buffer type and the sample type. Every processor depends on it, including the ones labs write in their own extensions.
  - Cheap: what only the engine sees, i.e. rings, threads, buffer assignment and the waiting strategy. These can be optimised later without touching any processor, as long as processors only ever see buffers, never rings.
  - Outside the loop: anything that runs outside the per-core loops (setup, teardown, failure handling) costs no latency, so it gets the simplest solution that works, never an elaborate one.

## Decided

### Boundaries
- **UI and engine are separate programs.** In the product, the user designs the graph in the UI, the generator writes `pipeline.cpp`, the compiler turns it into the engine program, and the UI spawns that program (see generator.md). Compilation time is not a concern (takes seconds with a build cache on a 9950X); runtime performance is.
- **The compiler is GCC, one exact version** (decided by the user on 18 November 2026; clang until then), for its C++26 reflection, which clang lacks. Falcon relies on reflection (see **An event's fields as a list** under **Events**), on `template for` (see **A port with slots** under **Processors**), and on what puts `Options` in a template argument: floating-point values, designated initializers and braces there (see **Processors**). A compiler implements the standard feature by feature, so `-std=c++26` alone doesn't guarantee these: each was checked on GCC 16.2, the version in use. It is fetched and not installed, and a release carries it (see release.md).
  - **Clang stays for development only**: the formatter, the lint, the editor's checks and the script that lists the processors (see generator.md) are clang's. Clang can't read reflection, so a file that holds it, and every file that includes it, is closed to them. The user chose reflection wherever it is useful; so far it is in one file, which gives clang an empty stand-in (see **An event's fields as a list**). The lint follows the build's compile commands, so it reads the C++ library the build uses, GCC's.
  - **GCC's warnings are the build's**, and they are errors. Where GCC warned and clang hadn't, the code changed, with one exception: `-Wno-ignored-attributes`. Wherever a SIMD vector type such as `__m512` is a template argument (a `std::array` of vectors, `std::conditional_t`, `std::is_same_v`), GCC drops the attribute that lets a pointer of that type read memory of any other type, and warns. Falcon passes vectors by value and reads and writes memory through intrinsics on `float*`, so nothing depends on that attribute, and keeping vector types out of every template argument would be a rule for each processor's writer. The flag gives up GCC's notice when an attribute written on a type alias, e.g. an alignment, is dropped inside a template; Falcon aligns with `alignas`, which is never dropped.
  - **GCC's C++ library checks at run time**, since the build defines `_GLIBCXX_ASSERTIONS`, which clang's library ignored (see **Hardening** in beyond_prototype.md).
  - **Latency**: on the FIR chain, GCC's median is about a quarter below clang's (see **The FIR chain's latency** in test_suite.md).
- **Hardware input/output latency** is outside the engine design. It is being worked out with the neurotech companies, who shape their firmware for it.

### One sample per pass
Each `process()` call handles at most one sample: one time point across all channels. There is no buffer size (samples per call, as in audio software). Batching samples only pays off when each call has a large fixed cost, such as Falcon 1's scheduling of hundreds of OS threads. Here each core runs one pinned thread, so batching would only add latency.
- Neuralynx and Ripple are expected to deliver each sample immediately (for Ripple, to verify; see **Agreed**).
- Neuropixels 1.0 sends 12 samples per packet, one packet every 0.4 ms, so 0.4 ms is its latency floor. Its sample rate is still 30 kHz: the 12 samples go through the graph one per pass, back to back (see **Buffers**), so a spike in the packet's 3rd sample triggers after 3 passes, not after all 12. If imec ever delivers single samples, nothing in the engine changes.
- No batching later either, not even at +2000 channels, where the channels are split across cores instead (see **Scaling to +2000 channels** in beyond_prototype.md).

### Processors
- **Three kinds, by their connections**: an input processor has only outputs (a hardware input, SignalGenerator), an operator has both inputs and outputs (IirFilter, a detector, Trigger), and an output processor has only inputs (a hardware output, EventLogger). The name can recall C++'s `operator` keyword; the alternatives were vaguer or already meant something in Falcon (intermediate, transform, stage, midstream, block, element, node, filter).
- **One processor per stream**, never per channel or tetrode (Falcon 1's hundreds of processors were a major cause of slowness). A processor handles all channels with handwritten SIMD: every processor has a hand-crafted AVX512 version and a hand-crafted AVX2 fallback, rather than relying on the compiler to vectorize. The version for the machine is picked at compile time, since `pipeline.cpp` is compiled for the machine that runs it. Both versions sit in the same `process()`, in the two branches of `if constexpr (HAS_AVX512)`, where `HAS_AVX512` is a constant the engine sets from the compiler's target; `load(simd_vector_index)` then returns an `__m512` or an `__m256` (see **Operations a processor uses** under **Buffers**). C++ skips a discarded `if constexpr` branch only for code that depends on the processor's template parameters; anything else in it must still compile on both instruction sets, so e.g. `SimdVector result = _mm512_setzero_ps();` fails in an AVX2 build. The AVX512 branch names `__m512` itself. The engine's own helpers depend on no such parameter, so they pick their version with `#ifdef __AVX512F__` instead. There is no scalar code, and AVX2 and FMA (fused multiply-add, on every AVX2 CPU since 2013) are required to run Falcon; the engine refuses to compile without either. Per-group settings (e.g. per-tetrode thresholds) are arrays inside the processor.
- **`process()` never loops and never waits.** In Falcon 1, each processor ran its own `while (running)` loop in its own thread. Here, `process()` checks its inputs, returns at once if there is nothing to do, and otherwise does its work. A waiting processor would stall every other processor on its core.
- **All logic lives inside the processor**, including when it runs. The engine never buffers anything for a processor.
  - A processor that produces output only every N samples (decimator, spike-count binner, decoder) leaves its output empty in between, so everything downstream of it also runs only every N samples. This is how lower rates exist inside a graph.
  - A processor with several inputs combines them itself. Example: p3 needs sample N from both p1 and p2. If p1's sample N arrives first, p3 copies it into its own state and waits; when p2's sample N arrives, p3 processes both. It works the same when p2 is on another core and its samples arrive through a ring. If an input stops, p3 drops its oldest kept sample and logs a warning once.
  - Phases become state. Falcon 1's RippleDetector had a burn-in loop before its detection loop; here it is `if (burningIn) { update statistics; return; }`.
  - A processor that acts on time checks the time itself on every pass, counting either CPU time or samples. Anything that ends an output, such as turning a TTL off 1 ms after a trigger, is timed in CPU time, so it ends even if the input stops. Such a processor must run on a spinning core (see **Waiting for data**).
- **A processor is a struct with an `Options` struct**: a `process()` function, a constructor and a destructor, plus an `Options` aggregate that holds only the processor's options, so they are set by name with designated initializers. The constructor acquires resources (memory allocations, sockets, file descriptors) and the destructor releases them. Internal state, such as filter history, lives in the processor, outside `Options`. No virtual functions: they would force one `process()` signature on every processor. The UI reads a processor's options and connections from a list that a script makes from the processors' source (see generator.md) (other options for later: **Processor type alternatives** in beyond_prototype.md).
  - Options are always named, never positional (non-negotiable): `IirFilter ap {300, 6000}` would also compile with highpass and lowpass swapped.
  - **Every option is a compile-time constant**, so the compiler can fold options into the instructions and use them for array sizes and loop counts. No option changes while the engine runs: changing one means generating, compiling and spawning a new engine program (see **Boundaries**), so every processor starts again from scratch (e.g. a detector's burn-in statistics are lost).
    - A processor checks its options with `static_assert`, and each such check carries a message that tells the user what is wrong, since the UI shows it (see **Every `static_assert` about an option carries a message** in generator.md).
    - Each option carries a doc comment (`///`) written for the user, since the UI shows it as the option's description (see **Every option has a doc comment, written for the user** in generator.md).
  - So `Options` is a template parameter, after the stream type: `IirFilter<RippleRaw, {.highpass = 300, .lowpass = 6000}> ap;` (compiler support: see **The compiler is GCC** under **Boundaries**). It can't be nested inside its processor, because it must be declared before the processor's template, so it gets its own name, e.g. `IirFilterOptions`. The constructor takes only the processor's name (see **Processor names** under **Logging**) and reads the options from the template parameter.
  - **An error is an exception, and it always ends the run**: a constructor that fails (e.g. a socket that won't open) throws, by calling `fail(name, "…", …)` (below), so its line names the processor, not only its type. So `name` is a processor's first member: it exists before anything else in the constructor can fail. The engine catches the exception and logs it, and the graph doesn't start. Errors are expected only there: nothing in the loop is expected to throw, and exceptions cost nothing while none is thrown. A condition the run survives is a warning (see **Logging**).
    - If `process()` ever meets a condition the run can't go on from, it calls `fail(name, "…", …)`, a cold, never-inlined helper of the engine's that takes only values, logs the error line and throws, so `process()` holds only a branch and a call (see **Inlining every `process()`** in beyond_prototype.md). The core's thread catches the exception and clears `is_pipeline_running`, so every loop ends and every destructor runs, setting its outputs safe (e.g. PCIeParallelOutput sets its pin low). `fail()` logs the line itself, as an `error` line with the processor's name through the central logger (see **Logging**), before it throws: C++ runs the failing core's destructors before the catch, so one that hangs would otherwise hide the reason. An exception that `fail()` didn't throw (a library's, or the name registry's) is logged by the catch instead, so after that core's destructors. A processor never catches a `fail()` exception and carries on, since its line is logged already. Rejected: handing the exception to the main thread to print, which shows it up to 100 ms later, or never if the main thread is stuck waiting for a core that doesn't end. The throw costs microseconds and allocates on the realtime core, while the run is ending anyway.
    - **An exception of any type ends the run this way**, not only a `std::exception`. One of another type (e.g. a library's own) has no message, so its line names its type. Left uncaught, it would end the program at once, with no destructor run.
    - **Destructors never throw.** An exception that leaves a destructor ends the program at once (`std::terminate`), so the other processors' destructors wouldn't run, and an output could stay on. A destructor prints a failure instead.
    - C++ then destroys the processors already built on that core, in reverse order, and never builds the later ones.
    - The failing processor's own destructor doesn't run, because C++ runs a destructor only for a fully built object. So a resource acquired before the throw is either released before throwing or held by a member with its own destructor (e.g. a socket wrapper), which C++ does run. This matters most for device state the OS doesn't reset when the program exits, e.g. a device left acquiring.
  - Rejected: optional `on_init()` and `on_destroy()` hooks, which `pipeline.cpp` would call through helpers that check with a concept (`HasOnInit`, `HasOnDestroy`) and `if constexpr` whether the processor defines them. A constructor and destructor are standard C++, and C++ runs them automatically.
  - Rejected: no constructor, with the processor itself an aggregate and each resource a member built from options declared above it (`int port = 6363; Socket sock {port};`). A member declared above an option it reads gets an uninitialised value, possibly without a compiler warning; checks across options (e.g. highpass below lowpass) have no natural place; and an aggregate can't have private members, so `pipeline.cpp` could set internal state by name.
- **The channel count is a compile-time constant**, so the compiler knows every loop's length and every buffer's size (e.g. 32 float32 channels are exactly two AVX512 vectors, or four AVX2 vectors). A processor never hardcodes it: the same code runs at 32, 64 or 2000 channels, and different streams can have different counts (e.g. the branches of a channel split, shape 9 in graph_shapes.md). A new channel count means regenerating and recompiling `pipeline.cpp`.
- **Stream type**: the compile-time facts about a stream (channel count, sample rate, sample type) are grouped in one named type, a `StreamInfo`, and each processor takes it as a template parameter:
  ```cpp
  using RippleRaw = StreamInfo<32, 30000.0, float>;   // written once

  IirFilter<RippleRaw, {.highpass = 300}>      ap;
  SpikeDetector<RippleRaw, {.threshold = -50}> spikes;
  ```
  Adding a fact later changes only `StreamInfo`, not any processor.
  - **Template parameters have descriptive names**, like every other name, so unfamiliar code reads without context: `InputStreamInfo` and `OutputStreamInfo` in a decimator, `EventType` and `Capacity` in `EventBuffer<EventType, Capacity>`, never `S`, `E` or `N`. No `.clang-tidy` rule checks template parameter names. A stream parameter can't be named just `StreamInfo`, which is the template's own name, so where no direction applies it is `StreamInfoType` (e.g. `SampleBuffer<StreamInfoType>`).
  - **Class constants are lower_case** (`InputStreamInfo::simd_vectors`, `InputStreamInfo::rate`), like the standard library's (`std::numeric_limits<float>::digits`), while global constants are UPPER_CASE (`HAS_AVX512`). `.clang-tidy` enforces both. A processor whose output stream differs from its input takes both stream types and derives what it needs from them: a decimator from 30 kHz to 1 kHz gets its factor of 30 from the two types and needs no option for it. The generator writes these types; for the prototype we write them by hand.
- **Options** (params) are primitives (int, floating point, bool, string), enums, fixed-size arrays of these (e.g. per-tetrode thresholds), or a path to a file, such as a filter coefficients file or an IMRO file. All of them work as template arguments as they are, negative and fractional values included (C++20), except strings (see below). A value of the wrong kind, such as 1.5 for an int option, is a compile error.
  - **String options use `Str`**, one string type written once in the engine: a processor declares `Str name;`, and `pipeline.cpp` writes `.name = "Abc"`. Neither `std::string` nor a pointer to a string literal can be a template argument. A string option's length is known when `pipeline.cpp` is compiled, so nothing needs a string that grows at run time: `Str` is a fixed-capacity character array of 256 bytes, so a string has at most 255 characters plus the terminating zero. A longer string is a compile error, never cut. Its bytes sit in the program's read-only data, not in processor state. Rejected for now: C++26 `std::define_static_string`, which would only remove the length limit and needs reflection in the compiler.
  - **A file option is only its path**, a string; the constructor reads the file at run time with ordinary file I/O. So the file's contents are not compile-time constants and never set an array size or a loop count. The exception is a file whose contents set sizes, such as filter coefficients (the number of sections sets the filter's state): the generator reads it and writes its contents into `pipeline.cpp` as an option value, so they are compile-time constants like any option (see **IirFilter**). Rejected: copying the file into the program at compile time with C++26 `#embed`, more machinery for no gain outside the loop (see **How to prioritise**).
- Processors are stateful or stateless. Each is a concrete type in one translation unit, so the compiler can inline a whole core loop into one fused unit. In the prototype, the compiler decides which `process()` calls to inline; forcing every call inline is in beyond_prototype.md (**Inlining every `process()`**).
- **Processor authors are trusted.** A processor is hot-path code that works directly on memory for speed, so the interface doesn't try to make mistakes impossible. It prevents a mistake only where that costs nothing at run time and doesn't limit how a processor is written (e.g. `In` and `Out` below); everything else is left to processor tests (see **Processor tests** in test_suite.md).
- **`process()` signature**: `process()` takes one struct, `Connections`, declared inside the processor, with one member per connection. Every member is an input `In<Kind>` or an output `Out<Kind>`, where `Kind` is one of the three kinds a connection carries (see **Buffers**): a sample buffer, an event buffer, or a state value such as `bool`. Example: `struct Connections { SampleInputBuffer<InputStreamInfo> input; EventOutputBuffer<Spikes<InputStreamInfo>, 1> output; };` and `void process(Connections connections);` (a sample buffer is a `SampleBuffer<StreamInfoType>`, an event buffer an `EventBuffer<EventType, Capacity>`, see **Capacity** under **Events**). `process()` returns nothing. A member is one connection, or a port with slots, which takes as many connections as `pipeline.cpp` gives it (see **A port with slots** below). `pipeline.cpp` names every connection at the call, `spike_detector.process({.input = ap_filter_to_spike_detector_sample_buffer, .output = spike_detector_to_trigger_spikes_event_buffer});`, as in the sketch under **pipeline.cpp**, and `In` and `Out` bind to the buffers and values. A processor's internal state (e.g. filter history) is not in `Connections`: it lives in the processor.
  - **Connections are written with aliases**: `SampleInputBuffer<StreamInfoType>` and `SampleOutputBuffer<StreamInfoType>` for the `In` and `Out` of a `SampleBuffer`, `EventInputBuffer<EventType, Capacity>` and `EventOutputBuffer<EventType, Capacity>` for an `EventBuffer`, and `StateInput<StateType, default_value>` and `StateOutput<StateType, initial_value>` for a state value (e.g. `StateOutput<bool, false> is_ripple_ongoing`, see **State values** under **Buffers**), and `InputSlots<Kinds...>` and `OutputSlots<Kinds...>` for a port with slots (see **A port with slots** below). Processors use only these and never write `In` or `Out` directly, so each connection is written one way. Each name says what flows and which way, and a buffer's name says it is a buffer, so someone new to Falcon can't mistake it for a processor. The aliases are transparent: the compiler and reflection still see `In` and `Out`. Rejected: `Out<EventBuffer<Spikes<RippleRaw>, 1>>` written out (nested brackets); `SampleInput`, `EventOutput` (read like processor names such as `NeuropixelsInput`); `InputSamples`, `OutEvents` (don't say it's a buffer).
  - **Connection names**: a processor's only input is named `input` and its only output `output`, whatever their kind. The processor's name already says what it does, so the connection's name needs to say no more. A processor with more than one input names each input after its role in the processor, e.g. a Trigger's `spikes` and `ripples`, and the same goes for outputs. Inputs and outputs are counted separately: a SpikeDetector with one input and two outputs has `input`, `spikes` and `noise`. State-value connections are exempt from `input` and `output`: a state is always named after its role, even as a processor's only input or output, e.g. RippleDetector's `is_ripple_ongoing` output, read by a Trigger's `is_ripple_ongoing` input to trigger only during ripples. A bool state starts with `is_` or `has_`, like every bool. The member's name is also the connection's label in the UI. Not a priority: names will settle as more processors are written.
  - Why a struct: two connections of the same type in the wrong order are a compile error instead of a wrong experiment. It costs nothing at run time: measured with four and with ten connections, once `process()` is inlined both forms compile to the same instructions. Out of line, the struct is copied to the stack on every call (a few ns, see **Inlining every `process()`** in beyond_prototype.md). Rejected: one parameter per connection, which compiles with a swap; argument comments at each call (`/*filtered=*/ap_buf`) checked by clang-tidy's `bugprone-argument-comment`, which catch a swap only when linting.
  - **Required and optional connections**: a member that `pipeline.cpp` must always pass is a plain `In` or `Out`; it has no default, so C++ rejects a call that leaves it out. A state input is the exception: it always has a default and is never required (see **An unconnected state input reads its default** under **Buffers**). A member that `pipeline.cpp` may leave out is a `std::optional` of its `In` or `Out`, e.g. `std::optional<EventOutputBuffer<NoiseLevel, 1>> noise = std::nullopt;`, and `process()` puts both the calculation and the publishing for it under `if (connections.noise) { connections.noise->push(...); }`. `pipeline.cpp` leaves it out when nothing is connected, a constant fixed when `pipeline.cpp` is compiled, so once `process()` is inlined, the compiler deletes the block, calculation included; out of line, it stays behind one run-time branch. Measured: with the connection left out, an inlined processor compiles to exactly the same instructions as a copy of it that never had the connection, both on its own and inside a running core's loop. When it is connected, `Out` still clears the buffer at the call.
    - A use without the check compiles: C++ has no nullable type that the compiler forces to be checked (`*` and `->` on an empty `std::optional` are undefined behaviour). It is caught by clang-tidy's `bugprone-unchecked-optional-access`, which analyzes a processor only where a pipeline or a processor test instantiates it (measured). It is also caught at run time by the C++ library's own checks, which every build has on since Falcon builds with GCC (see **Hardening** in beyond_prototype.md), and by processor tests that run each processor with every optional connection left out (see **Processor tests** in test_suite.md).
    - Rejected: every form that makes such a use a compile error, as too complicated to use or read: a wiring struct as a template argument, read with `if constexpr`; a loop, macro or lambda that names the buffer only inside the block (the macro's `break` and `continue` also act on its hidden loop); one function per optional connection (`process_noise()`). Also rejected: a handle whose `push` does nothing when not connected, since publishing on a missing buffer must never happen.
  - **A port with slots**: one member of `Connections` that takes as many connections as `pipeline.cpp` gives it, with no limit, each of its own kind: `InputSlots<Kinds...> inputs;`, or `OutputSlots<Kinds...>` for outputs. The processor is a template over those kinds, so `pipeline.cpp` names in the processor's type what is connected, e.g. `Recorder<options, SampleBuffer<…>, EventBuffer<…>>`, and passes the connections as a list, `recorder.process({.inputs = {a, b}});`. One instance sees every slot, each with its own type, and nothing is decided at run time. A port that takes any kind is an unconstrained list of kinds; one that takes only some (e.g. mask events) is a constrained one. The processor goes through its slots with a C++26 expansion statement, `template for (const auto& input : connections.inputs) { … }`, in which each slot has its own type, so whatever differs by kind is an overloaded function. A template's list of kinds has to come last, so such a processor's options come first. Recorder is the first such processor (see **Recorder**).
    - Costs: the processor's type and its compile time grow with its connections. And clang-tidy takes the names clang gives such a loop's slots (`__u0`, `__u1`, …) for the author's, so `.clang-tidy` lets those names through its naming checks.
    - No limit on the number of slots, unlike Falcon 1's ports (see **Ports with slots** in falcon1_differences.md), whose graphs held hundreds of connections; here a graph is lean, a few processors on each core. What those limits were for is mostly gone: the number of connections is fixed when `pipeline.cpp` is compiled, so nothing grows or is allocated during a run, and with one processor per stream a port gets a few connections, not one per tetrode. What remains to guard, and no number guards it: an extra consumer on another core costs the producer's core a copy per sample (see **A buffer that feeds rings** under **Rings**), and a slow consumer never delays or starves another one, since a writer never waits (see **Rings**).
    - Rejected: one instance of the processor per connection, made by the generator, which leaves the engine as it is but lets nothing combine its slots or write them into one file. Slots at run time behind one interface, as in Falcon 1: an ordinary loop, and a processor type that doesn't change with its connections, but an indirect call per slot on every pass, type mismatches found only when the graph starts, and a second kind of connection beside the compile-time one.
  - A member of `Connections` that is neither `In` nor `Out` can't be used, so an author can't get a direction wrong, and writing to an `In` is a compile error. A plain state type doesn't bind, since `pipeline.cpp` passes a `StateValue` (see **State values** under **Buffers**). `SampleBuffer` and `EventBuffer` can't be copied, so a member holding a copy doesn't compile, and their contents are private to `In`, `Out` and the rings, so a member holding a plain reference to a buffer can't read or write it. Without this, a plain reference to an output would never be cleared (see **`Out` clears an output buffer** under **pipeline.cpp**), and pushes into a copied event buffer would be lost, both without an error. Rejected: a reflection check over `Connections`' members, which would add reflection for a guarantee the types already give. Graph users never see these errors: the generator connects only matching inputs and outputs.
  - `process()` itself is never a function template: C++ doesn't deduce template arguments through the conversion to `In` or `Out`, so `template <typename EventType, int Capacity> void process(EventInputBuffer<EventType, Capacity> input)` fails to compile when `pipeline.cpp` passes an `EventBuffer<Spikes<RippleRaw>, 1>`. Every type comes from the processor's own template parameters instead (e.g. `EventLogger<Spikes<RippleRaw>, 1>`, see **Events**). This costs nothing: the generator knows every connection's type and writes it out.
  - `In` and `Out` are thin references, so the compiled loop is the same as with plain references. Reflection can later read `Connections` for the UI: direction from the wrapper, kind from `Kind`, name from the member's name.
  - Rejected: `const&` for inputs and `&` for outputs. An author who forgets `const` turns an input into an output without an error, and every author would have to be told to remember it.

### pipeline.cpp
`pipeline.cpp` holds the processors with their options, their buffers, a ring wherever a connection crosses cores, and one loop per core.

**Layout**: each core's function starts with a `// Processors` section (its processors with their options), then a `// Connections` section (its buffers and state values), then its loop, so a reader sees what runs and what connects it before reading the loop (see the sketch below). The two comment lines go from a generated `pipeline.cpp`, the order of the sections stays (decided by the user on 21 November 2026, see **`pipeline.cpp` holds as few comments as possible** in generator.md).
- **Buffer names**, to change (decided by the user on 21 November 2026, not in code): a buffer is named by its upstream processor and its output alone, and a ring also by the core that reads it (see **A buffer is named by its upstream processor and its output** in generator.md); a state value's name follows the same rule. Until the pipelines are changed, their names are as follows. They say which processors and connections a buffer joins and what it carries: `<producer>_to_<consumer>_<kind>_buffer`, with the processors' variable names in `pipeline.cpp`, e.g. `dummy_generator_to_example_logger_event_buffer` or `ap_filter_to_spike_detector_sample_buffer`. A connection named after its role (see **Connection names** under **Processors**) is added after its processor's name, at either end, e.g. `spike_detector_to_trigger_spikes_event_buffer`; the default `input` and `output` are left out. This also keeps two connections between the same two processors apart (e.g. a SpikeDetector's `spikes` and `noise` outputs, both read by one logger). A state value follows the same rule, ending in `_state`; since a state is always named by role, both ends show: `ripple_detector_is_ripple_ongoing_to_trigger_is_ripple_ongoing_state`. A state value that crosses cores is a `CrossCoreStateValue` and ends in `_cross_core_state`. Not chosen: `SharedStateValue`, since Falcon 1's shared states were shared between processors, with several writers (see **Shared states** in falcon1_differences.md); `AtomicStateValue`, which names how it is built and not what it is for; and `StateRing`, since it holds only the latest value and is no ring. A buffer read by several processors lists them all, in the order they appear in `pipeline.cpp`: `neuropixels_input_to_ap_filter_and_lfp_decimator_sample_buffer`. The generator writes these names, not people (see generator.md), so the rule only has to be mechanical and unambiguous; the prototype's hand-written graphs follow it too. A ring follows the same rule, ending in `_ring` (e.g. `lfp_decimator_to_ripple_detector_sample_ring`). A buffer next to a ring is named after the processors on the two cores, so it has the same name on both cores, matching its ring (e.g. `lfp_decimator_to_ripple_detector_sample_buffer` on cores 2 and 3).

**In/out buffers.** `process()` reads its input buffers, writes its output buffers and returns nothing, like an audio plugin. `pipeline.cpp` declares every buffer and passes the buffers to each processor's `Connections`, so the data flow is visible in the loop. Chosen for clarity: there is one way to hand over data.
- As fast as returning values: each buffer is a local variable of its core's function, touched only by the inlined loop (see **Processors**), so the compiler can keep the buffer's count in a register. The samples go through L1 either way. This holds only while buffers stay local to their core's function.
- A processor can take several input and output buffers.
- The engine owns the buffers, so the generator can later let processors share buffers, or let a filter overwrite its input in place, without touching any processor (see **Buffer reuse** in beyond_prototype.md). The UI's cache view can count every buffer from `pipeline.cpp` (see **Cache view** in pipeline_designer.md).
- **A connection that crosses cores is passed like a buffer**: `pipeline.cpp` gives the ring itself to `process()`, as the producer's output on one core and as the consumer's input on the other, and a core's loop is `while (next_pass())` around its `process()` calls and nothing else. The engine does the ring's work while it builds and destroys the `Connections` argument (see **Passing a ring to `process()`** under **Rings**), so no call can be forgotten or misplaced, however many rings a core has. An output that is read on its own core and on others is a buffer declared with the rings it feeds, e.g. `SampleBuffer<…> ap_filter_to_spike_detector_sample_buffer{ap_filter_to_recorder_sample_ring};`.
  - Rejected: the ring calls written out in the loop (`read` at the top of the reader's loop, `next_slot` before and `publish` after the producer's call, a flag per ring for the wait of a core that isn't realtime). The generator writes `pipeline.cpp`, and every ring added lines that had to sit in the right place.
  - **No copies across rings** where the producer's output is the ring: it writes straight into the ring's next free slot, and the reader's input points at the slot it reads.
- **`Out` clears an output buffer**: when `pipeline.cpp` passes a buffer to an `Out` (see **`process()` signature** under **Processors**), `Out`'s constructor clears it (count 0). C++ builds the whole `Connections` argument before `process()` starts, so the buffer is cleared right before its producer runs, on every call. So a processor that returns at once leaves its output empty, and neither a processor author nor `pipeline.cpp` can forget to clear it. Clearing right before the producer, not at the start of the pass, keeps feedback connections working, since they read the previous pass's output. It costs one write per buffer per pass. A state value passed to an `Out` is never cleared.
  - Rejected: wrapping every output in `out()` at the call (`lfp.process(raw_buf, out(lfp_buf))`), which did the clearing and showed the outputs in the loop. With `Out`, the signature already shows the direction, and a state value would have needed `out()` too without being cleared.

The sketch is an example with more processors than the prototype's graph. `Ring` stands for `SampleRing<StreamInfoType, slot_count>` or `EventRing<EventType, Capacity, slot_count>` (see **Rings**), whose constructor takes the ring's name for warnings; `Buffer` stands for `SampleBuffer<StreamInfoType>` or `EventBuffer<EventType, Capacity>` (see **Operations a processor uses** under **Buffers**), and stream types (see **Stream type** under Processors), the first template argument of every processor, are left out for brevity.

```cpp
// inserted where a connection crosses cores
Ring neuropixels_input_to_ap_filter_and_lfp_decimator_sample_ring;
Ring lfp_decimator_to_ripple_detector_sample_ring;
Ring ripple_detector_to_trigger_ripples_event_ring;

void core1() {
    // Processors
    NeuropixelsInput<{.port = 6363}> neuropixels_input;

    while (next_pass()) {
        // polls the hardware and writes straight into the ring; the sample is visible to core 2
        // when the call returns, if there is one
        neuropixels_input.process({.output = neuropixels_input_to_ap_filter_and_lfp_decimator_sample_ring});
    }
}

void core2() {
    // Processors
    IirFilter<{.highpass = 300, .lowpass = 6000}> ap_filter;
    SpikeDetector<{.threshold = -50}>             spike_detector;
    Decimator                                     lfp_decimator;   // factor 30 comes from its two stream types
    Trigger                                       trigger;
    PCIeParallelOutput                            pcie_parallel_output;

    // Connections, all owned by the engine
    Buffer ap_filter_to_spike_detector_sample_buffer;
    Buffer spike_detector_to_trigger_spikes_event_buffer;
    Buffer trigger_to_pcie_parallel_output_event_buffer;

    while (next_pass()) {
        // the ring's next sample, fetched here, once for this pass; Out clears the output buffer
        ap_filter.process({.input  = neuropixels_input_to_ap_filter_and_lfp_decimator_sample_ring,
                           .output = ap_filter_to_spike_detector_sample_buffer});
        // every process() returns at once if its input is empty
        spike_detector.process({.input  = ap_filter_to_spike_detector_sample_buffer,
                                .output = spike_detector_to_trigger_spikes_event_buffer});
        // the same sample as ap_filter got; has output only every 30th sample
        lfp_decimator.process({.input  = neuropixels_input_to_ap_filter_and_lfp_decimator_sample_ring,
                               .output = lfp_decimator_to_ripple_detector_sample_ring});
        // two inputs, so named by role
        trigger.process({.spikes  = spike_detector_to_trigger_spikes_event_buffer,
                         .ripples = ripple_detector_to_trigger_ripples_event_ring,
                         .output  = trigger_to_pcie_parallel_output_event_buffer});
        // raises its pin on a trigger event, lowers it once the pulse width has passed
        pcie_parallel_output.process({.input = trigger_to_pcie_parallel_output_event_buffer});
    }
}

void core3() {
    // Processors
    RippleDetector<{.threshold = 3}> ripple_detector;

    while (next_pass()) {
        ripple_detector.process({.input  = lfp_decimator_to_ripple_detector_sample_ring,
                                 .output = ripple_detector_to_trigger_ripples_event_ring});
    }
}
```

### Per-core loop
- **One loop per core.** Each core runs one thread, pinned to that core, and each pass of its loop calls every processor on that core once.
- **Each core's processors are declared inside that core's function** (as in the sketch under **pipeline.cpp**), so processors of different cores never share a cache line (false sharing). Rings and cross-core state values (see **State values** under **Buffers**) are then the only memory that cores share.
  - **What one core writes is kept 128 bytes apart from what another core reads or writes**: the positions of a ring, the members only its reading core or only its writing core uses, its slots as a whole, a cross-core state value, and the positions of each core's log messages. Two cache lines, not one, since the CPU may fetch the line next to the one it touches along with it, which must then not be a line another core writes. Sample values keep their own alignment of one cache line, which is for loading them, not for keeping cores apart.
- **Start barrier**: each core builds its processors, then waits at one barrier shared by all cores (e.g. C++20 `std::latch`). Once every core has arrived, all loops start together; if a constructor failed on any core (see **An error is an exception** under **Processors**), every core returns instead. Without the barrier, the input could start filling a ring while another core is still failing, and the full ring would log a second, misleading error. A core's function doesn't call the barrier: `next_pass()` waits at it on the core's first pass, so a loop of the form `while (next_pass())` can't leave it out, and never runs if startup failed (decided by the user on 21 November 2026, in code; measured to cost nothing that shows, see **The start barrier inside `next_pass()`** under **Done** in test_suite.md). A second call on a core returns at once, so a loop of another form still calls `wait_at_start_barrier()` itself in front of it.
  - A core's thread pins itself to its core only when it reaches the barrier, after building its processors. A thread that a library starts in a constructor (e.g. xipplib's, to receive packets) inherits its creator's CPUs; started on a pinned realtime core, it would compete with a loop that never yields, so its data would arrive late and in bursts.
- **Flush-to-zero** is set on every core. Flat or zeroed channels (dead, reference, or blanked during stimulation) drive IIR filter state into denormal floats, which many CPUs process far more slowly. Values that small (below 10⁻³⁸ in float32, 10⁻³⁰⁸ in double) mean nothing for neural data.
- **Order**: processors are called in a fixed order, and each comes after the processors it reads from, so a sample goes from input to output in a single pass. If a processor comes before one it reads from, that connection becomes a feedback connection, one pass late (see **Feedback connections** in beyond_prototype.md). In the product, the user sets the order in the node editor.
- **Chains**: connected processors on the same core form a chain. The chain ends where the next processor is on another core.
  - A chain has no rings inside, and each processor keeps its own state.
  - A chain starts at an input (hardware, or a ring from another core) and runs to its end without waiting: a sample passes through the whole chain in one pass. An empty pass costs one empty-input check per processor (estimate: under 1 ns each, to be measured).
  - A core can run several chains. They delay each other (see **Several chains on one core** in beyond_prototype.md).
- **Ring writes** can happen anywhere in the loop, since a write never waits: a ring is written when its producer's call returns, and read when its first reader is called (see **Passing a ring to `process()`** under **Rings**).
- **Example**: p1 → p2 → p3 → p4 → p5 → p6, with p3 on core 2 and the rest on core 1.
  - Chains: [p1 p2] and [p4 p5 p6] on core 1, [p3] on core 2.
  - Core 1's loop: p1, p2, the ring writer to core 2, the ring reader from core 2, p4, p5, p6.
  - In one pass, core 1 handles sample N+1 in p1 and p2 and sample N−1 in p4 to p6, while core 2 works on sample N.
  - With p3 on core 1 too, all six form one chain in one loop, with no rings.

### Buffers
- **A connection carries one of three kinds**, and nothing else flows between processors: samples (all channels of one time point; defined by sample type, channel count and rate), events (see **Events**), or a state value (see **State values** below).
  - Rejected: merging samples and events into one kind, a buffer of items of one type with a capacity per pass, where a sample is one more item type. It changes nothing for speed, latency, alignment or cache: both are a pointer plus a count with compile-time types, and alignment comes from the item type either way. Less engine code is not a goal.
- **A buffer is a pointer to data plus a count**: 0 or 1 sample with its header, or the events produced on this pass (zero or more). Its storage belongs to the engine, but a producer can point it at data that already exists elsewhere (a ring slot, a socket receive buffer), so nothing is copied to hand data over.
- **Each sample has a header** of four values, 32 B, set by the input processor (rings add to the last one):
  - its sample number: 64-bit, counted at the input's rate, with the same meaning on every device. Processors use it to match samples from different inputs, count samples and stamp events. The input derives it from the device's clock and never counts samples itself, so a lost sample shows up as a gap instead of shifting every later number without an error;
  - the device's own timestamp for that sample, in the device's own unit, which links Falcon's samples to the device's recording (e.g. Ripple's recorded ephys data, for the correctness check in test_suite.md). Processors never calculate with it. Example: Neuralynx counts its clock in µs, so sample numbers 0, 1, 2 at 32 kHz have device timestamps 31.25 µs apart; on Ripple, the device timestamp counts samples, so the two values are equal;
  - its arrival time (TSC), for the latency check in test_suite.md: LatencyBenchmark logs the time from it to the trigger decision (see **Trigger and outputs**);
  - its lost-sample count (`lost_sample_count`): how many samples were lost upstream since the start. The input adds the samples the device skipped (a jump in the device's own numbering), and each ring adds the samples it has dropped so far, in `publish()`. A processor sees a loss when the count differs from its previous sample's, whatever the stream's rate. The count only grows, so any later header carries every earlier loss: a processor that passes on only some headers (one in 30, or its newest event's) forwards it without doing anything.
    - Rejected: comparing each sample number with the previous one plus the stream's step, which needs a step fact in `StreamInfo` for every lower-rate stream (e.g. a spike-count binner's output, 300 samples apart for 10 ms bins at 30 kHz); a "gap here" flag, which every processor that passes on only some headers must carry forward, so one that forgets hides the loss downstream without an error; numbering each stream at its own rate, which breaks matching samples across rates.
  - Falcon 1 recorded the same two times (arrival time and device timestamp). Flags wait until something needs them.
- **The header travels with its sample.** A processor reads its input's header as `connections.input.header`, and starts each output sample with `connections.output.set_header(header)`, which copies the given header and sets the count to 1, so no sample exists without one. The same call serves a processor that passes on a header and one that builds a new one (an input processor, a test-signal generator, a spike-count binner fed by events). `set_header` is also where the processor decides that it outputs a sample on this pass: a decimator from 30 kHz to 1 kHz calls it on 1 pass in 30, and without the call the output stays empty. Usually it passes its input's header; a processor that outputs a sample late (e.g. after a lookahead) passes the header it kept with that sample, and one with two sample inputs passes one of their headers, whose arrival time is then what the latency log measures from, with the two inputs' lost-sample counts added, so a loss on either shows downstream. A processor with a sample input never makes up a new header: a made-up sample number breaks matching across inputs and gap detection, and a new arrival time makes the latency log measure from the wrong moment.
  - Rejected names: `emit`, `new_sample`, `start`, `forward` with a separate `create`, and `connections.output.header = connections.input.header` (setting a field that also makes the sample present is a hidden side effect). For the header itself: `stamp`. Whether a buffer holds a copy of the header or points at it in a ring slot is the engine's choice.
  - Rejected: one header per chain, handed by `pipeline.cpp` to the processors that need it. After a processor that outputs late, it would give every later processor the wrong sample number without an error.
- A count of 0 means nothing new on this pass.
- After a burst, the extra samples wait where they already are (in the ring or the socket buffer) and are handed over one per pass.
- **State values**: small results that describe a state, such as "the TTL is high" or "a ripple is ongoing", are plain values passed by reference. They keep their value until their producer changes it, and stay in registers once inlined. Anything that means "new on this pass", such as a detection, goes in a buffer, so `Out` clears it (see **`Out` clears an output buffer** under **pipeline.cpp**).
  - **A number, `bool` or enum** (e.g. `int`, `u64`, `float`, an enum of stimulation phases), so it fits in one register. Small structs could be allowed later without touching any processor.
  - **Its producer's author picks its initial value**, in the output's type: `StateOutput<bool, false> is_ripple_ongoing;`. There is no engine-wide default, and a missing one is a compile error, since `StateOutput` needs both arguments. `pipeline.cpp` declares the state as the producer's type, `StateValue<bool, false>`, which holds it; one declared with another initial value doesn't bind to that output and fails to compile. Left uninitialised, `-ftrivial-auto-var-init=pattern` would fill it with a pattern, so a `bool` could start `true` and report a ripple from the first pass, letting a Trigger fire on it. A reader takes `StateInput<bool, false>`, which binds to any initial value; its second argument is its default (see **An unconnected state input reads its default** below). Rejected: a named constant in the processor (`static constexpr bool initial_is_ripple_ongoing`), which the generator would find by name, so a missing or misspelt one fails only in the generator; an option (`.initial_is_ripple_ongoing`), which mixes connections into `Options` and lets the graph override the author's choice.
  - **An unconnected state input reads its default**: the processor's author picks the default in the input's type and initializes the member with `UNCONNECTED` (`StateInput<float, 6.0f> threshold_multiplier = UNCONNECTED;`), as options have defaults and an optional buffer is initialized with `std::nullopt`, and `pipeline.cpp` leaves an unconnected state input out of the call. The initializer is needed: without one the build's warnings reject a call that leaves the member out (`-Wmissing-designated-field-initializers`), and the lint rejects a bare `{}` as redundant. So a state input needs no producer, and no processor exists only to supply a fixed value. Connected, its producer's initial value applies and the default goes unused. One left out by mistake runs with its default, as a left-out option does. Every state input has a default, so none is required: a state complements a processor's main computation, which is designed to be right with the default never changing, so the author picks a default that is correct and safe with nothing connected (e.g. a line that stays low). Rejected: a required form without a default (`StateInput<bool>`), a second form for authors to choose between, for a case a well-chosen default covers; `pipeline.cpp` declaring the value (`StateValue<float, 6.0f>`), which makes every graph supply a value for each state input and leaves the UI nothing to prefill; a marker at the call (`.threshold_multiplier = unconnected`), a line per unconnected input against a mistake no worse than a left-out option.
  - **Across cores a reader gets the latest value, without waiting**: a state whose producer and reader are on different cores is one atomic value that the two cores share. The producer overwrites it. Each processor that reads it gets a copy taken right before its `process()` call, while its `Connections` argument is built (see **Passing a ring to `process()`** under **Rings**): the newest value it can get without waiting. Nothing is kept on the reading core, and one cross-core value serves any number of readers on any cores. Two processors on one core that read the same state can see different values in one pass, which is intended: each gets the newest value at its own call. A state doesn't mean that something new arrived (see **State value** in glossary.md), so no change has to be seen one by one. A state the UI writes during a run and a state read upstream of its producer cross cores the same way.
    - **The sample a change is seen on is not guaranteed.** The copy takes what the producer's core has written by that instant, and nothing makes the producer finish a sample before the reading core reaches it. Example: RippleDetector on core 3 sets `is_ripple_ongoing` while it processes sample 1000. If the Trigger on core 2 is called for sample 1000 before core 3 has finished that sample, it sees the change on sample 1001. While both cores keep the same pace, that is so in every run, except where core 3 finishes a sample at about the moment the Trigger is called: there a change lands on that sample or on the next, varying from change to change. When either core is briefly behind, e.g. catching up on what waits in its ring, the change is seen a sample or more earlier or later. On RippleDetector's core, the Trigger would see it on sample 1000, always. So a graph's behaviour depends on which cores its processors sit on, and whatever must be seen on an exact sample is sent as an event.
    - How soon a change is copied depends on how the reading core waits (see **Waiting for data**): a realtime core runs passes without samples too, so within one empty pass; a core that isn't realtime after its sleep, up to 1 ms later.
    - **Copied once per call, never read from inside `process()`.** `In` holds the copy as a plain value, so a processor that reads the state twice in one call gets the same value both times, and a read inside a loop over channels is a value in a register, not a load from shared memory on every turn, which the compiler could not move out of the loop. What a processor computes from its copy, and what it passes on to other processors on its core, the compiler optimises as within a core. Only the loads of two processors that read the same cross-core value are never merged into one. A state within a core is copied in the same way, not referred to. It fits in one register, so the copy is no bigger than a reference; out of line the copy is one load, where a reference is two and must be read again after every store that might have changed it; and one form for both spares `In` a run-time choice between them. Not chosen: a reference within a core, which is cheaper only for a state type larger than a register, if one is ever allowed.
    - **Each cross-core value has a cache line of its own, and its producer's core writes it only when the value changes**, when the producer's `process()` call returns, by comparing with the value it last wrote. A state output holds the value itself, within a core too, and hands it to its state value when the call returns; no other processor runs in between, so none can tell that from a write at the assignment. What moves between cores is the cache line a cross-core value sits on, each time one core writes it while another holds it. Written only on change, a steady state moves nothing, and each reader's copy finds the line in its own core's cache. Alone on its line, a write to one value never takes the line of another value, or of anything else, from a core that reads it. Packing several cross-core values into one line: see **State values across cores** in beyond_prototype.md. How far apart it is kept: see **What one core writes is kept 128 bytes apart from what another core reads or writes** under **Per-core loop**.
    - No way of crossing cores gives all three of: no waiting, a change seen on the same sample in every run, and every state served (any rates, a write from the UI, a feedback connection). The producer's result for a sample doesn't exist until the producer has computed it, so a reader that reaches that sample first either waits for it or uses an older one. Not chosen:
      - The reading core waits on every sample until the producer's core has finished that sample. The same sample in every run, as within a core. But a reader that gets its samples by another path, e.g. a Trigger on the spike path switched by `is_ripple_ongoing`, then waits for the slower of the two paths on every decision; a producer behind a decimator has no pass for most of the reader's samples; and it can't serve a write from the UI, which belongs to no sample, or a feedback connection, where each core would wait for the other.
      - A fixed delay: each change carries its sample number, and the reader applies it a fixed number of samples later. The same sample in every run, without waiting while the producer's core is less than that far behind. But every change is that late, a producer further behind needs a rule, and a change sent with its sample number through a ring is an event in all but name.
      - One copy per pass for all of a core's readers, taken at the first reader's call and told from the later calls by a mark of the pass, as a ring is read. All processors on a core then see the same value in a pass. But each reading core must keep its copy and its mark in memory of its own, off the cross-core value's cache line since it writes the mark on every pass, and each call compares the mark: more to keep and to place, for the rare case of two processors on one core reading the same state.
      - One copy per pass taken exactly at the start of the pass, which is steadier, since a reader's call comes later in the pass by what the core runs before it. `next_pass()` would have to know its core's cross-core values. Taken as arguments (`while (next_pass(is_ripple_ongoing_state))`), a hand-written `pipeline.cpp` can leave one out, that state then never changes, without an error, and the user finds it ugly. Registered at start, their addresses are stored, so the compiler reloads the copies from memory instead of keeping them in registers, against fusing a core's processors (see **Inlining every `process()`** in beyond_prototype.md).
- A buffer's contents are valid only until its producer's next call, which overwrites them: for the rest of the current pass, or into the next pass for a feedback connection (see **Order** under **Per-core loop**). Several processors can read the same buffer in that pass (e.g. `neuropixels_input_to_ap_filter_and_lfp_decimator_sample_buffer` is read by both `ap_filter` and `lfp_decimator` in the sketch). A processor copies what it needs to keep and never keeps a pointer into a buffer.
- A buffer filled by a ring reader looks the same as one filled by a processor on the same core, so a processor can't tell whether its input crossed cores.
- **Operations a processor uses**, each on the wrapper that allows it, so an `In` can only be read and an `Out` only written (see **`process()` signature** under **Processors**):
  - `SampleInputBuffer<StreamInfoType>`: `is_empty()`, `header`, and `load(simd_vector_index)`, which returns the channel vector at `simd_vector_index` as a float32 SIMD register of the compiled instruction set (`__m512` or `__m256`, see **One processor per stream** under **Processors**).
  - `SampleOutputBuffer<StreamInfoType>`: `set_header(header)` (see **The header travels with its sample** above) and `store(simd_vector_index, values)`.
  - `EventInputBuffer<EventType, Capacity>`: `is_empty()`, `size()`, and a loop over its events (`for (const EventType& event : connections.input)`).
  - `EventOutputBuffer<EventType, Capacity>`: `push(event)` for an event derived from `Event` directly, or `push(header, event)` for a stream event (a `StreamEvent`, see **Events**), which also sets the event's header. Each form is a compile error for the other kind of event, so a stream event can't be pushed without its header, which would leave it with sample number 0 and no error. Example: `connections.output.push(connections.input.header, Spikes<InputStreamInfo>{.channels = crossings})`.
  - A state value's `In` and `Out` read and assign like the value itself (`if (connections.is_stim_on)`, `connections.is_ripple_ongoing = true`).
  - `StreamInfoType::simd_vectors`: the number of channel vectors, i.e. the padded channel count divided by 16 on AVX512 or by 8 on AVX2.
  - No single-channel access: a processor that needs only a few channels gets them from a packer upstream, which copies them into a smaller stream (see **Channel selection** in beyond_prototype.md).
  - Mistakes left to processor tests (see **Processor authors are trusted** under **Processors**):
    - `store` without `set_header` compiles, and the processor seems to output nothing, since the count stays 0 (see **`Out` clears an output buffer** under **pipeline.cpp**), so the whole chain downstream stays silent. Only sample outputs have this case: an event is pushed whole in one call and a state value is assigned. Rejected: `set_header` returning the only object that has `store` (`auto sample = connections.output.set_header(connections.input.header); sample.store(simd_vector_index, values);`), one more line per sample processor and one more type for authors.
    - A processor that calls `set_header` but doesn't `store` every vector (e.g. an early `return` between them) leaves the skipped channels holding an older sample's values under the new header, and downstream reads them as real data. Example: artifact blanking stores zeros into the stimulated vectors but nothing into the others, assuming they stay "unchanged". A habit avoids it at no cost: each loop iteration computes one `result`, starting from the input where that makes sense, and ends with one `store`. Rejected guards: a test build where `set_header` fills the output with NaN; `set_header` always writing zeros first; counting `store` calls and checking them after `process()`; an all-at-once `set_header` that takes a function and calls it for every vector itself (`connections.output.set_header(connections.input.header, [&](int simd_vector_index) { return ...; })`), so the processor no longer writes its own loop.

### Events
A second, lightweight connection type for sparse outputs such as spikes, ripple onsets and decoder results. Within one core they are handed over in event buffers. Between cores they go through event rings (see **Event rings** under **Rings**).
- **One type per kind of event**: a plain fixed-size struct derived from the empty `struct Event {};`, e.g. a timer's `struct ScheduledEvent : Event { u32 count; };`. An event from a stream also has its sample's header as its first field (see below), e.g. `template <typename StreamInfoType> struct Spikes : Event { SampleHeader header{}; ChannelMask<StreamInfoType> channels; };`. The event type is part of the connection's type, so the compiler rejects connecting ripples to a processor that expects spikes. Processors that accept any kind of event (TTL output, recorder, logger) are templates over the event type, constrained to `std::derived_from<Event>`; the generator fills in the event type and the capacity from the connection (e.g. `EventLogger<Spikes<RippleRaw>, 1>`, see **Capacity** below).
  - The struct is itself called an event, not a record. In neuroscience, record and recording mean recorded signal, so a bare "record" didn't exclude a sample, and a recorder would have recorded records. Rejected: `Message`, since logging already sends numbered messages (see **Logging**); `EventData`, verbose everywhere (`StreamEventData`, `EventDataType`); keeping the names `EventRecord`, `StreamEventRecord` and `Record`, which keep the ambiguity.
  - Rejected: taking the base type, `EventInputBuffer<Event, Capacity>`. An `EventBuffer<Spikes<RippleRaw>, Capacity>` buffer is not an `EventBuffer<Event, Capacity>` buffer: the events have different sizes, and copying a `Spikes` event into an `Event` keeps none of its fields. The processor needs the concrete type to read the fields (e.g. through reflection).
  - `Event` holds no sample number, because not every event comes from a stream: a timer such as EventGenerator has no sample to point to, and a made-up number in a field shared by all events would mean something different for each producer.
  - `Event` exists although empty, so that a field every event needs can be added later in one place instead of in every event type, including those in labs' extensions.
  - Rejected: one type for all events (e.g. sample, channel, value), whose fields would mean different things for different producers, so a consumer could misread them without an error.
  - No virtual functions: they would add a hidden 8 B pointer to every event, and an event holding a pointer can't be copied byte for byte into a ring, shared memory or a file.
- **An event from a stream carries the whole header** of the sample it came from (see **Buffers**): the sample number for matching (the correctness check in test_suite.md, a spike-count binner), the arrival time for the latency log once events cross cores, and the device timestamp to find the event in the vendor's recording. It costs 32 B per event, and events are rare (most passes have none). Rejected: only the sample number (8 B), which would leave the latency log without an arrival time after a ring hop.
  - The header is the event's first field, `SampleHeader header{};` (decided by the user on 18 November 2026), and `StreamEvent` is the concept that asks for it: a type derived from `Event` whose field `header` is a `SampleHeader` and comes first. A processor that needs the header (e.g. a spike-count binner, which builds its output's header from its spikes' headers) requires `StreamEvent`, so connecting timer events to it is a compile error; a processor that takes any event (EventLogger, TTL output) requires `std::derived_from<Event>`. A header that is misspelled or not first makes a type that is no `StreamEvent`, so its producer's `push` with a header doesn't compile.
  - The producer passes its input's header to `push` (see **Operations a processor uses** under **Buffers**), never in the event's braces, so no stream event can be pushed without one. The field's default lets the braces name only the event's own fields, with no compiler reporting the header as left out.
  - Not kept: the header in a shared base, `struct StreamEvent : Event { SampleHeader header; };`, the first form, which defined it once. An initialiser by name leaves a base out, which GCC reports at every push, and whatever reads an event's fields (see **No serialization code** below) had to fetch the header through the base, apart from the other fields. A field was rejected at first, since every author repeats it and processors could find it only by its name; the concept answers that by checking its name, its type and its place. The change left every pipeline's machine code as it was.
  - Rejected: one header per event buffer, which is wrong when one pass's events come from different samples (e.g. a processor that outputs a spike a few samples late, after finding its peak, or one that merges two spike streams).
- **No serialization code**: whatever saves or shows events (recorder, EventLogger, UI) reads their fields through C++26 reflection, so an author only declares the struct.
- **An event's fields as a list**: `EVENT_FIELDS<EventType>`, from `src/core/event_fields.cpp`, is a plain list of an event's fields, each with its name, type, place, size and count. It is the one place that holds reflection: whatever writes or shows an event goes through the list. A field may be a number (an integer of any width, a float, a double, a bool), an enum (listed as the integer it is stored in), a `std::array` of numbers (listed with its count), a channel mask (listed as one, with its stream's channel count, since its words alone wouldn't say what they are), or a struct of these, whose fields are listed one by one under a dotted name (`header.sample_number`). Any other type is a compile error that names the field.
  - Clang, which the lint, the formatter and the editor are, can't read reflection, so for it the list is empty; those lines, about 60, are the only ones the lint doesn't check.
  - Asked by the user on 18 November 2026: whether Recorder needs reflection at all, where it could ask of each event what it is and write that. Left as it is by the user for now. Claude's answer: it doesn't need it. The other way is a branch per field that Recorder knows by name, as EventLogger has for the two it shows (a channel mask, a count), and a refusal of any event with a field it doesn't know, so that none is dropped unnoticed. It works with any compiler and the lint reads all of it. Its price comes with each new field or event type: Recorder is edited before it can be recorded, and an extension's own event type can't be, since Recorder can't know it. With reflection nobody writes anything for a new event, an extension's included, and the names in the file are the struct's own.
- **The prototype's SpikeDetector** emits, on each sample where channels cross the threshold, one `Spikes` event with their mask (see **Detection events are channel masks**), without waiting for the peak. The threshold is in µV and its sign gives the direction: a channel crosses a negative threshold when its value goes below it and its previous sample's wasn't (a positive one: above). So a channel fires once per crossing, not on every sample beyond. The first sample only records the state, padding channels never fire, and a NaN never crosses. The reference script for the trigger check in test_suite.md must apply the same rule. Rejected: Falcon 1's positive threshold with an "invert signal" option. Richer spike events come from separate processors later (see **Richer spike events** in beyond_prototype.md).
- **LevelCrossingDetector** emits, on each sample where channels cross a level, one `LevelCrossings` event with their mask (see **Detection events are channel masks**), so a consumer such as Trigger can wait for every channel. After a crossing, that channel ignores its next `post_detection_block` samples (default 2) and takes the sample that ends its block as its previous one, so only a new transition counts. The block is per channel: one block for all channels would hide a channel crossing a sample after another, so Trigger would miss it. Rejected: Falcon 1's one event per sample, naming only the lowest crossing channel, with one block for all channels. Its direction is an option of its own (upward or downward), not the threshold's sign as in SpikeDetector, since it runs on any signal: a test square wave, or an envelope that must drop below a positive level. Otherwise it follows SpikeDetector's rules: the first sample only records the state, padding channels never cross, and a NaN never crosses.
- **Capacity**: an event buffer has room for every event its producer can push in one pass, so nothing is lost even when every channel fires at once, as in a stimulation artifact. Each producer fixes that number at compile time, e.g. 1 for a detector, whose one event holds every channel that fired (see **Detection events are channel masks**). An event ring's reader hands over at most that many per pass (see **Event rings** under **Rings**).
  - The capacity is part of the buffer's type, `EventBuffer<EventType, Capacity>`: the producer's output says it (e.g. `EventOutputBuffer<Spikes<RippleRaw>, 1>`), and `pipeline.cpp` declares the buffer with the same type. A consumer takes `Capacity` as a template parameter too (e.g. `EventLogger<Spikes<RippleRaw>, 1>`), filled in by the generator, since `process()` can't deduce it (see **`process()` signature** under **Processors**). `push` doesn't check the capacity: the producer never pushes more than `Capacity` in one pass.
  - Rejected: the capacity outside the type, with `EventBuffer<EventType>` pointing at storage that `pipeline.cpp` sizes from a `max_events` constant each producer declares. It would keep `Capacity` out of consumers' types, at the cost of a second declaration per buffer in `pipeline.cpp`.
- **Detection events are channel masks**: SpikeDetector's and LevelCrossingDetector's output becomes one event per sample with one bit per channel (a channel mask), saying which channels crossed on that sample. Their per-channel events, each carrying the whole header, rested on events being rare (see **An event from a stream carries the whole header** under **Events**), but test signals, movement and chewing artifacts in freely moving animals, and stimulation artifacts that aren't blanked make every channel fire in the same pass. Measured at 10,000 channels (see **Latency tests for the paper** in test_suite.md): LevelCrossingDetector's 400 KB of `LevelCrossing` events and Trigger's loop over them cost about 7.8 µs, about 0.8 ns per event, more than 7 FirFilters over the same channels (about 7.4 µs) and a third of a 25 µs sample period at 40 kHz; everything else in that pass, the detector's comparisons over all 10,000 channels included, about 0.9 µs. With masks, that pass takes 0.85 µs in total, and the whole graph with its 7 FirFilters 7.71 µs instead of 15.74 µs (medians).
  - A mask's cost doesn't depend on how many channels fire: the detector stores the 16-bit comparison masks it already computes, Trigger ORs them in with SIMD and compares with all ones, and per-tetrode logic is an AND with a group mask. The header is stored once, which is right since the event is one sample's; a late peak or two merged streams push separate events. A producer pushes about 1 event per pass, so capacity and ring slots stay small. Bit c is channel c on both AVX2 and AVX512.
  - Events without one entry per channel (`TriggerEvent`, a timer's events, decoder results) stay as they are, and so do PCIeParallelOutput and LatencyBenchmark, which read only `TriggerEvent` or the header. EventLogger walks the set bits, and whatever counts spikes counts set bits, not events.
  - No consumer on the hot path needs a per-channel value straight from the detector. A detector fires on the sample where a channel crosses its threshold, so the value there is the threshold, by construction. Trigger and burst detection need only which channels crossed (counts come from the mask). The values worth having come later and from the filtered stream: a spike's peak, 0.1–0.3 ms after the crossing; a tetrode's marks for clusterless decoding, the main use case; its waveform. Each comes as a sparse event from its own processor or an optional output of SpikeDetector (see **Richer spike events** in beyond_prototype.md).
  - Its costs, and how far each is offset:
    - The event grows with the channel count even for one crossing (at 32 channels, 32 B + 4 B, padded to 40 B: the size of one per-channel event; at 384, 32 B + 48 B, two; at 10,000, about 32). Offset: a mask is 1 bit per channel, 1/32 of the float32 sample it comes from, so wherever the sample travels (a ring, a recording) the mask adds at most 3%. Remains: when few channels fire per sample, a list is smaller; e.g. 10,000 channels firing at 10 Hz each give about 2.5 crossings per sample at 40 kHz, about 100 B as per-channel events but 1.3 KB as a mask, which a recorder off the hot path can turn into a list before writing.
    - The producer stores its whole mask on every pass with a crossing, even for one channel: at 10,000 channels about 625 small stores, tens of ns (an estimate), against about 1 ns for one per-channel event. That is the price of a worst case that no longer depends on how many channels fire.
    - A consumer that needs channel numbers walks the set bits. Offset: an iterator hides it (`for (u32 channel : spikes.channels)`), and consumers that only combine channels (Trigger, per-tetrode rules) use SIMD on the mask instead.
    - Whatever saves or shows events writes each field by its type through reflection (see **No serialization code**), which turns a mask, an array of 64-bit words, into meaningless numbers. Offset: one rule for the mask type, in one place: a binary recording keeps the raw bits, the same size in every event, and a text log or the UI shows the channel numbers of the set bits.
    - A mask carries no value per channel (e.g. the amplitude at the crossing). Not offset: such values come in sparse events of their own, so two event shapes coexist and an author picks one.
  - Rejected:
    - One header per sample and a list of channel numbers (4 B each instead of 40 B). A single crossing stays small and the memory is 10 times smaller, but the push and Trigger's pass stay one per channel (about 0.5 ns each even within L1), and one pass can hold several samples' events, so the buffer would need a header per run of same-sample events.
    - Per-channel events as before, plus an aggregate output on each detector (a mask or a count, on an optional connection) for Trigger, the per-channel events going only to consumers off the hot path. Every detector would gain an aggregate output, which is the mask again, and a per-channel consumer on the same core would still pay.
    - A smaller per-channel event (e.g. the sample number instead of the whole header): about half the memory, the same loops, and the header is kept whole for the arrival time.
  - The mask type, `ChannelMask<StreamInfoType>`, by who uses it:
    - A producer (a detector) writes one channel vector's bits at a time, as `store` writes a sample's: `set_vector(simd_vector_index, {.bits = crossing_mask})`, 16 bits per vector on AVX512, 8 on AVX2. The bits come in a struct of their own, `ChannelVectorBits`, so the two arguments can't be swapped. The type keeps the padding bits 0, so a padding channel can never fire, and `is_empty()` tells whether any bit is set, so the producer pushes only an event with a crossing.
    - A combiner (Trigger, per-tetrode rules) uses whole-mask operations: `|=`, `&`, `==`, and `every_channel()`, the mask with every real channel set.
    - A lister (EventLogger, a recorder, a peak or mark processor) iterates the channel numbers of the set bits (`for (u32 channel : mask)`), counts them (`count()`), or tests one channel (`has_channel(channel)`).
    - Rejected: the mask as raw words that processors handle themselves, so every author would write bit tricks, the instruction set's width would leak into every processor, nothing would keep the padding bits 0, and reflection couldn't tell a mask from any other array; a fourth kind of connection for masks, which generic consumers (EventLogger, recorder, LatencyBenchmark) couldn't take; a bit stream with a value on every sample, which costs a write and a ring transfer on every pass, where an event skips the passes on which nothing crossed.
  - A producer builds its mask, then pushes the event with `push(header, event)`, like any other event. The push copies the event, 4 B of mask at 32 channels and 1.25 KB at 10,000, a few ns even then. Writing the bits straight into the event buffer instead is in **Event rings between cores** in beyond_prototype.md.
  - The event types are named in the plural, `Spikes` and `LevelCrossings`, since one event holds every crossing of one sample, and each type's comment says it holds a mask. "A spike" keeps meaning one spike, as in the sparse per-spike events to come (e.g. `GroupSpike`, see **Richer spike events** in beyond_prototype.md). Rejected: a mask suffix (`SpikeMask`), which names how the event is built instead of what it means, and repeats "mask" in `SpikeMask.channels`; the singular names, which read as one spike and clash with `GroupSpike`.
  - Capacity follows the existing rule (see **Capacity** under **Events**): the most events a producer can push in one pass, so 1 for a detector, which reports only the current sample. A late peak goes to an output of its own (see **Richer spike events** in beyond_prototype.md), so it doesn't raise it.
  - When an author makes an event a mask and when a sparse event is for the documentation (see **Documentation** in beyond_prototype.md); events about groups of channels are in **Group masks** in beyond_prototype.md.

### Rings
- A ring is inserted only where a connection crosses from one core to another: one ring per connection, in either direction. Two cores can have several rings between them. Each ring counts toward the cache of both the writer's and the reader's core.
- **Size**: an adjustable number of samples, always a power of 2.
- **One writer, one reader (SPSC)**, the simplest version: the prototype's only ring has one writer and one reader, and SPSC shares the fewest cache lines between the two cores. The old TODO list planned an SPSC design that minimizes cache misses. One writer with many readers is in beyond_prototype.md (**Rings with many readers**).
- **The header** (see **Buffers**) **sits in the slot**, in front of the samples: the simplest layout. Since samples fill whole cache lines, the header adds one cache line per sample (3 instead of 2 at 32 channels). Headers in a separate array would save half a line per sample, a later optimisation (see **Ring header layout** in beyond_prototype.md).
- **A full data ring is a failure, but the run goes on.** The writer never waits, and there is no backpressure: a sample that doesn't fit is written into the ring's spare storage, dropped and counted, and the count enters the lost-sample count of the samples the ring publishes after it (see **Each sample has a header** under **Buffers**). Realtime cores never print, so the main thread checks every ring each time it wakes (every 100 ms) and prints a console warning with the ring's name and how many samples it dropped. The user must change the graph or the hardware. Every ring registers itself when it is built, so none can be left out of the warnings. Rejected: stopping the run at the first dropped sample.
  - **The same for a ring to a slow reader**, Recorder included: a gap in a recording is accepted, since its warning shows on the console during the run. The file shows a gap in a sample slot, by the sample numbers and the lost-sample count of its records (see **Recorder**); a dropped event leaves no trace in the file (see **Event rings**), only in the warning and the log. Not chosen: a full ring to a recorder ending the run, for every reader or as a choice per reader, since a slow disk would then end an experiment.
- **Passing a ring to `process()`**: `In` and `Out` take a ring as they take a buffer, and do its work while the `Connections` argument is built before the call and destroyed after it (see **`Out` clears an output buffer** under **pipeline.cpp**).
  - **As an output**, a sample ring hands the producer its next free slot, or its spare storage when it is full, so the producer writes straight into the ring; when the call returns, the sample is published, if the producer wrote one. So it leaves right after its producer, not at the end of the pass.
  - **As an input**, the ring's next sample is fetched when the first processor that reads it is called, once per pass: every processor that reads the ring on that pass gets the same sample, and a ring read late in the loop still catches what arrived earlier in the same pass. The input points at the slot, or is left empty. The slot handed out on one pass is freed on the next pass's fetch, since the processors read it until then. Passes are told apart by a counter that `next_pass()` advances, so in a loop of another form a ring given as an input ends the run with an error.
  - **A buffer that feeds rings**, for an output read on its own core and on others, or on several other cores: `pipeline.cpp` declares the buffer with those rings (see **A connection that crosses cores is passed like a buffer** under **pipeline.cpp**), the processors on its core read it as any buffer, and when its producer's call returns, the sample is copied into each ring. One copy per reading core is what an extra consumer on another core costs the producer's core. A ring takes one feeding buffer; a second ends the run at start.
  - **A `process()` that fails hands nothing over**: `fail()` marks its thread before it throws, and the outputs destroyed while the exception unwinds neither publish nor copy, so no half-written sample reaches another core. An exception that `fail()` didn't throw has no such mark.
  - **Cost**: when the `process()` call is inlined, the same instructions as the calls written out, since which ring an output has, if any, is a compile-time fact. When it isn't, every sample or event output costs a load and a test after the call, also in a chain that touches no ring (see **Inlining every `process()`** in beyond_prototype.md). A ring's reading buffer lives in the ring, not in its core's function. To measure.
  - Not done yet: the Ripple Neuromed extension's two pipelines still call `next_slot`, `publish` and `read` themselves, which keeps working; converting them needs the hardware to check the result. Once they are converted, those calls stop being public.
- **Event rings**: events cross cores through an `EventRing<EventType, Capacity, slot_count>`, one writer core and one reader core as for samples, passed to `process()` in the same way. As an output, the ring hands the producer a buffer of its own to push into, and when the call returns the pushed events are copied into the ring. As an input, a pass's first reader copies out as many waiting events as `Capacity` (see **Capacity** under **Events**); the others wait in the ring for the next pass. An event buffer can feed event rings as a sample buffer feeds sample rings. A slot is free again as soon as its event has been read. A full ring drops the event, counts it, and the main thread warns, as for samples; a dropped event leaves no trace in the events after it. Copies, since an event buffer holds its events inside itself; reading and writing without a copy are in **Event rings between cores** in beyond_prototype.md.
- **Hop cost**: about 20 ns for the write position within a CCD and about 80 ns across CCDs, plus pulling the slot itself, header included (3 cache lines at 32 float32 channels, 5 at 64, 25 at 384; to be measured). Keep connected cores on one CCD.
- **A stuck processor does not stall other cores.** In the example under **Per-core loop**, p3 on core 2 stops making progress (a long computation, a bug, a CPU stall):
  - Core 1 keeps running. Its ring reader for p3 → p4 leaves its buffer empty, so p4, p5 and p6 produce no output, while p1 and p2 keep processing new samples.
  - The ring p2 → p3 fills up, and a full ring is a failure. A 64-sample ring at 30 kHz is full after 2.1 ms.
  - When p3 recovers, the waiting samples reach p3 and then p4 one per pass, so p4 to p6 process late samples until p3 has caught up. Catching up requires p3 to process samples faster than they arrive.

### Input processors
Each input processor runs alone on its own spinning core and hands samples to the processing cores through a ring, writing them straight into the ring's slots (see **pipeline.cpp**). That costs one core-to-core hop per sample, but the socket's system calls and kernel copies stay off the processing cores, so their caches stay warm. This is a placement for the first implementation, not an engine rule: with kernel bypass (task A.6 in beyond_prototype.md), an input can later move into a processing core's loop.
- RippleNeuromedInput in the round-trip graph, open: on a core of its own, the 32-slot ring to the processing core dropped samples (38 in one run) while the network card batched its interrupts (see **How to measure the round trip** under **Latency measurement** in test_suite.md). With batching off, a 4-slot ring usually drops nothing but drops a few samples while other work runs on the machine; 8 slots drop fewer, 16 almost none, and with every OS core busy (the lint running) even 64 slots drop. With xipplib's thread alone at SCHED_FIFO 40 (`chrt -f -p 40 <tid>`, below the network card's interrupt threads at 50), the busy OS cores caused no drops at first; over ten minutes of repeated lint runs, a 4-slot ring dropped 1 sample, and the drop wasn't reproduced since: further lint runs and stress tools on the OS cores dropped nothing with 4 slots, and the oscilloscope showed no change in the round trip. So normal-priority work on the OS cores no longer affects the graph; threads above FIFO 40 there (interrupt threads, kernel threads such as `migration`) still preempt xipplib's thread. The one drop's cause is unknown: a delay before the input or a stall of the processing core. So other work on the OS cores delays xipplib's thread, which then hands over its backlog at once, and the input writes that burst into the ring faster than the processing core reads it. Such a burst is also late by as long as the thread waited. So RippleNeuromedInput's constructor runs xipplib's setup with its own thread at SCHED_FIFO 40 and switches back after: a thread started with default attributes, as `std::thread` does, inherits its creator's scheduling, so xipplib's thread starts at FIFO 40, and threads the main thread starts don't. It then reports whether it found that thread at FIFO 40 (`ripple_neuromed_reader/utils.cpp`). The engine has no general way to give a library's thread a realtime priority. Planned: the input reads the Summit's UDP datagrams itself instead of through xipplib, which removes that thread and `utils.cpp`. Run in the processing core's loop instead, with no ring, nothing was detected. That cause isn't known yet. An input that makes no socket call itself could share a processing core in principle: xipplib's own thread receives the packets, and `xl_cont_raw` returns at once when nothing is new.
- **An input reports the samples lost before it** (e.g. a lost UDP packet, seen as a jump in the device's own numbering), since only the lost-sample count would show them (see **Each sample has a header** under **Buffers**) and the user must fix the setup (see **No lost packets** under **Principles**). It warns at each gap, with how many samples were lost and the sample after the gap, and again with the total when the run ends (see **Logging**). RippleNeuromedInput also warns once each time no sample has arrived for `no_data_warning_milliseconds` (100 ms by default), e.g. while the network cable is out; the samples lost meanwhile are warned about when data comes back.

### Waiting for data
- **Realtime cores spin**, so their loops also run passes when nothing has arrived. Lowest latency (one cache-line transfer), caches stay warm, and the core runs at 100% (heat).
- **Non-realtime cores** (recorder, viewer) may block: the OS wakes the thread (µs), and deep idle (C6) can flush L1/L2. A blocking core runs no empty passes.
  - The prototype's rings have no blocking read. `main` declares such a core with `.is_realtime = false` in its list of cores, and `next_pass()` then sleeps 1 ms after a pass that brought the core nothing through a ring. The wait is the loop's, never a processor's, so several processors can share such a core. Its rings must hold what arrives meanwhile.
- The waiting strategy only decides what a core does when none of its processors has new input. It does not change the delay between chains on one core when both have work in the same pass.
- Falcon 1's yielding and sleeping (`falcon/portpolicy.hpp`) are dropped. On an isolated core with one thread, yielding is just spinning plus system calls, and sleeping backs off to 1 ms (30 sample periods at 30 kHz).

### Start, stop and config
- **One run per engine program.** Start means the UI spawns the engine program. The program builds every processor (see **Start barrier** under **Per-core loop**): if a constructor failed, or a core's thread couldn't be started, it logs the error and exits; otherwise it runs the loops. Stop is one signal for the whole graph, never per processor: the loops end, the destructors release the processors' resources, and the program exits. So every run builds its processors from scratch.
  - The stop signals are SIGINT (Ctrl+C) and SIGTERM. Every thread blocks them from the start, and the main thread takes them with `sigtimedwait` and clears `is_pipeline_running`. Otherwise the kernel could deliver a signal to any thread, including a realtime core's, and interrupt its loop.
- A config change needs a new engine program anyway (see **Every option is a compile-time constant** under **Processors**).
- An engine program that stays alive between runs is in beyond_prototype.md (**Engine states**).
- **Each run writes into a directory of its own**, `<the program's folder>/runs/<run name>_<date>_<time>/`: the log file (see **The log file** under **Logging**) and every file an output processor writes (e.g. LatencyBenchmark's CSV). The engine creates it before any processor is built and never reuses one. If it can't, the graph doesn't start. It lies beside the program, and the program lies at the top of its pipeline's directory (see **Every pipeline has a directory of its own** in generator.md), so each pipeline owns its runs wherever its directory lies, and the engine needs to know only where its own program is (decided by the user on 21 November 2026, in code).
  - **The run's name is given when the program is started**, as `--run-name <name>` on its command line, and holds only letters, digits, `_` and `-`. It is the run's and not the pipeline's, so that experimenters name runs of one pipeline differently without compiling again, e.g. `memory_impairment/runs/hippocampus_stimulation_<date>_<time>/` and `memory_impairment/runs/cortex_stimulation_<date>_<time>/`. A run started without a name gets its date and time alone. `pipeline.cpp` holds no name, and a pipeline's name isn't the engine's business (see **A pipeline's description is a marked comment block** in generator.md). The spelling `--run-name` is Claude's, the user's being "`--run-prefix` or similar".
  - **`main()` hands its arguments to `run_on_cores`**, `run_on_cores(argument_count, arguments, {...})`, so that the engine can take more from the command line later (decided by the user on 21 November 2026). Anything on it but `--run-name <name>` keeps the run from starting.
  - Agreed: the pipeline's name is the graph's name, which the user enters in the UI. The generator writes it into `pipeline.cpp`, and a hand-written `pipeline.cpp` writes it itself (e.g. `run_on_cores("round_trip_latency", {…})`). It becomes part of a directory's name, so the UI accepts only characters a file name can hold, and the engine checks it again at start.
  - Agreed: a processor gets the directory from an engine function, `run_directory()`, which its constructor calls to build its files' paths. The engine creates the directory before any core's thread starts, so it is valid in every constructor and destructor. A processor's file option is a file name, not a path (e.g. LatencyBenchmark's `file_name`), checked at compile time (`is_file_name()`: not empty, `.` or `..`, and without a `/`), so a run's files can't land anywhere else.
  - `~` is the current user's home, also under `sudo`, which the engine needs for now (the PCIe card's I/O port access, xipplib's thread at SCHED_FIFO). Under `sudo`, the engine finds the user who ran it from `SUDO_USER` and makes the run's directory and files theirs; otherwise `~` and the files would be root's. Once the program holds only the privileges it needs and runs as the user, this is no longer needed (see **Privileges** in beyond_prototype.md).
### Logging
- **Processors report through `warn()` and `log()`**: one call form, `warn(name, "format", values…)`, and one mechanism (see **The call**, **In the loop** and **The central logger** below). In the loop, either costs a branch, plus a cold call only when it is raised, which copies plain values; the main thread formats the text. Every line, from setup, the run or teardown, goes through one central logger of the engine's, which writes it to the console and to a log file.
  - A condition the run survives (a ring's dropped samples, samples lost before an input, an input that stopped, a filter that restarted) is a warning.
  - **A warning shows during the run, as soon as it happens**, since the user must fix the setup while the experiment can still be saved. The main thread polls every warning, as it does every ring (every 100 ms, see **A full data ring is a failure** under **Rings**), and prints each change. What changed after its last poll is reported when the run ends.
  - **Every warning is serious.** There are no levels among warnings, and no warning may be hidden or left for later. A `log()` line is not a warning; in the loop, `log()` is advised only for processors on non-realtime cores.
  - What must be kept for each occurrence (triggers, latency rows) and statistics (e.g. spike rates) are data: events on a stream of their own, to EventLogger or the recorder, or rows kept in memory until the loop ends, as LatencyBenchmark keeps them.
- An error is an exception and ends the run (see **An error is an exception** under **Processors**). There is no `error()` call.
- Rejected: formatting text in the loop, and a library logger such as Quill (see **Log ring** in beyond_prototype.md).
- **The call**: `warn(name, "lost {} samples before Falcon, at sample {}", gap, sample_number)`. The processor's name comes first (see **Processor names** below), then the format string, then as many arguments as the processor's author needs, `std::format` style, with the format string checked at compile time. Each call counts as one occurrence; how much it stands for (e.g. a gap of 3 samples) and the sample number, when it matters, are arguments.
  - It costs the loop only a branch and a call. The work is in a function of the engine's marked cold and never inlined (`[[gnu::cold, gnu::noinline]]`), so it doesn't count toward the compiler's choice to inline `process()` (see **Inlining every `process()`** in beyond_prototype.md). Its body is cold but still runs on the realtime core, in the pass that raised it, so it may not allocate, lock, make system calls or throw.
  - It takes only values (the format string and the arguments), never a pointer into the processor. A pointer handed to code the compiler can't see into makes it treat the whole processor as reachable from elsewhere. Then, around every call it can't see into (e.g. `xl_cont_raw`, a system call), it writes the processor's state back to memory and reloads it afterwards, instead of keeping it in registers. Reasoned from how clang works, the compiler then; to check in GCC's disassembly. The same holds for a warning object that a processor declares as a member, since the main thread must be given its address.
  - Arguments are plain values only (numbers, enums, channel masks) or text (`std::string_view`, `const char*`), checked at compile time. `warn()` copies them into the record, text included, character by character, and the main thread formats the line; no pointer is kept that could dangle by then. Text is needed for lines that only exist at run time, e.g. a file's path or an exception's message. A record holds 256 bytes of arguments, a limit checked at compile time, since a record has a fixed size; text that doesn't fit is cut and ends in `...`. Rejected: string literals only, which can't carry such lines. Rejected: any type with a formatter, formatted on the realtime core (about a microsecond on that pass) for arguments a warning doesn't need.
  - **`log()` beside `warn()`**: both are thin wrappers around one mechanism, so there is one transport, throttle and set of tests, and one call form for authors; the message type lets the console and later the UI show each kind of message apart. `log()` may run in the loop too, through its core's ring and throttle like `warn()`, at the same cost. It is advised only for processors on non-realtime cores (e.g. a recorder): on a realtime core, a line is usually either a warning (the user must act) or data (an event stream), and other lines only bury the warnings. The throttle keeps logs from filling the ring a core shares with its warnings, except when many kinds are raised at once, which the "ring full" warning reports. The price: levels come back, though every warning is serious, and an author may log what should be a warning.
- **Processor names**: every processor has a name, which the user gives it in the UI, as in Falcon 1. Names are unique within a graph and identical to the processor's variable name in `pipeline.cpp` (e.g. `ripple_neuromed_input`). A line names its processor by that name.
  - Each processor's constructor takes its name, and `pipeline.cpp` writes it out next to the variable (`ripple_neuromed_input{"ripple_neuromed_input"}`). The generator writes both, so the duplication costs nothing there. Rejected: reading the name by reflection, or a per-core "current processor" that the loop sets before each `process()` call; the generator writing the name is simpler.
  - The processor passes its name to `warn()`, which can't read a field of the processor without a pointer into it: `warn(name, "lost {} samples", gap)`. The name is a pointer to static text, a value, so nothing of the processor escapes. Not taken: a base class holding the name, whose own `warn()` would pass it on. Processors have no base class, and it would save only that one argument.
  - The name's type, `ProcessorName`, accepts only string literals (a `consteval` constructor), so the text it points to lives as long as the program, and a pointer into a temporary string can't reach the main thread. It also accepts only what a variable's name can hold (letters, digits and `_`, not starting with a digit), so a name that couldn't be the variable's is a compile error.
  - No two processors may share a name. A processor's `name` member registers its name with the engine when it is built and throws if the name is taken, so the graph doesn't start; it unregisters when the processor is destroyed. This happens at setup and teardown only, never in the loop.
  - Two types, since one can't do both jobs. `ProcessorName` is the value: built from a string literal only, copied freely, what `pipeline.cpp` passes to the constructor and `warn()` takes. `RegisteredName` is the member: built once from a `ProcessorName`, it registers it, can't be copied, and turns into a `ProcessorName` when passed to `warn()`. A single registering type would register again with every copy passed to `warn()`, and find its own name taken. Each processor then has `explicit LevelCrossingDetector(ProcessorName processor_name) : name(processor_name) {}` and `RegisteredName name;`.
  - The compiler makes sure every processor has a name, since the engine never sees processor types:
    - `pipeline.cpp` always passes the name to the constructor, so a processor without a constructor that takes one doesn't compile there.
    - `warn()`'s first parameter is a `ProcessorName`, so a processor without one can't warn.
    - An engine concept requires a member `name` of type `RegisteredName`, and the generator writes `static_assert(Processor<decltype(ripple_neuromed_input)>);` after each declaration. This catches a processor that takes the name but doesn't keep it. A hand-written `pipeline.cpp` may leave these out, and then only the first two hold.
- **In the loop**, a call goes into storage the engine keeps for each core and the main thread reads: a ring of records, and a warning counter for each kind of warning. The engine owns both, so no processor's address is registered, and both outlive the processors, so the last check after the loops end sees everything.
  - The ring carries the first occurrence of each kind in each 100 ms, with its arguments (see **The throttle** below).
  - The warning counters carry how many times each kind happened since its last line, including the occurrences the throttle held back. The main thread reads them every poll, so a warning's final count shows even when its condition stops and no later record comes. A core counts an occurrence only once its record is in the ring, and the main thread reads the warning counters before the ring, so it has read the record of every occurrence it counts.
  - Rejected: the warning counters alone, which would show each line with the last occurrence's arguments instead of the first's.
  - **A kind** of warning is its processor's name plus its format string (two pointers to compare). So two IirFilters raising "restarted after a lost sample" each get their own throttle and their own line.
  - **The throttle** is in `warn()`, on the calling processor's core, since it must act before the push. A line for every occurrence (up to 30,000 a second) would flood the console and the ring and hide the other warnings. A warning counter for each kind of warning on that core counts how many records it pushed in the current interval and how many it held back. Beyond 1 record per kind per 100 ms (the main thread's poll interval), occurrences are only counted. So a flood of one kind can't fill the ring, and no processor writes a throttle of its own. A cap of its own for each kind is in beyond_prototype.md (**A cap per kind of message**). A processor still decides when to call `warn()` at all (e.g. when a condition starts and when it ends).
  - The warning counters take cache only while a warning is raised: one 64 B line per kind raised, since a cache holds only lines a core touches.
  - A full ring drops and counts, and the main thread prints a "warning ring full" warning with how many were dropped, as it does for a data ring. With the throttle, the ring fills only if many kinds are raised at once. Likewise, a core raising more kinds than it has warning counters for is itself reported.
  - The main thread prints one line per kind per poll, with the count from its warning counter. It writes a poll's lines in time order, across kinds and cores.
- **The central logger**: every line, a log or a warning, goes through it, so that all of them are written in one place, in one format, to the console and to a log file. Rejected: `log()` printing directly from a constructor, which leaves nothing that serializes the lines to a file.
  - **Two ways in**, picked by the engine, with one call form. Outside the loop (constructors, destructors, and once the run is stopping), `log()` and `warn()` hand their line to the logger directly, under a lock, since setup and teardown may wait. The loop is the time between its core passing the start barrier and either `is_pipeline_running` being cleared or an exception starting to unwind the core's function, whose destructors are teardown already. A throttle by kind would hurt there: lines with the same format (e.g. one per network card) would be merged. During the loop, `log()` and `warn()` go through their core's ring and throttle, and the main thread hands what it reads to the logger.
  - Setup and teardown lines stay whole. Constructors and destructors run on their cores at the same time, so a line printed in pieces (several `fputs` calls) could be split by another processor's output; `log()` and `warn()` hand each whole line to the logger.
  - **The log file** (see **Log destinations** in falcon1_differences.md): one per run, `falcon.log` in the run's directory (see **Each run writes into a directory of its own** under **Start, stop and config**). The engine opens it before any processor is built, so constructors' lines are in it, and flushes it after each poll, so a crash loses at most the last 100 ms. The console gets the same lines.
  - **A line**: wall-clock time to the microsecond, message type, processor name, text, and the count when the throttle held some back, e.g. `2026-11-14 16:31:39.123456 warning ripple_neuromed_input: lost 3 samples before Falcon, at sample 1234567 (×50)`. On a terminal, the console dims the time, colours the message type (warnings yellow, errors red) and shows each argument in bold, since a pipeline can also run headless, started from the command line. The log file and a redirected console get plain text, and setting `NO_COLOR` turns the styles off.
  - **The time**: the record holds the TSC at the call. At each poll, the main thread reads the TSC and the wall clock together and dates each record back from them, with the TSC frequency measured since the start, as LatencyBenchmark measures it (see **Trigger and outputs**). A record is at most 100 ms old, so a frequency measured over one second already dates it to within about a microsecond. A line from outside the loop is dated when it is written, under the logger's lock, so such lines from several threads come out in time order. A poll's line can still come after a directly written line that happened up to 100 ms later, since those aren't held back for it.
- **Test pipelines**: see **The logging tests** under **Done** in test_suite.md.

### Sample type
Input processors convert every sample to µV. Every processor after the input receives µV in one common floating-point format, float32 in the prototype, and never does math on raw ADC counts. Device-specific details (integer formats, per-channel gains, offsets, units) stay inside the input processor.
- **Load and store helpers**: processors read and write samples as SIMD vectors through the buffer's `load` and `store` helpers, never through raw float pointers, and do their math in float32 registers, except IirFilter, which computes in double (see **IirFilter**). The sample type is part of the stream type, fixed at compile time, so the helpers inline to the instructions one would write by hand: plain aligned loads and stores for float32 (`vmovaps`), since every sample's values start on a cache line; a misaligned buffer, which only an engine bug can produce, crashes on its first load instead of running slower without an error. For float16 they would convert on load and store (`vcvtph2ps`, `vcvtps2ph`), which a hand-written float16 processor on Zen 5 has to do anyway, since Zen 5 has no float16 arithmetic. So switching to float16 later changes only the stream type, not any processor (see **Sample width: float16** in beyond_prototype.md). A processor that needs a trick for one format uses a compile-time branch (`if constexpr`).
- **One format for every continuous stream**, whatever its unit (see **Goal**): voltage streams are in µV, and other streams carry other units, e.g. a phase estimator outputs radians and a spike binner outputs spike counts per bin.
- **Why µV, not V**: floating point has the same relative precision at any magnitude, so precision favours neither unit. µV is chosen because users enter thresholds and read traces in µV.
- **Why floating point, not integers in whole µV**: rounding the raw signal to whole µV would be harmless, since 1 µV is below the noise floor of extracellular recordings (several µV RMS). But after filtering, a frequency band can have an amplitude of only a few µV, so rounding to whole µV becomes a large relative error. Phases (radians) and z-scores are fractions. And every processor would have to round and clamp its output; a processor that forgets to clamp makes the integer overflow without an error.
- **Why float32 between processors, though IirFilter computes in double**: storing a value in float32 rounds it by at most half a step, 6×10⁻⁸ of the value (0.00006 µV at 1 mV), about 3000 times below the finest common ADC step (0.195 µV on Intan amplifiers) and far below the noise. float32's 24 significant bits hold as many as the best acquisition ADCs deliver. Rounding becomes dangerous only where feedback with poles near the unit circle amplifies it, inside an IIR filter, which is why IirFilter computes in double (see **Why double** under **IirFilter**); between processors each output is rounded once, so a chain adds one half-step per processor. Measured: IirFilter's float32 output differs from SciPy's double result by at most that half step, for every design tested (see `src/tests/iir_filter/README.md`). A double pipeline would double every ring's and buffer's bytes and halve the channels per SIMD register, for no gain in accuracy.
- Devices deliver different formats (not yet verified against the vendors' documentation): int16 raw ADC counts (Neuropixels, Blackrock), int32 raw ADC counts holding 24-bit values (Neuralynx raw UDP packets), floating point in µV (Ripple), floating point in volts (TDT). So "raw" is not one integer type, and "float" is not one unit.
- Converting in the input prevents two bugs that give wrong results without an error message:
  - **Mixed gains**: on Neuropixels 1.0 the IMRO table sets each channel's gain, so the same raw count means a different voltage on different channels and on different probes. Any processor that combines channels (common average reference, bipolar referencing, a decoder comparing spike amplitudes across channels) would compute wrong values from raw counts.
  - **Headroom**: NP1 samples are 10-bit values stored in int16 (−512 to 511), while Blackrock samples use the full int16 range. Integer math that has room on NP1 data overflows on Blackrock data.
- Cost: the ring right after the input (every graph has one, see **Input processors**) carries floats instead of int16. With float32, that is 4 cache lines per sample instead of 2 at 64 channels, and 125 instead of 63 at 2000 channels. The conversion itself is about 3 AVX512 instructions per 16 channels (widen to 32-bit, convert to float, multiply by the per-channel scale).

### Rates
- The sample rate comes from the input processor, and the rest of the pipeline follows it. Nothing assumes 30 kHz: Neuralynx samples at 32 kHz, TDT at 24414.0625 Hz.
- **A `double` in Hz** (`StreamInfo<32, 30000.0, float>`, see **Stream type** under **Processors**), since an `int` can't hold TDT's rate: rounded to 24414 Hz, every cutoff and duration would shift by 0.0003%, and the input's rate check below would need a tolerance. `pipeline.cpp` writes `30000.0`, not `30000`: C++ doesn't convert an `int` argument to a `double` template parameter (checked on GCC 16.2: `30000` there is a compile error).
- **Compile-time constant**, like the channel count. The UI and the generator infer each stream's rate while the user designs the graph, including the lower rate after a decimator, and `pipeline.cpp` hands it to the processors. In the prototype's hand-written `pipeline.cpp`, we write it in ourselves.
- Processors use the rate to turn the user's Hz and ms into per-sample values: filter coefficients, and durations as sample counts (refractory period, decoder time bins). Without it, the same graph on other hardware would shift every cutoff and duration without an error: a 300 Hz high-pass designed for 30 kHz sits at 320 Hz on 32 kHz data, and 30 samples are 1 ms at 30 kHz but 0.94 ms at 32 kHz.
- At start, the input processor checks that the device really runs at the compiled rate. If it doesn't, its constructor throws and the graph doesn't start (see **An error is an exception** under **Processors**).
- Lower rates inside a graph come from processors that output only every N samples (see **Processors**).

### IirFilter
IirFilter, the prototype's filter, follows Falcon 1's spike filter: an IIR filter, a cascade of second-order (biquad) sections with a delay of a few samples, whose coefficients are designed offline. Other filter kinds are processors of their own (see **FirFilter**, and **FIR filter** in beyond_prototype.md). The first set is Falcon 1's 4th-order Bessel band-pass, 300–6000 Hz at 30 kHz, as two sections (Bessel has the flattest delay of the IIR families, so it distorts spike shapes least). The `.highpass`/`.lowpass` options in this spec's examples are illustrative.
- **Coefficients come from a coefficients file, written into `pipeline.cpp` by the generator** as an option: `IirFilterOptions<SectionCount>{.design_rate, .gain, .sections = {{.b0, .b1, .b2, .a1, .a2}, …}}`, named since options are never positional, with `a0` divided out. The section count is the array's size, so it sets the filter's state size like any compile-time constant (see **A file option is only its path** under **Processors**). Any count works the same way: Falcon 1's biquad files have 2 to 12 sections (12 on 32 channels: about 200 AVX512 fused multiply-adds and 6 KB of state per sample). The file's header names its kind, `# type = iir`. For the prototype, we copy the Bessel file's coefficients into `pipeline.cpp` by hand.
- **The sampling rate is checked at compile time**: a coefficients file states the rate it was designed for in a machine-readable header line (`# sampling_rate = 30000`), the generator copies it in as `.design_rate`, and IirFilter rejects a mismatch with the stream's rate. Falcon 1's files stated it only in their free-text description, so a 30 kHz file on 32 kHz data shifted both cutoffs without an error (see **Rates**).
- **An unstable section is a compile error**: both its poles must lie inside the unit circle. A mistyped coefficient usually breaks this, and an unstable filter's output grows without bound. A NaN or infinite `a1` or `a2` fails it too.
- **Transposed Direct Form II, computed in double**, with fused multiply-adds. IirFilter widens each loaded float32 channel vector to two double vectors, runs them through the sections and narrows the result back before storing it, so samples between processors stay float32 (see **Sample type**). The coefficients are double, and each channel has two doubles of state (`z1`, `z2`) per section. The file's gain is folded into the first section's `b` coefficients at compile time. Direct Form II, the other structure with two values of state per section, is more fragile: its state holds the input multiplied by the poles' gain, which is large for low cutoffs.
  - **Why double**: a section's cutoff is encoded in how far `a1` and `a2` sit from −2 and 1 (1 + a1 + a2 ≈ (2π × cutoff ÷ rate)²), and float32 resolves the coefficients, and each sample's update of the state, only to about 6×10⁻⁸. At 30 kHz, 1 + a1 + a2 is about 4×10⁻³ at 300 Hz (the spike band: ample margin), 3×10⁻⁶ at 8 Hz (theta: cutoffs off by up to 2%, with the rounding noise inside the band) and 4×10⁻⁸ at 1 Hz (below float32's resolution: a different filter, possibly unstable). Double resolves about 10⁻¹⁶, so even a 0.1 Hz cutoff at 30 kHz keeps six digits to spare: any coefficients file runs as designed, and no one has to judge whether float32 could hold it.
  - Cost: an AVX512 register holds 8 doubles instead of 16 floats, so there are twice as many vector operations, plus the conversions: a few ns per sample at 32 channels and 2 sections (an estimate, to be measured), less than one ring hop (see **Hop cost** under **Rings**). Using float32 where it provably suffices: see **IirFilter in float32 when proven safe** in beyond_prototype.md.
- **It starts in steady state**: on the first sample, each channel's state is set as if that value had always been there, so the output starts at its steady value (0 for a band-pass). Starting from zero, a DC offset would give every channel a start-up transient that SpikeDetector reads as spikes on all channels at once. The reference script for the trigger check in test_suite.md must start the same way: SciPy's `sosfilt`, started with `sosfilt_zi` scaled by each channel's first value, runs the same sections in the same Transposed Direct Form II, so its start matches exactly. `lfilter_zi` would not: it treats the cascade as one (b, a) polynomial pair.
- **It restarts after a loss**: when a sample's lost-sample count (see **Each sample has a header** under **Buffers**) differs from the previous sample's, IirFilter starts again in steady state from that sample, as on its first. Running straight across the gap, it would turn the jump in the signal into a transient: measured with a 4-slot ring on a busy machine, ring drops of up to 1748 samples made the filter comparison pipeline's filtered branch count 7 to 13 spikes per second instead of 6, while its unfiltered branch kept its 17. With the restart, the same test, dropping about 13,700 samples over 47 s, gave no false spikes and lost one spike to a gap. A restart loses nothing more, since the missing samples are gone anyway. Cost: one comparison per sample. Each restart is a warning, with how many samples were lost and the sample it restarted from, so the user sees that the filter, not only the input, met the gap. Test: unplugging and replugging the network cable to the Ripple system while a graph runs, which the input and every filter after it should each report.
- Rejected for now as the spike filter: FIR, whose delay is half its length (about 1.7 ms for the roughly 100 taps a 300 Hz cutoff at 30 kHz needs; see **FirFilter**).

### FirFilter
An FIR filter on every channel: each output is a weighted sum of the channel's last N inputs, so for the usual symmetric taps its delay is half its length. In the prototype it serves the FIR chain latency pipeline (see **Latency tests for the paper** in test_suite.md).
- **Taps as an option**: `FirFilterOptions<TapCount>{.design_rate, .taps = {…}}`, where `taps[0]` weighs the newest input. As for IirFilter, the tap count sets the state size like any compile-time constant, and `.design_rate` must equal the stream's rate. A NaN or infinite tap is a compile error: every output would be NaN, which no detector reads as a crossing.
- **Computed in double**, as IirFilter, so no one has to judge whether float32 holds a given set of taps. Each input is widened once and kept in double: each channel's state is its last N inputs in double (101 taps at 384 channels: 310 KB, beyond L1). Float32 is for later (see **FIR filter** in beyond_prototype.md).
- **It starts in steady state and restarts after a loss**, on the same rule as IirFilter: every slot of the history is filled with that sample, so the output starts at the value a constant input gives.

### RippleDetector
Detects ripples in a stream already filtered to the ripple band and emits a `Ripple` event for each. It follows Falcon 1's (see **RippleDetector** under **Processors to port** in falcon1_differences.md) except where an entry below says otherwise.
- **The envelope is the mean square**: each sample is reduced to one value, the mean over every channel of its squared value. It estimates the ripple envelope and is left unsmoothed, so a detection waits for no filter, at the price of false detections from single outliers. Falcon 1 had no processor that computes an envelope alone. Computed in double: a float32's square is exact in double, so a reference script in float64 reproduces every detection.
  - Rejected: Falcon 1's mode that takes the plain mean instead, which only bypasses the envelope estimate. Later, as an option that is off by default: smoothing the envelope.
  - It averages every channel of its stream. Choosing the channels is the packer's job, upstream (see **Channel selection** in beyond_prototype.md), so RippleDetector is of use on a real recording only once the packer exists.
- **Running statistics**: the envelope's mean and mean absolute deviation (MAD) are exponential moving averages in which each sample weighs 1 ÷ (smoothing time × rate). The mean is updated first, and the MAD from the updated mean. The smoothing time is an option (10 s). During the first smoothing time (burn-in) nothing is detected, and sample n weighs (1 − weight) ÷ n more, so the statistics start as plain averages.
  - The deviation is the mean absolute deviation: Falcon 1's texts call it a standard deviation in one place and a median absolute deviation in another.
- **Detection**: one `Ripple` event, a stream event without a channel mask, on the sample where envelope − mean rises above `threshold_multiplier` × MAD, the previous tested sample having been at or below it. The detected sample is still added to the statistics.
  - One-sided, as the 2017 paper states the rule (signal − µ > factor × mad). Falcon 1's code tested the absolute distance, so a value far below the mean was detected too. With few channels the envelope's MAD is about as large as its mean, so no value can fall that far; averaged over many channels the envelope is steadier (an estimate: from about 50 channels with independent noise, at a multiplier of 6), and a flat or blanked signal would count as a ripple and trigger a stimulation.
- **Lockout**: for the lockout time after a detection (an option, 30 ms, counted in samples), samples are neither tested nor added to the statistics, so one ripple gives one event and stays out of the statistics. The previous tested value stands still meanwhile, so the first sample after a lockout never counts as a crossing.
- **State inputs** (see **An unconnected state input reads its default** under **Buffers**): `threshold_multiplier` (default 6), and `is_detection_enabled` (default true), which another processor sets false to blank out a stimulation's artifact: samples are then treated as in a lockout. The smoothing time and the lockout time are options: each further state input is one more value read on every sample and one more field for the UI, while an option changed during a session costs a restart and a new burn-in.
- **A value that isn't finite is skipped**, with a warning: a NaN or infinite value would stay in the running statistics for the rest of the run, and nothing would be detected again, without an error. Falcon 1 had no such guard.
- **After lost samples** it carries on with the statistics it has. The filter before it restarts in steady state (see **It restarts after a loss** under **IirFilter**), so no jump reaches it, and a new burn-in would cost a smoothing time of detection for every loss.
- **Outputs**: the `Ripple` event, which PCIeParallelOutput, EventLogger and LatencyBenchmark take as it is, while Trigger takes only mask events; and `is_in_lockout`, an optional state output (see **Required and optional connections** under **Processors**), true from the sample whose envelope crossed the threshold until the lockout has passed. Later, as optional outputs (see **Required and optional connections** under **Processors**), once a viewer can show them: the threshold, the mean and the MAD, which Falcon 1 exposed for tuning the multiplier. Falcon 1's `ripple` state was never set true; by where its code clears it, it was meant as `is_in_lockout` is. It lasts the lockout however long the ripple does, hence its name. A state that holds while the envelope stays high is open (see **State values across cores** under **Open questions**).

### Recorder
Writes what all its connections bring, samples and events alike, into one file in the run's directory, for the whole run, so signals and events can be looked at and analysed after the run: `src/tests/plot_recording.py` reads and plots the file. It is the one recorder: its port has slots of any kind (see **A port with slots** under **Processors**). A deliberately simple tool: how Falcon records an experiment is not designed, and its file format stands in until a proper one such as NWB (see **Slow readers**, **Recording formats** and **Experiment files** in beyond_prototype.md).
- **One file that describes itself**: its first line is JSON that names each slot and says how its records are laid out (for a sample slot, also its channel count and rate), so a reader needs nothing but the file. The names are an option, `slot_names`, one per connection: the pipeline designer fills each in beforehand with the upstream processor and its output, and the user may change it (decided by the user on 18 November 2026; see **A recorder's slot names are filled in beforehand** under **Later** in pipeline_designer.md). Chunks follow, each a u32 for the slot, a u32 for the number of records, then that many records of that slot. A sample's record is its number as a u64, then its real channels' values in order as float32; an event's record is the event's bytes as they are in memory, and the first line lists the event's fields, each with its name, type, place, size and count (see **An event's fields as a list** under **Events**), a field of the header under a name such as `header.sample_number`. All little-endian. The sample numbers match events with the samples that caused them, and a jump in a slot's numbers shows where samples were lost.
  - Chunks, so a reader takes a slot's records in whole blocks, not one at a time: a sample slot is written every 1024 samples, an event slot on every pass that brought it events. What waits for its chunk is lost if the run is killed.
  - Any event is written, with every field (since 18 November 2026; before, only the header was, and an event with fields of its own was a compile error). A channel mask is listed as one, with its stream's channel count. The bytes between an event's fields are written as they happen to be, and a reader skips them by the fields' places. `src/tests/plot_recording.py` builds each event's layout from the list, draws an event with a mask of the plotted stream's channels on those channels only, and still reads the files written before. Run and checked with spikes (see **Recording spikes** under **Done** in test_suite.md).
  - The first line stays JSON (decided by the user on 18 November 2026, who asked about lines of `name=value` instead): what it describes is a list of slots that each hold a list of fields, which JSON carries as it is and any language reads in one call, where `name=value` is flat and would need a naming scheme and a parser of our own.
  - Rejected: one recorder and one file per connection (SampleRecorder and EventRecorder, the first form, which worked), since one recorder is wanted, and a format such as NWB holds a whole session in one file.
  - Rejected on 18 November 2026: Recorder finding each name itself. The engine program holds no graph: a buffer doesn't know who writes it, the upstream processor is a local variable of another core's function, tied to Recorder's ring only by its `process()` call, and its output's name is a member's name, which only reflection turns into text. So the names are text in `pipeline.cpp` either way, and the option is where they already are. Weighed and not taken, each a new form for what the option does: a name on each buffer or ring, which a constructor never sees; the ring's own name; an argument of the constructor; and a fact of each slot's template argument.
- **On a core that isn't realtime, behind rings**, since writing to a file can block. That core's loop waits when nothing has arrived (see **Waiting for data**), and the rings must hold what arrives while the recorder writes or the loop waits.
- **A failed write ends the run** (see **An error is an exception** under **Processors**), so a recording that can't be written shows at once, not after the session.
- **Each connection reaches it through a ring of its own**, since a ring has one reader (see **Rings**): what it records is either the ring itself, when nothing else reads that output, or a buffer that feeds the recorder's ring (see **A buffer that feeds rings** under **Rings**).

### Trigger and outputs
A Trigger processor decides when to stimulate and emits a trigger event; the output processor turns each event into a pulse on its hardware.
- **Trigger only decides**: its output is an event buffer of trigger events, each a `StreamEvent` carrying the header of the sample that caused it. It works on events and sample numbers only, never on a clock, so its triggers are exactly what the trigger check in test_suite.md compares, and a replay reproduces them. Any rule that waits or locks out (see **Trigger rules** in beyond_prototype.md) counts samples.
- **The prototype's rule**, as Falcon 1's EventSync: Trigger fires once every channel has had an event since its last trigger event, then starts over. A channel's further events before then count once (EventSync took the next event from each input in turn, so extra ones carried over to later rounds). The trigger event carries the header of the sample whose event completed the set. Its input is any stream event with a channel mask of its stream, e.g. `Spikes` or `LevelCrossings` (see **Detection events are channel masks**): Trigger ORs each event's mask into the channels fired since its last trigger event and fires once every channel is set. There is no time window: the rule is built to measure latency with a test signal such as a square wave injected into every channel, where every channel crosses within a few samples. On real data one quiet channel would keep it from firing; richer rules are in **Trigger rules** in beyond_prototype.md. The reference script for the trigger check in test_suite.md applies the same rule.
- **PCIeParallelOutput times the pulse**, as Falcon 1's did. Its options are the pin number and the pulse width (the prototype's set in `pipeline.cpp`, e.g. 1 ms). It finds the card's I/O address itself when it starts, instead of taking it as an option (Falcon 1 assumed 0x3030), since the BIOS or the kernel assigns the address, which can change with the slot or the machine. Its constructor looks in sysfs for the PCI device with the card's IDs (the DeLock card's SUNIX chip: vendor 1fd4, device 1999, subsystem 0100), takes the start of its I/O range in base address register 1 (BAR1) as the data register's address, and prints it. Writing to a port where no card sits can upset other hardware, so it throws if no device or more than one matches, or if that range isn't an I/O range holding the data, status and control registers, and it never falls back to the address the parallel port driver reports (`/proc/sys/dev/parport/parport0/base-addr`), which may be another port's. Finding the address at run time costs nothing in the loop: x86's `out` instruction takes a port above 0xFF only from a register anyway. A trigger event sets the pin high, and the pin goes low once the pulse width has passed, timed in CPU time so the pulse ends even if the input stops (see **All logic lives inside the processor** under **Processors**); so it runs on a spinning core. Unlike Falcon 1's, it never waits inside `process()` but checks the time on every pass, and trigger events during a pulse neither extend it nor queue another (Falcon 1's waited out each pulse inside `Process()`, so events arriving meanwhile queued into back-to-back pulses).
- **LatencyBenchmark logs Falcon's latency**, as Falcon 1's did: an output processor for any stream event (a `StreamEvent`, the only events with an arrival time). Reading Trigger's output alongside PCIeParallelOutput and called right before it in the loop, it logs for each trigger the time from its sample's arrival to the decision. It logs every trigger, even one PCIeParallelOutput ignores during a pulse. Falcon 1's wrote its file and logged inside its loop, kept no sample number, and ran on a thread of its own, so it also measured its own scheduling.
  - It keeps each trigger's header and the TSC it read in an array its constructor allocates and touches, so the loop never takes a page fault or makes a system call. The array holds 2^20 triggers (about 3 hours at 100 per second); later ones are counted, not kept.
  - After the loop, its destructor writes one row per trigger to a CSV file: the trigger's sample number, its device timestamp, so each row can be matched with its TTL in the recorded event data, and the ns from arrival. It also logs their minimum, median, 99th percentile and maximum. The constructor creates the file, `file_name` in the run's directory (see **Each run writes into a directory of its own** under **Start, stop and config**), and refuses to overwrite one, so a run that can't write its log fails at start rather than after the session.
  - Ticks become ns with the TSC frequency measured against `CLOCK_MONOTONIC_RAW` between the constructor and the destructor: the longer the run, the more exact, and nothing waits at start. The constructor throws unless the TSC is invariant (`constant_tsc`, `nonstop_tsc`) and is the kernel's clock source, a sign that the kernel found the cores' TSCs in sync.
  - Rejected: logging inside PCIeParallelOutput, or a latency probe that any processor calls at a point in its code. An output's call holds nothing worth timing beyond the write, even less once pulse timing moves into a processor of its own (see **Pulse processor** in beyond_prototype.md). What each processor costs is a separate need (see **Runtime performance measurement** in beyond_prototype.md).
- **Why the pulse lives in the output**: its width is a property of what is wired to the line (a stimulator's or a laser driver's input), and other outputs (serial, DAQ, stimulators that take commands) realise a trigger differently, so Trigger stays the same for all of them. Once several output processors need pulses, the pulse logic moves into a processor of its own between Trigger and the outputs (see **Pulse processor** in beyond_prototype.md).
- **Safety**: the output processor's destructor sets every line low, so stopping Falcon never leaves a stimulator on. A crash during a pulse still can; only a pulse timed by the hardware ends regardless, and an output processor for such hardware just forwards the trigger event.
- Rejected: Trigger timing the pulse and outputting the line's state (`is_ttl_high`), which puts a clock into the decision and a property of the hardware into Trigger; the output making the whole decision, with no Trigger, which repeats the decision rules in every output processor; the engine timing pulses for processors, which breaks **All logic lives inside the processor**.

### Extensions
Processors that can't be public, such as an input built on a vendor's SDK, live in extensions, as in Falcon 1, where each extension was its own git repository inside an ignored folder.
- **Location**: `src/processors/custom/<extension name>/`, one folder per extension, each its own git repository (e.g. a lab's private one). `custom/` is git-ignored except `custom/template_processor/`, a template extension that labs copy to start their own (not `template`, a C++ keyword, which can't be a namespace). Falcon ships only the processors directly in `src/processors/`. Only extensions are installed machine-wide.
- **Namespace**: the folder name is the extension's C++ namespace, so processors from different extensions can share a name without clashing. A missing extension shows up as a compile error naming its namespace when `pipeline.cpp` is built.
- **Versioning**: an extension states its version in its `CMakeLists.txt`, its one central place (decided by the user on 21 November 2026, not in code), and nothing else about itself: no name or description, and no comment block at the top of a file. So every extension must have a `CMakeLists.txt`, also one that brings no library, and the version starts at 1.0.0 (both decided by the user that day; Claude's reading of the second, to confirm: the template extension's file states 1.0.0, which a lab's copy starts from). So an extension has a version even where its folder isn't a git repository; where it is one, its commit hash is known too (see **A pipeline says which version of Falcon generated it, and an executable which engine it was built from** in generator.md). Keeping the version right is the lab's responsibility. Open: see **An extension's version** in the open questions.
- **An extension brings its own libraries** through the `CMakeLists.txt` in its folder (required, see **Versioning** above), which the main `CMakeLists.txt` adds as a subdirectory for every extension it finds (as Falcon 1 did), so its paths are relative to the extension's folder; it adds the extension's include directories and libraries to the program. A vendor's SDK sits inside the extension folder, so it stays private too. A library built against another C++ standard library links next to Falcon's as long as only a C interface crosses between them; one built against an older version of GCC's library, which Falcon uses, shares Falcon's.
- **Pipelines that use an extension live in it**, in `custom/<extension name>/pipelines/`, since a public pipeline can't include a private processor.
- **The Ripple input is an extension**, `custom/ripple_neuromed_input/`, in a private repository until it can be published without Ripple's SDK (`xipplib.h` and its library), which may never be public. Naming Ripple and describing its stream in these docs is fine.
- **The template** holds a small processor (Gain, which multiplies every channel by a constant), a `CMakeLists.txt` showing where a library goes, and a pipeline that runs Gain.
