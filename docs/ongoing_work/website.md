# Website
`docs/` is the websites' source. Only what is under `docs/pages/` is published. `docs/ongoing_work/`, which holds this file and the other areas' files, is internal: the build reads nothing from it (see **How they are built**).

## Goal
Three websites, each linking to the other two:
- **Main**: the landing page a visitor sees first, made to impress.
- **Documentation**: the pages under **Pages**, reached from the main website. It reads as the documentation of a finished product. Its full page structure exists from the start; a page about something that isn't built yet says "coming soon" until it can be written.
- **API**: the reference generated from the code (classes, files, C++ concepts), for whoever writes a processor.

Work on the websites changes only `docs/` (in `docs/ongoing_work/`, only this file), the scripts that build them and, where the build needs it, `.gitignore` and the deployment workflow.

State: the three websites are built and link to each other (see **How they are built**). The main website is one placeholder page so far.

## How they are built
`scripts/doc_gen.sh` builds all three into `docs/build/` (git-ignored), which the workflow `.github/workflows/deploy_website.yml` publishes to GitHub Pages on a push to `main` or `develop`. The script needs no `sudo`: it downloads Doxygen and Doxygen's theme, at the versions it names, and the Python packages listed in `docs/requirements.txt` (Zensical among them) into the git-ignored `build/`. When that list changes, it installs them again. It stops at the first problem.

1. **API**: Doxygen reads `src/` with `docs/doxygen/Doxyfile` and writes the API's pages into `docs/pages/api/` (git-ignored) and a tag file, `build/falcon_api.tag`: each class's name and its page's file. `docs/doxygen/api_main.md` is the API's main page; it links to the other two websites.
2. **Main website and documentation**: Zensical reads `docs/zensical.toml` and everything under `docs/pages/`, and writes `docs/build/`. It renders the Markdown pages and copies every other file unchanged, the API's pages included. The top bar's tabs are "Home", "Documentation" and "API".

Addresses: the main website at the root, each documentation page directly under it (e.g. `installation/`), the API under `api/`. Every link between them is relative, so the websites work under any address.

### Class links
In a page, `{{ api("ChannelMask") }}` becomes a link to that class's page on the API website. It takes a class, struct or concept by its full C++ name. `docs/main.py` defines it, as a Zensical macro that looks the name up in the tag file; that is why the API is built first. A name the API doesn't have fails the build.

With macros on, Zensical reads `{{`, `{%` and `{#` in a page as macro syntax: a page that needs them as plain text must escape them.

### Search engines
Goal: Google presents Falcon as a piece of software. "Falcon" alone is taken by far larger names (a rocket, a security product, a Python web framework), so the realistic target is a search with a second word, e.g. "falcon closed loop" or "falcon neuroscience". Google alone decides whether to show a panel about Falcon, and its special result for software needs user ratings or reviews, which Falcon has none of and must not invent.

- The public address, https://falcon-neuro.org/, is `site_url` in `docs/zensical.toml`. Zensical derives each page's canonical address and `sitemap.xml` from it.
- Every page starts with a `description` in its front matter: the text under its title in search results. A page without one gets the website's description.
- `docs/overrides/main.html` adds to every page what a shared link shows (title, description, the image `docs/pages/assets/social_card.png`), gives the main page the title "Falcon: open-source software for closed-loop neuroscience", and adds to the main page a description of Falcon as software in schema.org's vocabulary: name, category, Linux, GPL v3, free of charge, the repository, the 2017 paper.
- `docs/pages/robots.txt` names the sitemap and keeps search engines off the API, whose pages hold little text while the code has few doc comments.

### Formulas
A page writes a formula in LaTeX: `$...$` within a line, `$$...$$` on lines of its own. The build turns it into MathML, which browsers display themselves, so a formula needs no JavaScript and no outside library. Two Python packages do it, listed with Zensical in `docs/requirements.txt`: `latex2mathml` converts, `l2m4m` makes Markdown call it.

Traps when writing one:
- Several aligned lines take `\begin{align*}`. `\begin{aligned}` isn't understood and comes out as one line.
- Within a line, Markdown reads a backslash before a punctuation mark (`\{`, `\\`, `\_`) before the formula does. Put such a formula on lines of its own.
- `{{` starts a macro (see **Class links**), also inside a formula: write `{ {`.
- A `|` inside a table cell ends the cell.

### Glossary
The glossary is the page `docs/pages/glossary.md` itself, which the engine's docs and the work on them use as their list of terms too, so the glossary exists once. After its description, the title is followed by the terms, with no introductory sentence. Each term is a list entry of its own, never a second term inside another's entry.

- What is written in it is therefore published. Its text passes through the macros and the formulas like any page's: `{{`, `{%`, `{#` and a pair of `$` have their meaning there too (see **Class links** and **Formulas**).
- No page includes a file any more, so `include_dir` in `docs/zensical.toml`, still `../src/core`, is unused and could go. Used again, it stays a small folder, since Zensical reads through all of it on every build: set to the repository's root, a build took 80 seconds and then failed on a file it couldn't read.

### Fonts
The text is set in Inter, from `docs/pages/assets/fonts/inter_latin.woff2`: the repository's own Inter file (`assets/`), reduced to Latin characters, 97 kB. Code is set in the visitor's own monospace font. `font = false` in `docs/zensical.toml` stops Zensical from loading fonts from Google.

### Search dialog
Zensical draws its search dialog over a blur of the whole page behind it. A browser that draws without a graphics card (hardware acceleration switched off, a virtual machine, a remote desktop) computes that blur again for every frame while the dialog is open, so the whole website turns slow as soon as the search opens. `docs/pages/javascripts/search_dialog.js`, which `extra_javascript` in `docs/zensical.toml` loads on every page, removes the blur and makes the dialog's panel opaque, since the page's text would otherwise show through it. The veil over the page stays translucent.

The dialog sits in a shadow root that Zensical's script creates, out of reach of `extra.css`: hence a script, which adds its rules to that shadow root.

Trap: the rules find the panel by the dialog's structure (its children are an empty veil and the panel) and colour it with Zensical's colour variables, and a later Zensical may change both. After changing Zensical's version, open the search and check that the panel is opaque and that nothing behind it is blurred.

## Local preview
Whoever works on the websites keeps them built and served locally the whole time, and gives the address when reporting a change, so each change can be looked at in a browser. From the repository's root:

1. Build everything, once per machine and again whenever the code's doc comments change:
   ```sh
   sh scripts/doc_gen.sh
   ```
2. Serve, once per session, as a background process:
   ```sh
   build/website_env/bin/zensical serve -f docs/zensical.toml -a 127.0.0.1:8765
   ```

The three websites are then at http://127.0.0.1:8765. Saving a page or `docs/zensical.toml` rebuilds them; the server's output says "No issues found" or names the problem. The server stops on a mistake in a macro call (see **Class links**), and has stopped once when a file under `docs/pages/` was deleted while it ran: correct the mistake and start it again.

Both steps at once: `sh scripts/doc_serve.sh [port]`, port 8765 unless another is given, or the `serve docs` task in VS Code.

Doxygen's warnings about undocumented members in the code are expected.

### Widgets
A page may use any widget Zensical offers: cards, buttons, the twelve kinds of box (titled, untitled, folding, beside the text, nested; for folding see **Decided**), tabs, code with a title, line numbers, a highlighted line and numbered notes, two blocks side by side, notes in the text, icons, keys, text marks, tooltips, footnotes, a checklist, a list of terms, an aligned table, formulas, a Mermaid diagram and pictures with a caption or beside the text.

`docs/ongoing_work/widget_showcase.md` shows how each one is written, once each, with examples from the two processor pages: read it before writing a widget. It is internal and never published. To see it as a page, copy it into `docs/pages/` and add it to `nav` in `docs/zensical.toml`; remove both again before the branch is merged.

`docs/zensical.toml` turns the widgets on: the features `content.code.annotate` and `content.footnote.tooltips`, and the Markdown extensions `abbr`, `def_list`, `pymdownx.caret`, `pymdownx.critic`, `pymdownx.emoji`, `pymdownx.keys`, `pymdownx.mark`, `pymdownx.tasklist`, `pymdownx.tilde` and the Mermaid fence of `pymdownx.superfences`.

Traps:
- Mermaid and emoji load from an outside server, which **Decided** rules out: Zensical's script fetches Mermaid from unpkg.com on a page that holds a diagram, and an emoji written as `:name:` becomes an image from a content delivery network. Icons written the same way (`:lucide-cpu:`) are safe: they are placed in the page itself. So no page uses a diagram or an emoji; the showcase holds one diagram, under a warning that says so.
- A code block with line numbers shows neither its empty lines, so every number below one is too low, nor the indentation at the start of a line. Both are in the built page and lost on screen; a block without line numbers shows its empty lines. Seen in a headless Brave, cause not found. Until it is, no page numbers its code lines.
- The extensions give `==`, `^^`, `~~`, `++` and `:name:` a meaning on every page.

## Decided
- A page tells a user what Falcon does and what that means for the user. It never restates the engine's design rules, which were written to steer the work on the engine: the Streams page's first section on SIMD was a table of such rules ("one processor for a whole stream", "no processor has a version without SIMD") and the user rejected it as machine-written (17 November 2026).
- A stream is a series of samples only, as the glossary has it (decided by the user on 17 November 2026): no page says "event stream", "sample stream" or "data stream". The page above "Streams" and "Events" is "Data flow", chosen by the user over "Data", which could be taken for recorded files, "Data between processors", which is too long, "Streams and events" and "Connections".
- Three websites, not one (see **Goal**). Nothing generated from the code, e.g. the "Concepts" entry, appears on the main or the documentation website.
- The API website keeps Doxygen's own pages with the doxygen-awesome-css theme, as they are today. At most ten people will ever read it, so it gets no further effort on its look.
- The effort goes to the main website and the documentation, which must look excellent. The documentation leaves Doxygen for that. Looks rejected so far: doxygen-awesome-css, m.css (Magnum's documentation), Poxy (toml++'s). Chosen: Zensical, approved on Falcon's own pages. Second choice: the Shibuya theme for Sphinx, as on https://shibuya.lepture.com/customisation/announcement/.
- The logo is the falcon alone, never inside a disc (the disc version is the Debian desktop icon): dark in light mode, pure white in dark mode, on all three websites. The browser-tab icon is the falcon alone too; it follows the system's light or dark setting, since a tab icon can't follow the website's switch.
- Light and dark mode: the documentation and the main website have Zensical's own switch of three steps: follow the system, light, dark, in that order, each with its own icon (three palette entries in `docs/zensical.toml`). A page opens on "follow the system". Restored by the user on 18 November 2026, in place of a switch that went only between light and dark, with no "system" choice. The API website keeps the switch of its theme, which has two steps and opens in the system's mode.
- The public address is https://falcon-neuro.org/.
- For search engines, only what the websites themselves can do. Nothing outside the repository (Wikidata, research-software registries, a DOI): too much for now. No Google Search Console either, as there is no Google account: Google finds the new pages by itself, from the address it already knows and the sitemap that `robots.txt` names.
- The websites are open source and free of bloat: built only from open-source parts, and a visitor's browser loads nothing from an outside server (no Google Fonts, no library from a content delivery network).
- No Node and no JavaScript toolchain in the websites' build.
- The pages don't show the "Made with Zensical" line (`generator = false` in `docs/zensical.toml`, a switch Zensical's theme provides), nor the grey strip that held it: `docs/pages/stylesheets/extra.css` hides the strip, which would also hide a copyright line or social links if either were set later.
- A class named in a documentation page links to that class's page on the API website automatically: nobody writes the address by hand.
- The website carries only content that is needed, and no page without it. "License and contributing" is deleted: the overview names the licence and links to the repository. The six pages that said only "coming soon" are deleted too. "Coming soon" may be said, but once on the whole website (see **Pages**).
- The overview says that a new engine is coming soon and that the documentation describes the new version.
- Boxes are used on the documentation's pages: tried on the spike detector's page, they improve it. There: a note box "Edge cases" under the example table, in place of the list after "It follows that"; a tip box that opens "Choosing the threshold".
- No box is folded when a page opens: it hides information.
- A box's text is complete without its title: full sentences that would read the same as plain text. Its title is the kind's own name ("Tip", "Warning") or a plain noun label ("Edge cases"), never a headline, and never a phrase the text leans on. Rejected as marketing: a tip box titled "A common choice" over the fragment "Four to five times the standard deviation of the noise, ...".
- The documentation is scientific and humble in tone. Nothing in it reads like a sales page.
- A paper cited in a sentence is a footnote: its number in the sentence, its text at the foot of the page and shown on hover. The spike detector's page cites Quian Quiroga and colleagues this way.
- The documentation is written in the manner of a scientific toolkit's documentation from about 2015: plain statements and summary tables. The processor reference is the model for a page that lists things.
- A processor's page is named by the processor's code name, e.g. "SpikeDetector" and not "Spike detector": its title, its entry in the sidebar and its row in the processor reference (asked for by the user on 18 November 2026). The file keeps its name, e.g. `spike_detector.md`.
- No page has a section "In the code": the user had it removed from all six pages that had one (18 November 2026). Where a page names a processor or an event, the name itself is the link (asked for by the user on 18 November 2026). A documentation link is preferred over an API link wherever one exists (said by the user on 18 November 2026): a processor links to its documentation page, and an event named outside the Events page links to its section there (e.g. `../data_flow/events.md#spikes`). An API link is left only where no documentation page exists: a processor's own name in the first sentence of its page, an event in its own section of the Events page, and a struct that has no page (`SampleHeader`, `StreamInfo`, `SampleRing`, `EventRing`, `BiquadSection`). A struct that a page described but never named (`SampleHeader`, `StreamInfo`, `SampleRing`, `EventRing`, `BiquadSection`) is now named, with its link, in the sentence or table cell that describes it. The options' structs (e.g. `IirFilterOptions`, `SpikeDetectorOptions`) are linked from no page: no text names them, and each is reached from its processor's API page.
- A limit on an option is said plainly in the option's description, e.g. "It can't be 0." No page says "Falcon refuses a graph, before it runs, when …", has a warning box for such a limit or a section "What Falcon checks": the user called that wording "AI slop grammar" that "looks weird" and asked to "just say threshold can't be 0, like a human being" (18 November 2026). An option that has no default says "Required" in the default's column. What must hold on the computer when a run starts (a card, a CPU flag, a file that doesn't exist yet) is a short list headed "Requirements", closed by the sentence that the run otherwise fails at its start with an error message.
- The wording rules below must never cost a sentence its natural grammar (the user, 18 November 2026: the website reads as written in 2015 about a scientific software framework, with no AI slop). Claude's reading: a plain "not" that informs is fine ("generated by a timer, not derived from a signal"), and a twisted phrase written to avoid one ("from a timer and from no signal", "the computer's clock and no acquisition device's") is the fault. Such phrases were straightened on the pages written on 18 November 2026; the Overview, the glossary, Streams and Rings were not gone through for them.
- The top bar's tab that leads to the API website is named "Falcon C++ API" (renamed by the user from "API" on 18 November 2026). The documentation's own navigation has no entry for the API: one named "Falcon API" was added there that day on a misreading and removed again, since the top bar already has the tab.
- No sentence counts or lists what the page itself shows, e.g. "Falcon's built-in processors emit five events. Four of them come from a sample and one from a timer.": it is out of date as soon as an item is added, and the reader sees the items on the page anyway. The user called it filler, "something that's put there to make the page longer", and had every such sentence removed (18 November 2026). Likewise a list of the other processors or events something works with is given as an example ("e.g.", "such as"), never as the whole list.
- No sentence is there to lengthen a page. A fact is said once on a page, and what a processor's own page says is not retold on another page: the Events page gives, for each event, when it is emitted, the sample it belongs to, what it holds and what it leaves out, and leaves the detector's computation to the detector's page (the user, 18 November 2026: "remove all of unnecessary documentation"). In the other direction, a detector's page has no section on what its event holds: its output's row links to the event's section of the Events page. Nor does a page say how many channels a processor computes at a time, or what it keeps in memory from one sample to the next, which a user can't act on.
- All pages follow the wording rules below. In the glossary only wording changed, never a term's meaning.
- No words for effect: no emphasis ("the very sample", "exactly", "nothing more", "never adapts"), no contrast made for effect ("the crossing, not the peak"), no processor described as a person ("watches"). A section that lists what a processor doesn't do is headed "Limitations" and states each limit plainly.
- No second clause hung on a sentence with ", and" ("Extracellular spikes mostly point downward, and the default threshold is negative to match"): it reads as machine-written. Say how the two facts relate ("which is why", "so", "because") or write two sentences. A plain list ("a, b and c") is not meant.
- No machine-sounding filler: no sentence that only announces what follows, no promise of content in a page's search description that the page doesn't hold, no bold lead-in on each item of a list.
- The processor pages keep their formulas and their signal-processing detail. Rewriting them for a junior neuroscientist, with the detail moved to the API, was considered and dropped.
- The maintainer merges and deploys. Whoever works on the websites never commits, merges, pushes or deploys.
