# Differences from Falcon 1

Where the new engine departs from Falcon 1 (the old `falcon/` engine, its extensions and its Dart UI). Anything not listed works as in Falcon 1, or will: the new engine must do everything Falcon 1 could. Falcon 1 was used only by its authors, so no user habits or existing graphs constrain the new engine. Each entry says what Falcon 1 did and what replaces it, and points to the section that decides it and gives the reasons. A new decision in [spec.md](spec.md) or [beyond_prototype.md](beyond_prototype.md) that departs from Falcon 1 gets an entry here too.

## Different for good
Decided; Falcon 1's way is not coming back.

- **Graph definition**: Falcon 1 built the graph at run time from a YAML file (processors with their options, connection rules, linked states), and checked the options while building it. Now the UI generates `graph.cpp` and compiles it into the engine program, so every option is a compile-time constant and changing one means compiling and spawning a new program (**Boundaries**, and **Every option is a compile-time constant** under **Processors**, in spec.md; **Generator** in beyond_prototype.md).
- **Threads**: Falcon 1 ran each processor in its own OS thread, optionally pinned to a core and given a realtime priority (its `thread_core` and `threadpriority` options), and each processor's `Process()` ran its own `while` loop; a phase such as RippleDetector's burn-in was a loop of its own. Now each core runs one pinned thread that calls each of its processors once per pass; `process()` never loops or waits, and a phase is state inside the processor (**Per-core loop**, and **`process()` never loops and never waits** and **All logic lives inside the processor** under **Processors**, in spec.md).
- **Processor lifecycle**: Falcon 1 processors derived from `IProcessor` and overrode a virtual method per stage: `Configure`, `CreatePorts`, `Prepare` and `Unprepare` (graph build and destroy), `Preprocess` and `Postprocess` (each run's start and end), and `Process`. Now a processor is a struct with an `Options` template parameter, a constructor, a destructor and `process()`, with no virtual functions (**A processor is a struct with an `Options` struct** under **Processors** in spec.md).
- **Processor granularity**: Falcon 1 graphs had one processor per channel or tetrode, hundreds in all (one YAML entry such as `tetrode(1-16)` expanded into many). Now one processor handles a whole stream with hand-written SIMD, and per-group settings are arrays inside it (**One processor per stream** under **Processors** in spec.md).
- **Connections**: Falcon 1 ports had slots, so one port could take a variable number of connections, set in the YAML. Now a processor's connections are a fixed set of named members of its `Connections` struct (**`process()` signature** under **Processors** in spec.md).
- **Samples per call**: Falcon 1 processors handled packets of several samples and could take several packets in one call (`RetrieveDataN`, `RetrieveDataAll`). Now each `process()` call handles at most one sample (**One sample per pass** in spec.md).
- **Data between processors**: Falcon 1 gave every output its own disruptor ring buffer of preallocated `TimeSeriesType` packets (256 slots by default, set per output with the `buffer_sizes` option), read by every input connected to it. Now there is one generic stream type in float32 µV, plain buffers within a core, and a ring, as small as possible, with one writer and one reader only where a connection crosses cores (**Goal**, **Buffers**, **Rings** and **Sample type** in spec.md).
- **Full rings**: in Falcon 1, a writer whose ring was full waited for its slowest reader, so a slow processor stalled everything upstream of it; a reader warned when its backlog passed 85% of the ring. Now the writer never waits: a sample that doesn't fit is dropped and counted, and the run goes on (**A full data ring is a failure, but the run goes on** under **Rings** in spec.md). The UI showing ring fill levels is planned (**Ring fill levels** under **UI** in beyond_prototype.md).
- **Waiting for data**: Falcon 1 let each output choose how its readers wait: blocking (the default), sleeping, yielding or busy spinning (`falcon/portpolicy.hpp`). Now realtime cores spin and non-realtime cores may block (**Waiting for data** in spec.md).
- **Data types**: Falcon 1's data types were a class hierarchy with virtual functions, and each stream's parameters and rate were set when the graph was built, with each input checking the parameters against what it accepted. Now a stream's facts form a compile-time `StreamInfo` type, so a mismatch is a compile error (**Stream type** under **Processors** in spec.md).
- **Sample numbering**: Falcon 1 numbered packets in the order each output produced them, so a packet lost before the input didn't show. Now the input derives each sample's number from the device's clock, so a lost sample shows up as a gap (**Each sample has a header** under **Buffers** in spec.md).
- **Serialization**: Falcon 1's data types each had hand-written serialization code (binary, YAML and FlatBuffers), used to save and stream data. Now there is no serialization code: whatever saves or shows events reads their fields through reflection (**No serialization code** under **Events** in spec.md).
- **Shared states**: Falcon 1 linked states across processors in the YAML's `states` section: atomic values that several processors could read and write, each with read/write permissions for its owner, the other processors and clients. Now a state value is a connection with one producer and is a plain value within a core (**State values** under **Buffers** in spec.md); across cores it is open (**State values across cores** in beyond_prototype.md). Client access is under **Runtime control** below.
- **Errors during a run**: in Falcon 1, an exception in any stage of any processor, `Process` included, ended the run with an error. Now nothing in the loop throws; only a constructor can fail, and then the graph doesn't start (**Exceptions only outside the loop** under **Processors** in spec.md).
- **Logging from processors**: Falcon 1 processors logged text from their own threads (g3log). Now realtime cores never print: they send numbered messages with raw values through a ring to a logger on a non-realtime core (**Logging** in spec.md). Where the logger writes is under **Log destinations** below.
- **Resource paths**: Falcon 1 resolved paths in options through prefixes (`resources://`, `filters://`, `graphs://`, `run://`, `test://`) pointing to folders on the machine. Now a file option is a plain path, and the experiment file holds a copy of every resource it uses (**A file option is only its path** under **Processors** in spec.md, **Experiment files** in beyond_prototype.md).
- **Extensions**: Falcon 1 compiled every extension listed in the build into the `falcon` program and registered each processor in one global list by its class name. Now an extension lives in `src/processors/custom/<extension name>/` and its folder name is its C++ namespace (**Extensions** in spec.md).
- **Event kinds**: Falcon 1's events were one data type carrying a name, and processors picked theirs by name (e.g. a `target event` option). Now each kind of event is its own type, so connecting the wrong kind is a compile error (**One type per kind of event** under **Events** in spec.md).
- **Deciding on an output**: Falcon 1 combined events in EventSync (a target event on every input) and EventFilter (how many inputs within a sync time, and blocking events that veto for a while), and its DigitalOutput mapped named events to actions on digital lines and timed the pulses itself. Now a Trigger processor makes the decision and emits trigger events, and the output processor times the pulse: PCIeParallelOutput, as Falcon 1's did, but checking the time on every pass instead of waiting out each pulse, so events during a pulse are ignored instead of queued into back-to-back pulses (**Trigger and outputs** in spec.md).
- **Spike threshold**: Falcon 1's spike detection took a positive threshold plus an "invert signal" option. Now the threshold's sign gives the direction (**The prototype's SpikeDetector** under **Events** in spec.md).
- **Filter kinds**: Falcon 1 had one filter processor, MultiChannelFilter. Its only option was a coefficients file whose header named the filter's kind (`# type = biquad`, `fir` or `slope`), and a virtual filter class picked the implementation at run time. Now each kind is its own processor and its own UI node: `IirFilter`, `FirFilter` and `SlopeFilter` (**FIR filter** in beyond_prototype.md).
- **Filter arithmetic**: Falcon 1 filtered in double, in Direct Form II. Now still in double, in Transposed Direct Form II, while samples between processors are float32 (**IirFilter** in spec.md).
- **Filter design rate**: Falcon 1's coefficient files stated their sampling rate only in free text, so a file designed for another rate ran without an error. Now a coefficients file states it in a machine-readable header line, checked against the stream's rate at compile time (**IirFilter** in spec.md).
- **UI**: Falcon 1's UI is written in Dart. The new one is written in Dear ImGui and reads processors and their options through C++26 reflection (task D.4 under **Tasks** in beyond_prototype.md).

## Not yet in the new engine
Falcon 1 could do these; the prototype can't. Each entry gives its status: planned, deferred, open, or not discussed yet.

- **Engine between runs** (deferred): Falcon 1 was a server that stayed alive. Clients (keyboard, command line, a ZeroMQ socket) sent commands to build, start, stop and destroy graphs, and a built graph could run several times. Now each run is one engine program, spawned by the UI and stopped by a signal (**Start, stop and config** in spec.md); a program that stays alive between runs is **Engine states** in beyond_prototype.md.
- **Runtime control** (open): Falcon 1 clients could, during a run, read and write processor states their permissions allowed (`update`, `retrieve`), call methods a processor exposed (`apply`), and export the running graph with its state values (`yaml`). Now no client can change anything during a run, since every option is a compile-time constant (**Runtime control** in beyond_prototype.md).
- **Run folders** (not discussed yet): Falcon 1 created a folder for every run (run group, then run name or start time, then one folder per processor), into which processors wrote their output files, kept a `_last_run` link to the newest one, and could hand a processor a previous run's folder as a template. How the new engine records is not designed yet (**Experiment files** and **Slow readers** in beyond_prototype.md).
- **Test mode** (open): Falcon 1 had a test flag, set per run or per processor, under which processors ran extra steps (`TestPrepare`, `TestFinalize`) and saved test data, such as source timestamps for latency tests, into a test folder. Separately, a processor could record its own timing (cycles spent waiting and working) to a file. The prototype logs each trigger's latency (**How we judge that it works** under **Agreed** in spec.md); measuring every processor's timing is open (**Runtime performance measurement** in beyond_prototype.md).
- **Log destinations** (not discussed yet): Falcon 1 logged to a file, to the screen and to a ZeroMQ socket that clients such as the UI subscribed to, with debug messages behind a flag. The prototype only prints warnings about full rings to the console (**Rings** in spec.md).
- **Realtime thread setup** (not discussed yet): Falcon 1 locked all its memory in RAM (`mlockall`), gave processor threads the `SCHED_FIFO` realtime priority, and could log a processor thread's involuntary context switches. spec.md covers core isolation only (**Machine setup** under **Agreed**).
- **A processor ending the run** (not discussed yet): a Falcon 1 processor could end the run itself (`Terminate()`), and a run also ended once every processor's `Process()` had returned. Now only the stop signal ends a run (**Start, stop and config** in spec.md).
- **Option units and checks** (not discussed yet): Falcon 1 options carried units (e.g. Hz, ms, samples) and checks (e.g. positive, within a range), applied when the graph was built. Now an option is a plain value; only some processors check their own at compile time (e.g. **IirFilter** in spec.md).
- **Option descriptions and processor documentation** (not discussed yet): Falcon 1 gave every option a description and every processor a `doc.yaml`, which clients fetched with the `documentation` command. Now reflection gives the UI each option's name and type only (**A processor is a struct with an `Options` struct** under **Processors** in spec.md).
- **Extension tools** (not discussed yet): a Falcon 1 extension could bring its own libraries and tools, built by its own `CMakeLists.txt`. Libraries still come through the extension's own `CMakeLists.txt` (**Extensions** in spec.md); tools have no place yet.
- **Decimator** (deferred until a graph needs one): Falcon 1 had a Decimator processor, and its filter files include ripple filters designed for 2 and 4 kHz next to an anti-aliasing filter for 32 kHz. The new engine leaves it out until a graph needs one (**Decimator** in beyond_prototype.md).
- **Slope filters** (planned): besides biquad cascades and FIR filters given as taps (e.g. Neuralynx's 32-tap spike filter, the one Neuralynx's own acquisition uses; now FirFilter, **FirFilter** in spec.md), Falcon 1 ran slope filters: Savitzky–Golay derivatives built from a window size, a polynomial order and a derivative order (**FIR filter** in beyond_prototype.md).

## Not yet compared
Falcon 1's processors and data types live in its extensions (`falcon-fklab-extensions`, `ripple_neuromed_reader`), outside this repository. Of them, only MultiChannelFilter is compared above. The others, and the Dart UI (`falcon_gui/`), may provide features still missing above: e.g. acquisition inputs other than Ripple, recording to disk, streaming data to other programs, and the live viewer.
