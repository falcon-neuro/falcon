# Prototype spec

The new Falcon engine is a single `engine.cpp` in `src/core`. It replaces the old `falcon/` engine (disruptor ring buffer, heap-allocated `TimeSeriesType` packets).

This file is the minimum spec for the prototype. Later work is in [beyond_prototype.md](beyond_prototype.md). The graph shapes the engine must support are in [graph_shapes.md](graph_shapes.md). The fundamental words these docs use are defined in [glossary.md](glossary.md).

## Goal
One generic multichannel stream type. Every input processor produces it; every other processor and the UI viewer consume it. Hardware-specific structures (e.g. Neuropixels' `electrodePacket`) exist only inside their input processor.

## Priorities
These two guide every design decision, from the sample format to the graph as a whole:
- **Scientific accuracy**: every value a processor receives or outputs is the correct physical quantity (e.g. µV). No precision loss, overflow or rounding may change a detection or a trigger without an error message.
- **Embedded-systems approach**: the data the hot loop touches stays in the caches of the core that uses it (see **Principles**), and values stay in CPU registers from one processing step to the next instead of being written to memory and read back (see **Vector chains** in beyond_prototype.md).

## Principles
- **Everything fits in cache.** All rings and all processor state on a core must fit in that core's cache.
  - Hot data is what is touched for every sample: rings, and processor state such as filter coefficients and history. It is sized against L1/L2 per core and the shared L3.
  - Cold data, such as stream metadata, is decided on compile time. Processors can have the few values they need into their own compact state (e.g. an input's 384 µV-per-bit scales, 1.5 KB).
  - Channels are padded to a multiple of 16, one AVX512 vector of float32, so a sample fills whole 64 B cache lines and SIMD loops have no leftover channels.
  - Ring bytes = samples × padded channels × bytes per sample. One float32 sample is 256 B (4 cache lines) at 64 channels and 1.5 KB at 384 channels (NP1). A 64-sample ring at 384 channels is 48 KB as int16 and 96 KB as float32.
- **Every sample as soon as possible**: one sample per pass (see **One sample per pass**), and the smallest rings everywhere.
- **No lost packets.** Rings start as small as possible. If packets get lost, the user makes them bigger: a bigger ring survives a short stall (see **Rings**). A graph too slow to keep up is spread over more cores (see **Heavy processors** in beyond_prototype.md). A lost sample means the setup is failing, and the user fixes the setup. Processors learn of a loss from each sample's lost-sample count (see **Each sample has a header** under **Buffers**), and IirFilter restarts after one (see **IirFilter**).
- **Deterministic replay**: replaying a recording should give about the same triggers as the live run; 99% matching is enough. For the same input, most processors give exactly the same output anyway, so no extra effort goes into making replays exactly identical (see **Exact replay** in beyond_prototype.md).
- **Low channel count first** Design and optimise for ~32-64 channels now. +2000 channels come in the future (see **Scaling to +2000 channels** in beyond_prototype.md).

## Prototype plan
Goal: a first engine that runs a real graph end to end. The basics are defined, and later optimisations stay possible.

### Agreed
- **No generator.** We write `graph.cpp` by hand to test the engine. In the product, users never write it: the UI generates it from the processor nodes they drag and drop (see **Generator** in beyond_prototype.md).
- **Input: Ripple Neuromed, 32 channels**, read through Ripple's C library (`xl_cont_raw` in xipplib). Its documentation confirms: the raw stream is 30 kHz (a compile-time constant in `graph.cpp`, see **Rates**), electrode data is float in µV, each call returns as many points as requested plus one 32-bit timestamp for the first point. There is no separate sample number: the timestamp counts 30 kHz ticks, one per sample, so the input widens it to 64 bits (32 bits wrap after about 40 hours) and uses it as the sample number (see **Buffers**). Still to verify:
  - how soon a point is available through the library after the hardware sends it (one every 33 µs is expected, see **One sample per pass**);
  - that its data arrives over UDP (see **Machine setup**). The library does run threads of its own (it uses `std::thread`), kept off the realtime cores (see **Start barrier** under **Per-core loop**).
- **SignalGenerator for testing without the Ripple system**: an input processor that stands in for it, giving a sine wave, a square wave or a train of spike-shaped pulses (a sharp trough of the given depth and a smaller rebound, within 2 ms) in µV on every channel at the stream's rate, optionally on top of a slow LFP sine, so a filter's effect on spikes and LFP can be seen. It runs alone on its core, like any input, so it may block that core's thread: it sleeps until shortly before each sample is due, then busy-spins to the exact time, on a fixed schedule from its first pass. Sleeping alone wakes too late for a 33 µs period, and spinning alone keeps the core at 100%. The spin adapts to how late the sleeps wake: it lasts a minimum (10 µs by default) plus the worst recent wake-up delay, which jumps up at once after a late wake-up and halves every second. So after a late wake-up it sleeps less for a while, and it stops sleeping altogether while wake-ups take a whole period. Its constructor sets its thread's timer slack to 1 ns, since Linux otherwise lets a normal thread's sleep end up to 50 µs late. Its device timestamp counts samples, as Ripple's does. It stamps a sample's arrival time only once all its channels are computed, as a hardware sample arrives only once its packet is complete, so the latency log counts none of the generation. No file playback.
- **Graph**: the Ripple input alone on its own core (see **Input processors**), a ring to one processing core that runs IirFilter → SpikeDetector → TTL output, the start/stop signal, and a minimal logger. This is shape 1 (chain) of graph_shapes.md. The processor interface must not rule out any other shape.
- **Machine setup** by hand: one core handles the OS and interrupts and all other cores are isolated for Falcon. Falcon runs on any number of cores, even one, but the advice for low latency is at least 4: two realtime cores, one for the input and one for the rest of the graph, and two non-realtime ones, one for Falcon's UI and one for the rest of the OS. Also by hand: interrupt batching is turned off on the network card that receives Ripple's data; the UDP receive buffer limit is raised so a short stall doesn't drop packets in the kernel. Automating these is tasks A.1, A.4 and A.5 in beyond_prototype.md.
  - The boot CPU (CPU 0) never runs a realtime loop: even when isolated, the kernel removes it from `nohz_full` and keeps its tick for timekeeping, so it takes a timer interrupt every 1 to 4 ms (the kernel's tick rate). Isolated, it still keeps OS processes off the cores that share Falcon's L3.
  - A network card's queue interrupts are managed by the kernel, one queue per CPU, and can't be moved off isolated cores; a packet interrupts the CPU of the queue the card's hashing (RSS) picks for it. So RSS must send packets only to the queues of OS cores (to verify on the card that receives Ripple's data).
  - The realtime cores' clock must stay at its maximum while a graph runs. An idle isolated core drops to its lowest clock (600 MHz on a CPU that boosts to 5.7 GHz), where a pass takes about 9 times longer, and changing the clock mid-run stalls the core. On a `nohz_full` core, with no tick, a governor that adjusts the clock at the scheduler's updates may raise it late (to verify while a graph runs). Measured with a core that slept between samples: the same work took about twice as long (see **Latency tests for the paper** in beyond_prototype.md). The latency log stays correct at any clock, since the TSC ticks at a constant rate; only the work gets slower.
- **No live viewer.** The path for the viewer's data from the engine process to the UI process is not needed yet (see **Live viewer** in beyond_prototype.md).
- **How we judge that it works**:
  - Correct triggers: Ripple's software (Trellis) records the same session alongside Falcon. A reference script applies the same filter and threshold to that recording. At least 99% of the triggers Falcon logged must match the sample numbers it detects.
  - Latency inside Falcon: for each trigger, LatencyBenchmark (see **Trigger and outputs**) logs the time from packet arrival to the trigger decision, using the CPU's timestamp counter (TSC). The pin write itself counts outside Falcon: a PCIe I/O write, which the card acknowledges before `outb` returns, timed on its own by a loopback test (an output pin of the card wired to one of its input pins). The arrival time is read on the input core and the decision time on the processing core, so the TSC must be invariant and synchronised across cores; to be checked on the target CPU.
  - Latency end to end: the TTL output is wired back into a digital input of the Ripple system, so the trigger is recorded on the same clock as the neural data. The latency test graph: a test square wave injected into all 32 channels → Ripple input → ring → 8 IirFilters in series, each with one pass-through section (b0 = 1, gain 1: their cost counts, the signal passes unchanged), as in Falcon 1's latency benchmark → LevelCrossingDetector → Trigger → PCIeParallelOutput on a DeLock PCIe parallel port card (SUNIX chip), with LatencyBenchmark reading Trigger's output right before it. The Ripple system records the raw channels and the digital input, so each trigger's round trip, from the edge in the recorded ephys data to the TTL in the recorded event data, is measured on Ripple's clock. A run counts only if the recorded event data hold one TTL per rising edge: a missing TTL means a lost sample or a missed trigger. The round trip minus Falcon's part (above) is the time spent outside Falcon: in Ripple's hardware, the network, the kernel, xipplib and the PCIe card.
- **How to prioritise**: decide now what is expensive to change later, and build the simplest version of everything else.
  - Expensive: what processor code sees, i.e. the `process()` signature, the buffer type and the sample type. Every processor depends on it, including the ones labs write in their own extensions.
  - Cheap: what only the engine sees, i.e. rings, threads, buffer assignment and the waiting strategy. These can be optimised later without touching any processor, as long as processors only ever see buffers, never rings.
  - Outside the loop: anything that runs outside the per-core loops (setup, teardown, failure handling) costs no latency, so it gets the simplest solution that works, never an elaborate one.

## Decided

### Boundaries
- **UI and engine are separate programs.** In the product, the user designs the graph in the UI, the generator writes `graph.cpp`, clang compiles it into the engine program, and the UI spawns that program (see **Generator** in beyond_prototype.md). Compilation time is not a concern (takes seconds with a build cache on a 9950X); runtime performance is.
- **The bundled clang supports C++26.** Falcon relies on reflection (see **Events** and **Processors**), plus the C++20 features that put `Options` in a template argument: floating-point values and designated initializers there (see **Processors**). A compiler implements the standard feature by feature, so `-std=c++26` alone doesn't guarantee these; check each one on the clang version chosen for bundling.
- **Hardware input/output latency** is outside the engine design. It is being worked out with the neurotech companies, who shape their firmware for it.

### One sample per pass
Each `process()` call handles at most one sample: one time point across all channels. There is no buffer size (samples per call, as in audio software). Batching samples only pays off when each call has a large fixed cost, such as Falcon 1's scheduling of hundreds of OS threads. Here each core runs one pinned thread, so batching would only add latency.
- Neuralynx and Ripple are expected to deliver each sample immediately (for Ripple, to verify; see **Agreed**).
- Neuropixels 1.0 sends 12 samples per packet, one packet every 0.4 ms, so 0.4 ms is its latency floor. Its sample rate is still 30 kHz: the 12 samples go through the graph one per pass, back to back (see **Buffers**), so a spike in the packet's 3rd sample triggers after 3 passes, not after all 12. If imec ever delivers single samples, nothing in the engine changes.
- No batching later either, not even at +2000 channels, where the channels are split across cores instead (see **Scaling to +2000 channels** in beyond_prototype.md).

### Processors
- **Three kinds, by their connections**: an input processor has only outputs (a hardware input, SignalGenerator), an operator has both inputs and outputs (IirFilter, a detector, Trigger), and an output processor has only inputs (a hardware output, EventLogger). The name can recall C++'s `operator` keyword; the alternatives were vaguer or already meant something in Falcon (intermediate, transform, stage, midstream, block, element, node, filter).
- **One processor per stream**, never per channel or tetrode (Falcon 1's hundreds of processors were a major cause of slowness). A processor handles all channels with handwritten SIMD: every processor has a hand-crafted AVX512 version and a hand-crafted AVX2 fallback, rather than relying on the compiler to vectorize. The version for the machine is picked at compile time, since `graph.cpp` is compiled for the machine that runs it. Both versions sit in the same `process()`, in the two branches of `if constexpr (HAS_AVX512)`, where `HAS_AVX512` is a constant the engine sets from the compiler's target; `load(simd_vector_index)` then returns an `__m512` or an `__m256` (see **Operations a processor uses** under **Buffers**). C++ skips a discarded `if constexpr` branch only for code that depends on the processor's template parameters; anything else in it must still compile on both instruction sets, so e.g. `SimdVector result = _mm512_setzero_ps();` fails in an AVX2 build. The AVX512 branch names `__m512` itself. The engine's own helpers depend on no such parameter, so they pick their version with `#ifdef __AVX512F__` instead. There is no scalar code, and AVX2 and FMA (fused multiply-add, on every AVX2 CPU since 2013) are required to run Falcon; the engine refuses to compile without either. Per-group settings (e.g. per-tetrode thresholds) are arrays inside the processor.
- **`process()` never loops and never waits.** In Falcon 1, each processor ran its own `while (running)` loop in its own thread. Here, `process()` checks its inputs, returns at once if there is nothing to do, and otherwise does its work. A waiting processor would stall every other processor on its core.
- **All logic lives inside the processor**, including when it runs. The engine never buffers anything for a processor.
  - A processor that produces output only every N samples (decimator, spike-count binner, decoder) leaves its output empty in between, so everything downstream of it also runs only every N samples. This is how lower rates exist inside a graph.
  - A processor with several inputs combines them itself. Example: p3 needs sample N from both p1 and p2. If p1's sample N arrives first, p3 copies it into its own state and waits; when p2's sample N arrives, p3 processes both. It works the same when p2 is on another core and its samples arrive through a ring. If an input stops, p3 drops its oldest kept sample and logs a warning once.
  - Phases become state. Falcon 1's RippleDetector had a burn-in loop before its detection loop; here it is `if (burningIn) { update statistics; return; }`.
  - A processor that acts on time checks the time itself on every pass, counting either CPU time or samples. Anything that ends an output, such as turning a TTL off 1 ms after a trigger, is timed in CPU time, so it ends even if the input stops. Such a processor must run on a spinning core (see **Waiting for data**).
- **A processor is a struct with an `Options` struct**: a `process()` function, a constructor and a destructor, plus an `Options` aggregate that holds only the processor's options, so they are set by name with designated initializers. The constructor acquires resources (memory allocations, sockets, file descriptors) and the destructor releases them. Internal state, such as filter history, lives in the processor, outside `Options`. No virtual functions: they would force one `process()` signature on every processor. Later, C++26 reflection can read `Options` and `process()`'s parameters (its inputs and outputs) for the UI (other options for later: **Processor type alternatives** in beyond_prototype.md).
  - Options are always named, never positional (non-negotiable): `IirFilter ap {300, 6000}` would also compile with highpass and lowpass swapped.
  - **Every option is a compile-time constant**, so the compiler can fold options into the instructions and use them for array sizes and loop counts. No option changes while the engine runs: changing one means generating, compiling and spawning a new engine program (see **Boundaries**), so every processor starts again from scratch (e.g. a detector's burn-in statistics are lost).
  - So `Options` is a template parameter, after the stream type: `IirFilter<RippleRaw, {.highpass = 300, .lowpass = 6000}> ap;` (compiler support: see **The bundled clang supports C++26** under **Boundaries**). It can't be nested inside its processor, because it must be declared before the processor's template, so it gets its own name, e.g. `IirFilterOptions`. The constructor takes no arguments and reads the options from the template parameter.
  - **Exceptions only outside the loop**: a constructor that fails (e.g. a socket that won't open) throws. The engine catches the exception and logs it, and the graph doesn't start. Nothing in the loop throws. Exceptions cost nothing while none is thrown.
    - C++ then destroys the processors already built on that core, in reverse order, and never builds the later ones.
    - The failing processor's own destructor doesn't run, because C++ runs a destructor only for a fully built object. So a resource acquired before the throw is either released before throwing or held by a member with its own destructor (e.g. a socket wrapper), which C++ does run. This matters most for device state the OS doesn't reset when the program exits, e.g. a device left acquiring.
  - Rejected: optional `on_init()` and `on_destroy()` hooks, which `graph.cpp` would call through helpers that check with a concept (`HasOnInit`, `HasOnDestroy`) and `if constexpr` whether the processor defines them. A constructor and destructor are standard C++, and C++ runs them automatically.
  - Rejected: no constructor, with the processor itself an aggregate and each resource a member built from options declared above it (`int port = 6363; Socket sock {port};`). A member declared above an option it reads gets an uninitialised value, possibly without a compiler warning; checks across options (e.g. highpass below lowpass) have no natural place; and an aggregate can't have private members, so `graph.cpp` could set internal state by name.
- **The channel count is a compile-time constant**, so the compiler knows every loop's length and every buffer's size (e.g. 32 float32 channels are exactly two AVX512 vectors, or four AVX2 vectors). A processor never hardcodes it: the same code runs at 32, 64 or 2000 channels, and different streams can have different counts (e.g. the branches of a channel split, shape 9 in graph_shapes.md). A new channel count means regenerating and recompiling `graph.cpp`.
- **Stream type**: the compile-time facts about a stream (channel count, sample rate, sample type) are grouped in one named type, a `StreamInfo`, and each processor takes it as a template parameter:
  ```cpp
  using RippleRaw = StreamInfo<32, 30000.0, float>;   // written once

  IirFilter<RippleRaw, {.highpass = 300}>      ap;
  SpikeDetector<RippleRaw, {.threshold = -50}> spikes;
  ```
  Adding a fact later changes only `StreamInfo`, not any processor.
  - **Template parameters have descriptive names**, like every other name, so unfamiliar code reads without context: `InputStreamInfo` and `OutputStreamInfo` in a decimator, `EventType` and `Capacity` in `EventBuffer<EventType, Capacity>`, never `S`, `E` or `N`. No `.clang-tidy` rule checks template parameter names. A stream parameter can't be named just `StreamInfo`, which is the template's own name, so where no direction applies it is `StreamInfoType` (e.g. `SampleBuffer<StreamInfoType>`).
  - **Class constants are lower_case** (`InputStreamInfo::simd_vectors`, `InputStreamInfo::rate`), like the standard library's (`std::numeric_limits<float>::digits`), while global constants are UPPER_CASE (`HAS_AVX512`). `.clang-tidy` enforces both. A processor whose output stream differs from its input takes both stream types and derives what it needs from them: a decimator from 30 kHz to 1 kHz gets its factor of 30 from the two types and needs no option for it. The generator writes these types; for the prototype we write them by hand.
- **Options** (params) are primitives (int, floating point, bool, string), enums, fixed-size arrays of these (e.g. per-tetrode thresholds), or a path to a file, such as a filter coefficients file or an IMRO file. All of them work as template arguments as they are, negative and fractional values included (C++20), except strings (see below). A value of the wrong kind, such as 1.5 for an int option, is a compile error.
  - **String options use `Str`**, one string type written once in the engine: a processor declares `Str name;`, and `graph.cpp` writes `.name = "Abc"`. Neither `std::string` nor a pointer to a string literal can be a template argument. A string option's length is known when `graph.cpp` is compiled, so nothing needs a string that grows at run time: `Str` is a fixed-capacity character array of 256 bytes, so a string has at most 255 characters plus the terminating zero. A longer string is a compile error, never cut. Its bytes sit in the program's read-only data, not in processor state. Rejected for now: C++26 `std::define_static_string`, which would only remove the length limit and needs reflection in the compiler.
  - **A file option is only its path**, a string; the constructor reads the file at run time with ordinary file I/O. So the file's contents are not compile-time constants and never set an array size or a loop count. The exception is a file whose contents set sizes, such as filter coefficients (the number of sections sets the filter's state): the generator reads it and writes its contents into `graph.cpp` as an option value, so they are compile-time constants like any option (see **IirFilter**). Rejected: copying the file into the program at compile time with C++26 `#embed`, more machinery for no gain outside the loop (see **How to prioritise**).
- Processors are stateful or stateless. Each is a concrete type in one translation unit, so the compiler can inline a whole core loop into one fused unit. In the prototype, clang decides which `process()` calls to inline; forcing every call inline is in beyond_prototype.md (**Inlining every `process()`**).
- **Processor authors are trusted.** A processor is hot-path code that works directly on memory for speed, so the interface doesn't try to make mistakes impossible. It prevents a mistake only where that costs nothing at run time and doesn't limit how a processor is written (e.g. `In` and `Out` below); everything else is left to processor tests (see **Processor tests** in beyond_prototype.md).
- **`process()` signature**: `process()` takes one struct, `Connections`, declared inside the processor, with one member per connection. Every member is an input `In<Kind>` or an output `Out<Kind>`, where `Kind` is one of the three kinds a connection carries (see **Buffers**): a sample buffer, an event buffer, or a state value such as `bool`. Example: `struct Connections { SampleInputBuffer<InputStreamInfo> input; EventOutputBuffer<Spike, 32> output; };` and `void process(Connections connections);` (a sample buffer is a `SampleBuffer<StreamInfoType>`, an event buffer an `EventBuffer<EventType, Capacity>`, see **Capacity** under **Events**). `process()` returns nothing, and its connections are the processor's fixed set of inputs and outputs; a variable number of inputs is not a realistic need. `graph.cpp` names every connection at the call, `spike_detector.process({.input = ap_filter_to_spike_detector_sample_buffer, .output = spike_detector_to_trigger_spikes_event_buffer});`, as in the sketch under **graph.cpp**, and `In` and `Out` bind to the buffers and values. A processor's internal state (e.g. filter history) is not in `Connections`: it lives in the processor.
  - **Connections are written with aliases**: `SampleInputBuffer<StreamInfoType>` and `SampleOutputBuffer<StreamInfoType>` for the `In` and `Out` of a `SampleBuffer`, `EventInputBuffer<EventType, Capacity>` and `EventOutputBuffer<EventType, Capacity>` for an `EventBuffer`, and `StateInput<StateType>` and `StateOutput<StateType, initial_value>` for a state value (e.g. `StateOutput<bool, false> is_ripple_ongoing`, see **State values** under **Buffers**). Processors use only these and never write `In` or `Out` directly, so each connection is written one way. Each name says what flows and which way, and a buffer's name says it is a buffer, so someone new to Falcon can't mistake it for a processor. The aliases are transparent: the compiler and reflection still see `In` and `Out`. Rejected: `Out<EventBuffer<Spike, 32>>` written out (nested brackets); `SampleInput`, `EventOutput` (read like processor names such as `NeuropixelsInput`); `InputSamples`, `OutEvents` (don't say it's a buffer).
  - **Connection names**: a processor's only input is named `input` and its only output `output`, whatever their kind. The processor's name already says what it does, so the connection's name needs to say no more. A processor with more than one input names each input after its role in the processor, e.g. a Trigger's `spikes` and `ripples`, and the same goes for outputs. Inputs and outputs are counted separately: a SpikeDetector with one input and two outputs has `input`, `spikes` and `noise`. State-value connections are exempt from `input` and `output`: a state is always named after its role, even as a processor's only input or output, e.g. RippleDetector's `is_ripple_ongoing` output, read by a Trigger's `is_ripple_ongoing` input to trigger only during ripples. A bool state starts with `is_` or `has_`, like every bool. The member's name is also the connection's label in the UI. Not a priority: names will settle as more processors are written.
  - Why a struct: two connections of the same type in the wrong order are a compile error instead of a wrong experiment. It costs nothing at run time: measured with four and with ten connections, once `process()` is inlined both forms compile to the same instructions. Out of line, the struct is copied to the stack on every call (a few ns, see **Inlining every `process()`** in beyond_prototype.md). Rejected: one parameter per connection, which compiles with a swap; argument comments at each call (`/*filtered=*/ap_buf`) checked by clang-tidy's `bugprone-argument-comment`, which catch a swap only when linting.
  - **Required and optional connections**: a member that `graph.cpp` must always pass is a plain `In` or `Out`; it has no default, so C++ rejects a call that leaves it out. A member that `graph.cpp` may leave out is a `std::optional` of its `In` or `Out`, e.g. `std::optional<EventOutputBuffer<NoiseLevel, 1>> noise = std::nullopt;`, and `process()` puts both the calculation and the publishing for it under `if (connections.noise) { connections.noise->push(...); }`. `graph.cpp` leaves it out when nothing is connected, a constant fixed when `graph.cpp` is compiled, so once `process()` is inlined, clang deletes the block, calculation included; out of line, it stays behind one run-time branch. Measured: with the connection left out, an inlined processor compiles to exactly the same instructions as a copy of it that never had the connection, both on its own and inside a running core's loop. When it is connected, `Out` still clears the buffer at the call.
    - A use without the check compiles: C++ has no nullable type that the compiler forces to be checked (`*` and `->` on an empty `std::optional` are undefined behaviour). It is caught by clang-tidy's `bugprone-unchecked-optional-access`, which analyzes a processor only where a pipeline or a processor test instantiates it (measured). It is also caught by libc++ hardening at run time (see **Hardening** in beyond_prototype.md), and by processor tests that run each processor with every optional connection left out (see **Processor tests** in beyond_prototype.md).
    - Rejected: every form that makes such a use a compile error, as too complicated to use or read: a wiring struct as a template argument, read with `if constexpr`; a loop, macro or lambda that names the buffer only inside the block (the macro's `break` and `continue` also act on its hidden loop); one function per optional connection (`process_noise()`). Also rejected: a handle whose `push` does nothing when not connected, since publishing on a missing buffer must never happen.
  - A member of `Connections` that is neither `In` nor `Out` can't be used, so an author can't get a direction wrong, and writing to an `In` is a compile error. A plain state type doesn't bind, since `graph.cpp` passes a `StateValue` (see **State values** under **Buffers**). `SampleBuffer` and `EventBuffer` can't be copied, so a member holding a copy doesn't compile, and their contents are private to `In`, `Out` and the rings, so a member holding a plain reference to a buffer can't read or write it. Without this, a plain reference to an output would never be cleared (see **`Out` clears an output buffer** under **graph.cpp**), and pushes into a copied event buffer would be lost, both without an error. Rejected: a reflection check over `Connections`' members, which would need C++26 reflection in the bundled clang for a guarantee the types already give. Graph users never see these errors: the generator connects only matching inputs and outputs.
  - `process()` itself is never a function template: C++ doesn't deduce template arguments through the conversion to `In` or `Out`, so `template <typename EventType, int Capacity> void process(EventInputBuffer<EventType, Capacity> input)` fails to compile when `graph.cpp` passes an `EventBuffer<Spike, 32>`. Every type comes from the processor's own template parameters instead (e.g. `EventLogger<Spike, 32>`, see **Events**). This costs nothing: the generator knows every connection's type and writes it out.
  - `In` and `Out` are thin references, so the compiled loop is the same as with plain references. Reflection can later read `Connections` for the UI: direction from the wrapper, kind from `Kind`, name from the member's name.
  - Rejected: `const&` for inputs and `&` for outputs. An author who forgets `const` turns an input into an output without an error, and every author would have to be told to remember it.

### graph.cpp
`graph.cpp` holds the processors with their options, their buffers, a ring wherever a connection crosses cores, and one loop per core.

**Layout**: each core's function starts with a `// Processors` section (its processors with their options), then a `// Connections` section (its buffers and state values), then its loop, so a reader sees what runs and what connects it before reading the loop (see the sketch below).
- **Buffer names** say which processors and connections a buffer joins and what it carries: `<producer>_to_<consumer>_<kind>_buffer`, with the processors' variable names in `graph.cpp`, e.g. `dummy_generator_to_example_logger_event_buffer` or `ap_filter_to_spike_detector_sample_buffer`. A connection named after its role (see **Connection names** under **Processors**) is added after its processor's name, at either end, e.g. `spike_detector_to_trigger_spikes_event_buffer`; the default `input` and `output` are left out. This also keeps two connections between the same two processors apart (e.g. a SpikeDetector's `spikes` and `noise` outputs, both read by one logger). A state value follows the same rule, ending in `_state`; since a state is always named by role, both ends show: `ripple_detector_is_ripple_ongoing_to_trigger_is_ripple_ongoing_state`. A buffer read by several processors lists them all, in the order they appear in `graph.cpp`: `neuropixels_input_to_ap_filter_and_lfp_decimator_sample_buffer`. The generator writes these names, not people (see **Generator** in beyond_prototype.md), so the rule only has to be mechanical and unambiguous; the prototype's hand-written graphs follow it too. A ring follows the same rule, ending in `_ring` (e.g. `lfp_decimator_to_ripple_detector_sample_ring`). A buffer next to a ring is named after the processors on the two cores, so it has the same name on both cores, matching its ring (e.g. `lfp_decimator_to_ripple_detector_sample_buffer` on cores 2 and 3).

**In/out buffers.** `process()` reads its input buffers, writes its output buffers and returns nothing, like an audio plugin. `graph.cpp` declares every buffer and passes the buffers to each processor's `Connections`, so the data flow is visible in the loop. Chosen for clarity: there is one way to hand over data.
- As fast as returning values: each buffer is a local variable of its core's function, touched only by the inlined loop (see **Processors**), so the compiler can keep the buffer's count in a register. The samples go through L1 either way. This holds only while buffers stay local to their core's function.
- A processor can take several input and output buffers.
- The engine owns the buffers, so the generator can later let processors share buffers, or let a filter overwrite its input in place, without touching any processor (see **Buffer reuse** in beyond_prototype.md). The UI's cache view can count every buffer from `graph.cpp` (task D.5 in beyond_prototype.md).
- **No copies across rings**: a ring can hand a producer its next free slot as the output buffer, so the producer writes straight into the ring, as the input does in the sketch. A ring reader points its output buffer at the slot it reads.
- **`Out` clears an output buffer**: when `graph.cpp` passes a buffer to an `Out` (see **`process()` signature** under **Processors**), `Out`'s constructor clears it (count 0). C++ builds the whole `Connections` argument before `process()` starts, so the buffer is cleared right before its producer runs, on every call. So a processor that returns at once leaves its output empty, and neither a processor author nor `graph.cpp` can forget to clear it. Clearing right before the producer, not at the start of the pass, keeps feedback connections working, since they read the previous pass's output. It costs one write per buffer per pass. A state value passed to an `Out` is never cleared.
  - Rejected: wrapping every output in `out()` at the call (`lfp.process(raw_buf, out(lfp_buf))`), which did the clearing and showed the outputs in the loop. With `Out`, the signature already shows the direction, and a state value would have needed `out()` too without being cleared.

The sketch is an example with more processors than the prototype's graph. `Ring` stands for `SampleRing<StreamInfoType, slot_count>` (see **Rings**), whose constructor takes the ring's name for warnings; its `write` is a placeholder for a ring the producer doesn't write into directly, and event rings are not designed yet (see **Event rings between cores** in beyond_prototype.md); `Buffer` stands for `SampleBuffer<StreamInfoType>` or `EventBuffer<EventType, Capacity>` (see **Operations a processor uses** under **Buffers**), and stream types (see **Stream type** under Processors), the first template argument of every processor, are left out for brevity.

```cpp
// inserted where a connection crosses cores
Ring neuropixels_input_to_ap_filter_and_lfp_decimator_sample_ring;
Ring lfp_decimator_to_ripple_detector_sample_ring;
Ring ripple_detector_to_trigger_ripples_event_ring;

void core1() {
    // Processors
    NeuropixelsInput<{.port = 6363}> neuropixels_input;

    while (is_pipeline_running) {
        // the input writes straight into the ring
        Buffer& slot = neuropixels_input_to_ap_filter_and_lfp_decimator_sample_ring.next_slot();
        // polls the hardware; Out clears the slot first
        neuropixels_input.process({.output = slot});
        // makes the samples visible to core 2, if there are any
        neuropixels_input_to_ap_filter_and_lfp_decimator_sample_ring.publish();
    }
}

void core2() {
    // Processors
    IirFilter<{.highpass = 300, .lowpass = 6000}> ap_filter;
    SpikeDetector<{.threshold = -50}>             spike_detector;
    Decimator                                     lfp_decimator;   // factor 30 comes from its two stream types
    Trigger                                       trigger;
    PCIeParallelOutput                            pcie_parallel_output;

    // Connections, all owned by the engine
    Buffer neuropixels_input_to_ap_filter_and_lfp_decimator_sample_buffer;
    Buffer ap_filter_to_spike_detector_sample_buffer;
    Buffer spike_detector_to_trigger_spikes_event_buffer;
    Buffer lfp_decimator_to_ripple_detector_sample_buffer;
    Buffer ripple_detector_to_trigger_ripples_event_buffer;
    Buffer trigger_to_pcie_parallel_output_event_buffer;

    while (is_pipeline_running) {
        // points the buffer at the next ring slot, or leaves it empty
        neuropixels_input_to_ap_filter_and_lfp_decimator_sample_ring.read(
            neuropixels_input_to_ap_filter_and_lfp_decimator_sample_buffer);
        // Out clears the output buffer right before the call
        ap_filter.process({.input  = neuropixels_input_to_ap_filter_and_lfp_decimator_sample_buffer,
                           .output = ap_filter_to_spike_detector_sample_buffer});
        // every process() returns at once if its input is empty
        spike_detector.process({.input  = ap_filter_to_spike_detector_sample_buffer,
                                .output = spike_detector_to_trigger_spikes_event_buffer});
        // has output only every 30th sample
        lfp_decimator.process({.input  = neuropixels_input_to_ap_filter_and_lfp_decimator_sample_buffer,
                               .output = lfp_decimator_to_ripple_detector_sample_buffer});
        // copies into the ring
        lfp_decimator_to_ripple_detector_sample_ring.write(lfp_decimator_to_ripple_detector_sample_buffer);
        ripple_detector_to_trigger_ripples_event_ring.read(ripple_detector_to_trigger_ripples_event_buffer);
        // two inputs, so named by role
        trigger.process({.spikes  = spike_detector_to_trigger_spikes_event_buffer,
                         .ripples = ripple_detector_to_trigger_ripples_event_buffer,
                         .output  = trigger_to_pcie_parallel_output_event_buffer});
        // raises its pin on a trigger event, lowers it once the pulse width has passed
        pcie_parallel_output.process({.input = trigger_to_pcie_parallel_output_event_buffer});
    }
}

void core3() {
    // Processors
    RippleDetector<{.threshold = 3}> ripple_detector;

    // Connections
    Buffer lfp_decimator_to_ripple_detector_sample_buffer;
    Buffer ripple_detector_to_trigger_ripples_event_buffer;

    while (is_pipeline_running) {
        lfp_decimator_to_ripple_detector_sample_ring.read(lfp_decimator_to_ripple_detector_sample_buffer);
        ripple_detector.process({.input  = lfp_decimator_to_ripple_detector_sample_buffer,
                                 .output = ripple_detector_to_trigger_ripples_event_buffer});
        ripple_detector_to_trigger_ripples_event_ring.write(ripple_detector_to_trigger_ripples_event_buffer);
    }
}
```

### Per-core loop
- **One loop per core.** Each core runs one thread, pinned to that core, and each pass of its loop calls every processor on that core once.
- **Each core's processors are declared inside that core's function** (as in the sketch under **graph.cpp**), so processors of different cores never share a cache line (false sharing). Rings are then the only memory that cores share.
- **Start barrier**: each core builds its processors, then waits at one barrier shared by all cores (e.g. C++20 `std::latch`). Once every core has arrived, all loops start together; if a constructor failed on any core (see **Exceptions only outside the loop** under **Processors**), every core returns instead. Without the barrier, the input could start filling a ring while another core is still failing, and the full ring would log a second, misleading error.
  - A core's thread pins itself to its core only when it reaches the barrier, after building its processors. A thread that a library starts in a constructor (e.g. xipplib's, to receive packets) inherits its creator's CPUs; started on a pinned realtime core, it would compete with a loop that never yields, so its data would arrive late and in bursts.
- **Flush-to-zero** is set on every core. Flat or zeroed channels (dead, reference, or blanked during stimulation) drive IIR filter state into denormal floats, which many CPUs process far more slowly. Values that small (below 10⁻³⁸ in float32, 10⁻³⁰⁸ in double) mean nothing for neural data.
- **Order**: processors are called in a fixed order, and each comes after the processors it reads from, so a sample goes from input to output in a single pass. If a processor comes before one it reads from, that connection becomes a feedback connection, one pass late (see **Feedback connections** in beyond_prototype.md). In the product, the user sets the order in the node editor.
- **Chains**: connected processors on the same core form a chain. The chain ends where the next processor is on another core.
  - A chain has no rings inside, and each processor keeps its own state.
  - A chain starts at an input (hardware, or a ring from another core) and runs to its end without waiting: a sample passes through the whole chain in one pass. An empty pass costs one empty-input check per processor (estimate: under 1 ns each, to be measured).
  - A core can run several chains. They delay each other (see **Several chains on one core** in beyond_prototype.md).
- **Ring writes** can happen anywhere in the loop, since a write never waits.
- **Example**: p1 → p2 → p3 → p4 → p5 → p6, with p3 on core 2 and the rest on core 1.
  - Chains: [p1 p2] and [p4 p5 p6] on core 1, [p3] on core 2.
  - Core 1's loop: p1, p2, the ring writer to core 2, the ring reader from core 2, p4, p5, p6.
  - In one pass, core 1 handles sample N+1 in p1 and p2 and sample N−1 in p4 to p6, while core 2 works on sample N.
  - With p3 on core 1 too, all six form one chain in one loop, with no rings.

### Buffers
- **A connection carries one of three kinds**, and nothing else flows between processors: samples (all channels of one time point; defined by sample type, channel count and rate), events (see **Events**), or a state value (see **State values** below).
  - Rejected: merging samples and events into one kind, a buffer of items of one type with a capacity per pass, where a sample is one more item type. It changes nothing for speed, latency, alignment or cache: both are a pointer plus a count with compile-time types, and alignment comes from the item type either way. Less engine code is not a goal.
- **A buffer is a pointer to data plus a count**: 0 or 1 sample with its header, or the events produced on this pass (zero or more). Its storage belongs to the engine, but a producer can point it at data that already exists elsewhere (a ring slot, a socket receive buffer), so nothing is copied to hand data over.
- **Each sample has a header** of four values, 32 B, set by the input processor (rings add to the last one):
  - its sample number: 64-bit, counted at the input's rate, with the same meaning on every device. Processors use it to match samples from different inputs, count samples and stamp events. The input derives it from the device's clock and never counts samples itself, so a lost sample shows up as a gap instead of shifting every later number without an error;
  - the device's own timestamp for that sample, in the device's own unit, which links Falcon's samples to the device's recording (e.g. Ripple's recorded ephys data, for the correctness check under **Agreed**). Processors never calculate with it. Example: Neuralynx counts its clock in µs, so sample numbers 0, 1, 2 at 32 kHz have device timestamps 31.25 µs apart; on Ripple, the device timestamp counts samples, so the two values are equal;
  - its arrival time (TSC), for the latency check under **Agreed**: LatencyBenchmark logs the time from it to the trigger decision (see **Trigger and outputs**);
  - its lost-sample count (`lost_sample_count`): how many samples were lost upstream since the start. The input adds the samples the device skipped (a jump in the device's own numbering), and each ring adds the samples it has dropped so far, in `publish()`. A processor sees a loss when the count differs from its previous sample's, whatever the stream's rate. The count only grows, so any later header carries every earlier loss: a processor that passes on only some headers (one in 30, or its newest event's) forwards it without doing anything.
    - Rejected: comparing each sample number with the previous one plus the stream's step, which needs a step fact in `StreamInfo` for every lower-rate stream (e.g. a spike-count binner's output, 300 samples apart for 10 ms bins at 30 kHz); a "gap here" flag, which every processor that passes on only some headers must carry forward, so one that forgets hides the loss downstream without an error; numbering each stream at its own rate, which breaks matching samples across rates.
  - Falcon 1 recorded the same two times (arrival time and device timestamp). Flags wait until something needs them.
- **The header travels with its sample.** A processor reads its input's header as `connections.input.header`, and starts each output sample with `connections.output.set_header(header)`, which copies the given header and sets the count to 1, so no sample exists without one. The same call serves a processor that passes on a header and one that builds a new one (an input processor, a test-signal generator, a spike-count binner fed by events). `set_header` is also where the processor decides that it outputs a sample on this pass: a decimator from 30 kHz to 1 kHz calls it on 1 pass in 30, and without the call the output stays empty. Usually it passes its input's header; a processor that outputs a sample late (e.g. after a lookahead) passes the header it kept with that sample, and one with two sample inputs passes one of their headers, whose arrival time is then what the latency log measures from, with the two inputs' lost-sample counts added, so a loss on either shows downstream. A processor with a sample input never makes up a new header: a made-up sample number breaks matching across inputs and gap detection, and a new arrival time makes the latency log measure from the wrong moment.
  - Rejected names: `emit`, `new_sample`, `start`, `forward` with a separate `create`, and `connections.output.header = connections.input.header` (setting a field that also makes the sample present is a hidden side effect). For the header itself: `stamp`. Whether a buffer holds a copy of the header or points at it in a ring slot is the engine's choice.
  - Rejected: one header per chain, handed by `graph.cpp` to the processors that need it. After a processor that outputs late, it would give every later processor the wrong sample number without an error.
- A count of 0 means nothing new on this pass.
- After a burst, the extra samples wait where they already are (in the ring or the socket buffer) and are handed over one per pass.
- **State values**: small results that describe a state, such as "the TTL is high" or "a ripple is ongoing", are plain values passed by reference. They keep their value until their producer changes it, and stay in registers once inlined. Anything that means "new on this pass", such as a detection, goes in a buffer, so `Out` clears it (see **`Out` clears an output buffer** under **graph.cpp**).
  - **A number, `bool` or enum** (e.g. `int`, `u64`, `float`, an enum of stimulation phases), so it fits in one register. Small structs could be allowed later without touching any processor.
  - **Its producer's author picks its initial value**, in the output's type: `StateOutput<bool, false> is_ripple_ongoing;`. There is no engine-wide default, and a missing one is a compile error, since `StateOutput` needs both arguments. `graph.cpp` declares the state as the producer's type, `StateValue<bool, false>`, which holds it; one declared with another initial value doesn't bind to that output and fails to compile. Left uninitialised, `-ftrivial-auto-var-init=pattern` would fill it with a pattern, so a `bool` could start `true` and report a ripple from the first pass, letting a Trigger fire on it. A reader takes `StateInput<bool>`, which binds to any initial value. Rejected: a named constant in the processor (`static constexpr bool initial_is_ripple_ongoing`), which the generator would find by name, so a missing or misspelt one fails only in the generator; an option (`.initial_is_ripple_ongoing`), which mixes connections into `Options` and lets the graph override the author's choice.
- A buffer's contents are valid only until its producer's next call, which overwrites them: for the rest of the current pass, or into the next pass for a feedback connection (see **Order** under **Per-core loop**). Several processors can read the same buffer in that pass (e.g. `neuropixels_input_to_ap_filter_and_lfp_decimator_sample_buffer` is read by both `ap_filter` and `lfp_decimator` in the sketch). A processor copies what it needs to keep and never keeps a pointer into a buffer.
- A buffer filled by a ring reader looks the same as one filled by a processor on the same core, so a processor can't tell whether its input crossed cores.
- **Operations a processor uses**, each on the wrapper that allows it, so an `In` can only be read and an `Out` only written (see **`process()` signature** under **Processors**):
  - `SampleInputBuffer<StreamInfoType>`: `is_empty()`, `header`, and `load(simd_vector_index)`, which returns the channel vector at `simd_vector_index` as a float32 SIMD register of the compiled instruction set (`__m512` or `__m256`, see **One processor per stream** under **Processors**).
  - `SampleOutputBuffer<StreamInfoType>`: `set_header(header)` (see **The header travels with its sample** above) and `store(simd_vector_index, values)`.
  - `EventInputBuffer<EventType, Capacity>`: `is_empty()`, `size()`, and a loop over its events (`for (const EventType& event : connections.input)`).
  - `EventOutputBuffer<EventType, Capacity>`: `push(event)` for an event derived from `Event` directly, or `push(header, event)` for a stream event (derived from `StreamEvent`), which also sets the event's header (see **Events**). Each form is a compile error for the other kind of event, so a stream event can't be pushed without its header, which would leave it with sample number 0 and no error. Example: `connections.output.push(connections.input.header, Spike{.channel = channel})`.
  - A state value's `In` and `Out` read and assign like the value itself (`if (connections.is_stim_on)`, `connections.is_ripple_ongoing = true`).
  - `StreamInfoType::simd_vectors`: the number of channel vectors, i.e. the padded channel count divided by 16 on AVX512 or by 8 on AVX2.
  - No single-channel access: a processor that needs only a few channels gets them from a packer upstream, which copies them into a smaller stream (see **Channel selection** in beyond_prototype.md).
  - Mistakes left to processor tests (see **Processor authors are trusted** under **Processors**):
    - `store` without `set_header` compiles, and the processor seems to output nothing, since the count stays 0 (see **`Out` clears an output buffer** under **graph.cpp**), so the whole chain downstream stays silent. Only sample outputs have this case: an event is pushed whole in one call and a state value is assigned. Rejected: `set_header` returning the only object that has `store` (`auto sample = connections.output.set_header(connections.input.header); sample.store(simd_vector_index, values);`), one more line per sample processor and one more type for authors.
    - A processor that calls `set_header` but doesn't `store` every vector (e.g. an early `return` between them) leaves the skipped channels holding an older sample's values under the new header, and downstream reads them as real data. Example: artifact blanking stores zeros into the stimulated vectors but nothing into the others, assuming they stay "unchanged". A habit avoids it at no cost: each loop iteration computes one `result`, starting from the input where that makes sense, and ends with one `store`. Rejected guards: a test build where `set_header` fills the output with NaN; `set_header` always writing zeros first; counting `store` calls and checking them after `process()`; an all-at-once `set_header` that takes a function and calls it for every vector itself (`connections.output.set_header(connections.input.header, [&](int simd_vector_index) { return ...; })`), so the processor no longer writes its own loop.

### Events
A second, lightweight connection type for sparse outputs such as spikes, ripple onsets and decoder results. Within one core they are handed over in event buffers. Between cores they go through event rings (see **Event rings between cores** in beyond_prototype.md).
- **One type per kind of event**: a plain fixed-size struct derived from the empty `struct Event {};`, either directly (e.g. a timer's `struct ScheduledEvent : Event { u32 count; };`) or through `StreamEvent` for an event from a stream (see below), e.g. `struct Spike : StreamEvent { u32 channel; };`. The event type is part of the connection's type, so the compiler rejects connecting ripples to a processor that expects spikes. Processors that accept any kind of event (TTL output, recorder, logger) are templates over the event type, constrained to `std::derived_from<Event>`; the generator fills in the event type and the capacity from the connection (e.g. `EventLogger<Spike, 32>`, see **Capacity** below).
  - The struct is itself called an event, not a record. In neuroscience, record and recording mean recorded signal, so a bare "record" didn't exclude a sample, and a recorder would have recorded records. Rejected: `Message`, since logging already sends numbered messages (see **Logging**); `EventData`, verbose everywhere (`StreamEventData`, `EventDataType`); keeping the names `EventRecord`, `StreamEventRecord` and `Record`, which keep the ambiguity.
  - Rejected: taking the base type, `EventInputBuffer<Event, Capacity>`. An `EventBuffer<Spike, Capacity>` buffer is not an `EventBuffer<Event, Capacity>` buffer: the events have different sizes, and copying a `Spike` into an `Event` keeps none of its fields. The processor needs the concrete type to read the fields (e.g. through reflection).
  - `Event` holds no sample number, because not every event comes from a stream: a timer such as EventGenerator has no sample to point to, and a made-up number in a field shared by all events would mean something different for each producer.
  - `Event` exists although empty, so that a field every event needs can be added later in one place instead of in every event type, including those in labs' extensions.
  - Rejected: one type for all events (e.g. sample, channel, value), whose fields would mean different things for different producers, so a consumer could misread them without an error.
  - No virtual functions: they would add a hidden 8 B pointer to every event, and an event holding a pointer can't be copied byte for byte into a ring, shared memory or a file.
- **An event from a stream carries the whole header** of the sample it came from (see **Buffers**): the sample number for matching (the correctness check under **Agreed**, a spike-count binner), the arrival time for the latency log once events cross cores, and the device timestamp to find the event in the vendor's recording. It costs 32 B per event, and events are rare (most passes have none). Rejected: only the sample number (8 B), which would leave the latency log without an arrival time after a ring hop.
  - The header sits in a shared base, `struct StreamEvent : Event { SampleHeader header; };`, so it is defined once. A processor that needs the header (e.g. a spike-count binner, which builds its output's header from its spikes' headers) requires `std::derived_from<StreamEvent>`, so connecting timer events to it is a compile error; a processor that takes any event (logger, TTL output) requires `std::derived_from<Event>`.
  - The producer passes its input's header to `push` (see **Operations a processor uses** under **Buffers**): designated initializers can't name a base's members, so it can't go in the event's braces.
  - Rejected: a `header` field in each event type, which every author would repeat and which processors could find only by its name; one header per event buffer, which is wrong when one pass's events come from different samples (e.g. a processor that outputs a spike a few samples late, after finding its peak, or one that merges two spike streams).
- **No serialization code**: whatever saves or shows events (recorder, logger, UI) reads their fields through C++26 reflection, so an author only declares the struct (compiler support: see **The bundled clang supports C++26** under **Boundaries**).
- **The prototype's SpikeDetector** emits a `Spike` on the sample where a channel crosses the threshold, without waiting for the peak. The threshold is in µV and its sign gives the direction: a channel crosses a negative threshold when its value goes below it and its previous sample's wasn't (a positive one: above). So a channel fires once per crossing, not on every sample beyond. The first sample only records the state, padding channels never fire, and a NaN never crosses. The reference script for the trigger check under **Agreed** must apply the same rule. Rejected: Falcon 1's positive threshold with an "invert signal" option. Richer spike events come from separate processors later (see **Richer spike events** in beyond_prototype.md).
- **LevelCrossingDetector** emits one `LevelCrossing` for each channel that crosses a level, so Trigger can wait for every channel (the latency test graph under **Agreed**). After a crossing, that channel ignores its next `post_detection_block` samples (default 2) and takes the sample that ends its block as its previous one, so only a new transition counts. The block is per channel: one block for all channels would hide a channel crossing a sample after another, so Trigger would miss it. Rejected: Falcon 1's one event per sample, naming only the lowest crossing channel, with one block for all channels. Its direction is an option of its own (upward or downward), not the threshold's sign as in SpikeDetector, since it runs on any signal: a test square wave, or an envelope that must drop below a positive level. Otherwise it follows SpikeDetector's rules: the first sample only records the state, padding channels never cross, and a NaN never crosses.
- **Capacity**: an event buffer has room for every channel firing in the same sample: a stimulation artifact crosses threshold on all channels at once, and a buffer too small for that would lose events. Each producer fixes at compile time how many events it can emit in one pass, e.g. one per channel for a spike detector. The same will hold for event rings.
  - The capacity is part of the buffer's type, `EventBuffer<EventType, Capacity>`: the producer's output says it (e.g. `EventOutputBuffer<Spike, 32>`), and `graph.cpp` declares the buffer with the same type. A consumer takes `Capacity` as a template parameter too (e.g. `EventLogger<Spike, 32>`), filled in by the generator, since `process()` can't deduce it (see **`process()` signature** under **Processors**). `push` doesn't check the capacity: the producer never pushes more than `Capacity` in one pass.
  - Rejected: the capacity outside the type, with `EventBuffer<EventType>` pointing at storage that `graph.cpp` sizes from a `max_events` constant each producer declares. It would keep `Capacity` out of consumers' types, at the cost of a second declaration per buffer in `graph.cpp`.

### Rings
- A ring is inserted only where a connection crosses from one core to another: one ring per connection, in either direction. Two cores can have several rings between them. Each ring counts toward the cache of both the writer's and the reader's core.
- **Size**: an adjustable number of samples, always a power of 2.
- **One writer, one reader (SPSC)**, the simplest version: the prototype's only ring has one writer and one reader, and SPSC shares the fewest cache lines between the two cores. The old TODO list planned an SPSC design that minimizes cache misses. One writer with many readers is in beyond_prototype.md (**Rings with many readers**).
- **The header** (see **Buffers**) **sits in the slot**, in front of the samples: the simplest layout. Since samples fill whole cache lines, the header adds one cache line per sample (3 instead of 2 at 32 channels). Headers in a separate array would save half a line per sample, a later optimisation (see **Ring header layout** in beyond_prototype.md).
- **A full data ring is a failure, but the run goes on.** The writer never waits, and there is no backpressure: a sample that doesn't fit is written into the ring's spare storage, dropped and counted, and the count enters the lost-sample count of the samples the ring publishes after it (see **Each sample has a header** under **Buffers**). Realtime cores never print, so the main thread checks every ring each time it wakes (every 100 ms) and prints a console warning with the ring's name and how many samples it dropped, until the logger exists (see **Logging**). The user must change the graph or the hardware. Every ring registers itself when it is built, so none can be left out of the warnings. Rejected: stopping the run at the first dropped sample. Log rings are the exception (see **Logging**).
- **Writing**: on the writing core, `next_slot()` points the ring's writer buffer at the next free slot (or at the spare storage when full) and hands it to the producer's output, so the producer writes straight into the ring; `publish()` then makes the sample visible, if the producer wrote one.
- **Reading**: on the reading core, a ring reader works like any processor in the loop. `read(buffer)` points its buffer at the next slot, or leaves it empty (count 0) if this reader has read everything. Checking it is a memory read. The slot handed out on one pass is freed only on the next `read`, since the processors read it until then.
- **Hop cost**: about 20 ns for the write position within a CCD and about 80 ns across CCDs, plus pulling the slot itself, header included (3 cache lines at 32 float32 channels, 5 at 64, 25 at 384; to be measured). Keep connected cores on one CCD.
- **A stuck processor does not stall other cores.** In the example under **Per-core loop**, p3 on core 2 stops making progress (a long computation, a bug, a CPU stall):
  - Core 1 keeps running. Its ring reader for p3 → p4 leaves its buffer empty, so p4, p5 and p6 produce no output, while p1 and p2 keep processing new samples.
  - The ring p2 → p3 fills up, and a full ring is a failure. A 64-sample ring at 30 kHz is full after 2.1 ms.
  - When p3 recovers, the waiting samples reach p3 and then p4 one per pass, so p4 to p6 process late samples until p3 has caught up. Catching up requires p3 to process samples faster than they arrive.

### Input processors
Each input processor runs alone on its own spinning core and hands samples to the processing cores through a ring, writing them straight into the ring's slots (see **graph.cpp**). That costs one core-to-core hop per sample, but the socket's system calls and kernel copies stay off the processing cores, so their caches stay warm. This is a placement for the first implementation, not an engine rule: with kernel bypass (task A.6 in beyond_prototype.md), an input can later move into a processing core's loop.

### Waiting for data
- **Realtime cores spin**, so their loops also run passes when nothing has arrived. Lowest latency (one cache-line transfer), caches stay warm, and the core runs at 100% (heat).
- **Non-realtime cores** (recorder, viewer, logger) may block: the OS wakes the thread (µs), and deep idle (C6) can flush L1/L2. A blocking core runs no empty passes.
- The waiting strategy only decides what a core does when none of its processors has new input. It does not change the delay between chains on one core when both have work in the same pass.
- Falcon 1's yielding and sleeping (`falcon/portpolicy.hpp`) are dropped. On an isolated core with one thread, yielding is just spinning plus system calls, and sleeping backs off to 1 ms (30 sample periods at 30 kHz).

### Start, stop and config
- **One run per engine program.** Start means the UI spawns the engine program. The program builds every processor (see **Start barrier** under **Per-core loop**): if a constructor failed, or a core's thread couldn't be started, it logs the error and exits; otherwise it runs the loops. Stop is one signal for the whole graph, never per processor: the loops end, the destructors release the processors' resources, and the program exits. So every run builds its processors from scratch.
  - The stop signals are SIGINT (Ctrl+C) and SIGTERM. Every thread blocks them from the start, and the main thread takes them with `sigtimedwait` and clears `is_pipeline_running`. Otherwise the kernel could deliver a signal to any thread, including a realtime core's, and interrupt its loop.
- A config change needs a new engine program anyway (see **Every option is a compile-time constant** under **Processors**).
- An engine program that stays alive between runs is in beyond_prototype.md (**Engine states**).

### Logging
- A logger runs on a non-realtime core. Realtime cores never print and make no system calls; they send log messages to the logger through a ring.
- A message is a message number plus the raw values. The logger turns it into text.
- A full log ring is not a failure: the message is dropped and counted, and the logger reports how many were dropped.
- A realtime core never wakes the logger. The logger checks its rings on its own schedule (e.g. every few ms).
- Processors warn once instead of on every pass (e.g. once when an input stops).
- Errors, such as a full data ring, are logged the same way.

### Sample type
Input processors convert every sample to µV. Every processor after the input receives µV in one common floating-point format, float32 in the prototype, and never does math on raw ADC counts. Device-specific details (integer formats, per-channel gains, offsets, units) stay inside the input processor.
- **Load and store helpers**: processors read and write samples as SIMD vectors through the buffer's `load` and `store` helpers, never through raw float pointers, and do their math in float32 registers, except IirFilter, which computes in double (see **IirFilter**). The sample type is part of the stream type, fixed at compile time, so the helpers inline to the instructions one would write by hand: plain aligned loads and stores for float32 (`vmovaps`), since every sample's values start on a cache line; a misaligned buffer, which only an engine bug can produce, crashes on its first load instead of running slower without an error. For float16 they would convert on load and store (`vcvtph2ps`, `vcvtps2ph`), which a hand-written float16 processor on Zen 5 has to do anyway, since Zen 5 has no float16 arithmetic. So switching to float16 later changes only the stream type, not any processor (see **Sample width: float16** in beyond_prototype.md). A processor that needs a trick for one format uses a compile-time branch (`if constexpr`).
- **One format for every continuous stream**, whatever its unit (see **Goal**): voltage streams are in µV, and other streams carry other units, e.g. a phase estimator outputs radians and a spike binner outputs spike counts per bin.
- **Why µV, not V**: floating point has the same relative precision at any magnitude, so precision favours neither unit. µV is chosen because users enter thresholds and read traces in µV.
- **Why floating point, not integers in whole µV**: rounding the raw signal to whole µV would be harmless, since 1 µV is below the noise floor of extracellular recordings (several µV RMS). But after filtering, a frequency band can have an amplitude of only a few µV, so rounding to whole µV becomes a large relative error. Phases (radians) and z-scores are fractions. And every processor would have to round and clamp its output; a processor that forgets to clamp makes the integer overflow without an error.
- **Why float32 between processors, though IirFilter computes in double**: storing a value in float32 rounds it by at most half a step, 6×10⁻⁸ of the value (0.00006 µV at 1 mV), about 3000 times below the finest common ADC step (0.195 µV on Intan amplifiers) and far below the noise. float32's 24 significant bits hold as many as the best acquisition ADCs deliver. Rounding becomes dangerous only where feedback with poles near the unit circle amplifies it, inside an IIR filter, which is why IirFilter computes in double (see **Why double** under **IirFilter**); between processors each output is rounded once, so a chain adds one half-step per processor. Measured: IirFilter's float32 output differs from SciPy's double result by at most that half step, for every design tested (see **Processor tests** in beyond_prototype.md). A double pipeline would double every ring's and buffer's bytes and halve the channels per SIMD register, for no gain in accuracy.
- Devices deliver different formats (not yet verified against the vendors' documentation): int16 raw ADC counts (Neuropixels, Blackrock), int32 raw ADC counts holding 24-bit values (Neuralynx raw UDP packets), floating point in µV (Ripple), floating point in volts (TDT). So "raw" is not one integer type, and "float" is not one unit.
- Converting in the input prevents two bugs that give wrong results without an error message:
  - **Mixed gains**: on Neuropixels 1.0 the IMRO table sets each channel's gain, so the same raw count means a different voltage on different channels and on different probes. Any processor that combines channels (common average reference, bipolar referencing, a decoder comparing spike amplitudes across channels) would compute wrong values from raw counts.
  - **Headroom**: NP1 samples are 10-bit values stored in int16 (−512 to 511), while Blackrock samples use the full int16 range. Integer math that has room on NP1 data overflows on Blackrock data.
- Cost: the ring right after the input (every graph has one, see **Input processors**) carries floats instead of int16. With float32, that is 4 cache lines per sample instead of 2 at 64 channels, and 125 instead of 63 at 2000 channels. The conversion itself is about 3 AVX512 instructions per 16 channels (widen to 32-bit, convert to float, multiply by the per-channel scale).

### Rates
- The sample rate comes from the input processor, and the rest of the pipeline follows it. Nothing assumes 30 kHz: Neuralynx samples at 32 kHz, TDT at 24414.0625 Hz.
- **A `double` in Hz** (`StreamInfo<32, 30000.0, float>`, see **Stream type** under **Processors**), since an `int` can't hold TDT's rate: rounded to 24414 Hz, every cutoff and duration would shift by 0.0003%, and the input's rate check below would need a tolerance. `graph.cpp` writes `30000.0`, not `30000`: C++ doesn't convert an `int` argument to a `double` template parameter (to verify on the bundled clang).
- **Compile-time constant**, like the channel count. The UI and the generator infer each stream's rate while the user designs the graph, including the lower rate after a decimator, and `graph.cpp` hands it to the processors. In the prototype's hand-written `graph.cpp`, we write it in ourselves.
- Processors use the rate to turn the user's Hz and ms into per-sample values: filter coefficients, and durations as sample counts (refractory period, decoder time bins). Without it, the same graph on other hardware would shift every cutoff and duration without an error: a 300 Hz high-pass designed for 30 kHz sits at 320 Hz on 32 kHz data, and 30 samples are 1 ms at 30 kHz but 0.94 ms at 32 kHz.
- At start, the input processor checks that the device really runs at the compiled rate. If it doesn't, its constructor throws and the graph doesn't start (see **Exceptions only outside the loop** under **Processors**).
- Lower rates inside a graph come from processors that output only every N samples (see **Processors**).

### IirFilter
IirFilter, the prototype's filter, follows Falcon 1's spike filter: an IIR filter, a cascade of second-order (biquad) sections with a delay of a few samples, whose coefficients are designed offline. Other filter kinds are processors of their own (see **FirFilter**, and **FIR filter** in beyond_prototype.md). The first set is Falcon 1's 4th-order Bessel band-pass, 300–6000 Hz at 30 kHz, as two sections (Bessel has the flattest delay of the IIR families, so it distorts spike shapes least). The `.highpass`/`.lowpass` options in this spec's examples are illustrative.
- **Coefficients come from a coefficients file, written into `graph.cpp` by the generator** as an option: `IirFilterOptions<SectionCount>{.design_rate, .gain, .sections = {{.b0, .b1, .b2, .a1, .a2}, …}}`, named since options are never positional, with `a0` divided out. The section count is the array's size, so it sets the filter's state size like any compile-time constant (see **A file option is only its path** under **Processors**). Any count works the same way: Falcon 1's biquad files have 2 to 12 sections (12 on 32 channels: about 200 AVX512 fused multiply-adds and 6 KB of state per sample). The file's header names its kind, `# type = iir`. For the prototype, we copy the Bessel file's coefficients into `graph.cpp` by hand.
- **The sampling rate is checked at compile time**: a coefficients file states the rate it was designed for in a machine-readable header line (`# sampling_rate = 30000`), the generator copies it in as `.design_rate`, and IirFilter rejects a mismatch with the stream's rate. Falcon 1's files stated it only in their free-text description, so a 30 kHz file on 32 kHz data shifted both cutoffs without an error (see **Rates**).
- **An unstable section is a compile error**: both its poles must lie inside the unit circle. A mistyped coefficient usually breaks this, and an unstable filter's output grows without bound. A NaN or infinite `a1` or `a2` fails it too.
- **Transposed Direct Form II, computed in double**, with fused multiply-adds. IirFilter widens each loaded float32 channel vector to two double vectors, runs them through the sections and narrows the result back before storing it, so samples between processors stay float32 (see **Sample type**). The coefficients are double, and each channel has two doubles of state (`z1`, `z2`) per section. The file's gain is folded into the first section's `b` coefficients at compile time. Direct Form II, the other structure with two values of state per section, is more fragile: its state holds the input multiplied by the poles' gain, which is large for low cutoffs.
  - **Why double**: a section's cutoff is encoded in how far `a1` and `a2` sit from −2 and 1 (1 + a1 + a2 ≈ (2π × cutoff ÷ rate)²), and float32 resolves the coefficients, and each sample's update of the state, only to about 6×10⁻⁸. At 30 kHz, 1 + a1 + a2 is about 4×10⁻³ at 300 Hz (the spike band: ample margin), 3×10⁻⁶ at 8 Hz (theta: cutoffs off by up to 2%, with the rounding noise inside the band) and 4×10⁻⁸ at 1 Hz (below float32's resolution: a different filter, possibly unstable). Double resolves about 10⁻¹⁶, so even a 0.1 Hz cutoff at 30 kHz keeps six digits to spare: any coefficients file runs as designed, and no one has to judge whether float32 could hold it.
  - Cost: an AVX512 register holds 8 doubles instead of 16 floats, so there are twice as many vector operations, plus the conversions: a few ns per sample at 32 channels and 2 sections (an estimate, to be measured), less than one ring hop (see **Hop cost** under **Rings**). Using float32 where it provably suffices: see **IirFilter in float32 when proven safe** in beyond_prototype.md.
- **It starts in steady state**: on the first sample, each channel's state is set as if that value had always been there, so the output starts at its steady value (0 for a band-pass). Starting from zero, a DC offset would give every channel a start-up transient that SpikeDetector reads as spikes on all channels at once. The reference script for the trigger check under **Agreed** must start the same way: SciPy's `sosfilt`, started with `sosfilt_zi` scaled by each channel's first value, runs the same sections in the same Transposed Direct Form II, so its start matches exactly. `lfilter_zi` would not: it treats the cascade as one (b, a) polynomial pair.
- **It restarts after a loss**: when a sample's lost-sample count (see **Each sample has a header** under **Buffers**) differs from the previous sample's, IirFilter starts again in steady state from that sample, as on its first. Running straight across the gap, it would turn the jump in the signal into a transient: measured with a 4-slot ring on a busy machine, ring drops of up to 1748 samples made the filter comparison pipeline's filtered branch count 7 to 13 spikes per second instead of 6, while its unfiltered branch kept its 17. With the restart, the same test, dropping about 13,700 samples over 47 s, gave no false spikes and lost one spike to a gap. A restart loses nothing more, since the missing samples are gone anyway. Cost: one comparison per sample.
- Rejected for now as the spike filter: FIR, whose delay is half its length (about 1.7 ms for the roughly 100 taps a 300 Hz cutoff at 30 kHz needs; see **FirFilter**).

### FirFilter
An FIR filter on every channel: each output is a weighted sum of the channel's last N inputs, so for the usual symmetric taps its delay is half its length. In the prototype it serves the FIR chain latency pipeline (see **Latency tests for the paper** in beyond_prototype.md).
- **Taps as an option**: `FirFilterOptions<TapCount>{.design_rate, .taps = {…}}`, where `taps[0]` weighs the newest input. As for IirFilter, the tap count sets the state size like any compile-time constant, and `.design_rate` must equal the stream's rate. A NaN or infinite tap is a compile error: every output would be NaN, which no detector reads as a crossing.
- **Computed in double**, as IirFilter, so no one has to judge whether float32 holds a given set of taps. Each input is widened once and kept in double: each channel's state is its last N inputs in double (101 taps at 384 channels: 310 KB, beyond L1). Float32 is for later (see **FIR filter** in beyond_prototype.md).
- **It starts in steady state and restarts after a loss**, on the same rule as IirFilter: every slot of the history is filled with that sample, so the output starts at the value a constant input gives.

### Trigger and outputs
A Trigger processor decides when to stimulate and emits a trigger event; the output processor turns each event into a pulse on its hardware.
- **Trigger only decides**: its output is an event buffer of trigger events, each a `StreamEvent` carrying the header of the sample that caused it. It works on events and sample numbers only, never on a clock, so its triggers are exactly what the trigger check under **Agreed** compares, and a replay reproduces them. Any rule that waits or locks out (see **Trigger rules** in beyond_prototype.md) counts samples.
- **The prototype's rule**, as Falcon 1's EventSync: Trigger fires once every channel has had an event since its last trigger event, then starts over. A channel's further events before then count once (EventSync took the next event from each input in turn, so extra ones carried over to later rounds). The trigger event carries the header of the sample whose event completed the set. Its input is any per-channel stream event, e.g. a `Spike` or a `LevelCrossing`: Trigger is a template over the event type, which must derive from `StreamEvent` and have a `u32 channel` (a negative channel would index past its set of channels). There is no time window: the rule is built to measure latency with a test signal such as a square wave injected into every channel, where every channel crosses within a few samples. On real data one quiet channel would keep it from firing; richer rules are in **Trigger rules** in beyond_prototype.md. The reference script for the trigger check under **Agreed** applies the same rule.
- **PCIeParallelOutput times the pulse**, as Falcon 1's did. Its options are the pin number and the pulse width (the prototype's set in `graph.cpp`, e.g. 1 ms). It finds the card's I/O address itself when it starts, instead of taking it as an option (Falcon 1 assumed 0x3030), since the BIOS or the kernel assigns the address, which can change with the slot or the machine. Its constructor looks in sysfs for the PCI device with the card's IDs (the DeLock card's SUNIX chip: vendor 1fd4, device 1999, subsystem 0100), takes the start of its I/O range in base address register 1 (BAR1) as the data register's address, and prints it. Writing to a port where no card sits can upset other hardware, so it throws if no device or more than one matches, or if that range isn't an I/O range holding the data, status and control registers, and it never falls back to the address the parallel port driver reports (`/proc/sys/dev/parport/parport0/base-addr`), which may be another port's. Finding the address at run time costs nothing in the loop: x86's `out` instruction takes a port above 0xFF only from a register anyway. A trigger event sets the pin high, and the pin goes low once the pulse width has passed, timed in CPU time so the pulse ends even if the input stops (see **All logic lives inside the processor** under **Processors**); so it runs on a spinning core. Unlike Falcon 1's, it never waits inside `process()` but checks the time on every pass, and trigger events during a pulse neither extend it nor queue another (Falcon 1's waited out each pulse inside `Process()`, so events arriving meanwhile queued into back-to-back pulses).
- **LatencyBenchmark logs Falcon's latency**, as Falcon 1's did: an output processor for any stream event (derived from `StreamEvent`, the only events with an arrival time). Reading Trigger's output alongside PCIeParallelOutput and called right before it in the loop, it logs for each trigger the time from its sample's arrival to the decision. It logs every trigger, even one PCIeParallelOutput ignores during a pulse. Falcon 1's wrote its file and logged inside its loop, kept no sample number, and ran on a thread of its own, so it also measured its own scheduling.
  - It keeps each trigger's header and the TSC it read in an array its constructor allocates and touches, so the loop never takes a page fault or makes a system call. The array holds 2^20 triggers (about 3 hours at 100 per second); later ones are counted, not kept.
  - After the loop, its destructor writes one row per trigger to a CSV file: the trigger's sample number, its device timestamp, so each row can be matched with its TTL in the recorded event data, and the ns from arrival. It also prints their minimum, median, 99th percentile and maximum. The constructor creates the file, named after the start time, and refuses to overwrite one, so a run that can't write its log fails at start rather than after the session.
  - Ticks become ns with the TSC frequency measured against `CLOCK_MONOTONIC_RAW` between the constructor and the destructor: the longer the run, the more exact, and nothing waits at start. The constructor throws unless the TSC is invariant (`constant_tsc`, `nonstop_tsc`) and is the kernel's clock source, a sign that the kernel found the cores' TSCs in sync.
  - Rejected: logging inside PCIeParallelOutput, or a latency probe that any processor calls at a point in its code. An output's call holds nothing worth timing beyond the write, even less once pulse timing moves into a processor of its own (see **Pulse processor** in beyond_prototype.md). What each processor costs is a separate need (see **Runtime performance measurement** in beyond_prototype.md).
- **Why the pulse lives in the output**: its width is a property of what is wired to the line (a stimulator's or a laser driver's input), and other outputs (serial, DAQ, stimulators that take commands) realise a trigger differently, so Trigger stays the same for all of them. Once several output processors need pulses, the pulse logic moves into a processor of its own between Trigger and the outputs (see **Pulse processor** in beyond_prototype.md).
- **Safety**: the output processor's destructor sets every line low, so stopping Falcon never leaves a stimulator on. A crash during a pulse still can; only a pulse timed by the hardware ends regardless, and an output processor for such hardware just forwards the trigger event.
- Rejected: Trigger timing the pulse and outputting the line's state (`is_ttl_high`), which puts a clock into the decision and a property of the hardware into Trigger; the output making the whole decision, with no Trigger, which repeats the decision rules in every output processor; the engine timing pulses for processors, which breaks **All logic lives inside the processor**.

### Extensions
Processors that can't be public, such as an input built on a vendor's SDK, live in extensions, as in Falcon 1, where each extension was its own git repository inside an ignored folder.
- **Location**: `src/processors/custom/<extension name>/`, one folder per extension, each its own git repository (e.g. a lab's private one). `custom/` is git-ignored except `custom/template_processor/`, a template extension that labs copy to start their own (not `template`, a C++ keyword, which can't be a namespace). Falcon ships only the processors directly in `src/processors/`. Only extensions are installed machine-wide.
- **Namespace**: the folder name is the extension's C++ namespace, so processors from different extensions can share a name without clashing. A missing extension shows up as a compile error naming its namespace when `graph.cpp` is built.
- **Versioning** is the lab's responsibility: Falcon doesn't track extension versions, since an extension folder may not be a git repository.
- **An extension brings its own libraries** through an optional `CMakeLists.txt` in its folder, which the main `CMakeLists.txt` adds as a subdirectory for every extension it finds (as Falcon 1 did), so its paths are relative to the extension's folder; it adds the extension's include directories and libraries to the program. A vendor's SDK sits inside the extension folder, so it stays private too. A library built against another C++ standard library (e.g. GCC's libstdc++, while Falcon builds with libc++) links next to Falcon's as long as only a C interface crosses between them.
- **Pipelines that use an extension live in it**, in `custom/<extension name>/pipelines/`, since a public pipeline can't include a private processor.
- **The Ripple input is an extension**, `custom/ripple_neuromed_input/`, in a private repository until it can be published without Ripple's SDK (`xipplib.h` and its library), which may never be public. Naming Ripple and describing its stream in these docs is fine.
- **The template** holds a small processor (Gain, which multiplies every channel by a constant), a `CMakeLists.txt` showing where a library goes, and a pipeline that runs Gain.

## Open questions
The processor interface as actual C++ types, since it is what's expensive to change (see **How to prioritise** under **Agreed**). All settled: the sample's header, the buffer types `SampleBuffer<StreamInfoType>` and `EventBuffer<EventType, Capacity>` and the operations a processor uses on them (see **Buffers**), the event bases `Event` and `StreamEvent` (see **Events**), the processor's form with its `Options`, constructor, destructor and `process()` signature, and the names of connections and template parameters (see **Processors**).

**Telling the user about lost samples.** A full ring is warned about (see **Rings**), but samples lost before the input (e.g. a lost UDP packet) only raise the lost-sample count (see **Each sample has a header** under **Buffers**), and nothing reports it. Since the user must fix the setup (see **No lost packets** under **Principles**), they must know it happened. Proposed: the input processor logs each gap once, with the number of samples missing.

**Detection events are channel masks.** Decided: SpikeDetector's and LevelCrossingDetector's output becomes one event per sample with one bit per channel (a channel mask), saying which channels crossed on that sample. Their per-channel events, each carrying the whole header, rested on events being rare (see **An event from a stream carries the whole header** under **Events**), but test signals, movement and chewing artifacts in freely moving animals, and stimulation artifacts that aren't blanked make every channel fire in the same pass. Measured at 10,000 channels (see **Latency tests for the paper** in beyond_prototype.md): LevelCrossingDetector's 400 KB of `LevelCrossing` events and Trigger's loop over them cost about 7.8 µs, about 0.8 ns per event, more than 7 FirFilters over the same channels (about 7.4 µs) and a third of a 25 µs sample period at 40 kHz; everything else in that pass, the detector's comparisons over all 10,000 channels included, about 0.9 µs.
- A mask's cost doesn't depend on how many channels fire: the detector stores the 16-bit comparison masks it already computes, Trigger ORs them in with SIMD and compares with all ones, and per-tetrode logic is an AND with a group mask. The header is stored once, which is right since the event is one sample's; a late peak or two merged streams push separate events. A producer pushes about 1 event per pass, so capacity and ring slots stay small. Bit c is channel c on both AVX2 and AVX512.
- Events without one entry per channel (`TriggerEvent`, a timer's events, decoder results) stay as they are, and so do PCIeParallelOutput and LatencyBenchmark, which read only `TriggerEvent` or the header. EventLogger walks the set bits, and whatever counts spikes counts set bits, not events.
- No consumer on the hot path needs a per-channel value straight from the detector. A detector fires on the sample where a channel crosses its threshold, so the value there is the threshold, by construction. Trigger and burst detection need only which channels crossed (counts come from the mask). The values worth having come later and from the filtered stream: a spike's peak, 0.1–0.3 ms after the crossing; a tetrode's marks for clusterless decoding, the main use case; its waveform. Each comes as a sparse event from its own processor or an optional output of SpikeDetector (see **Richer spike events** in beyond_prototype.md).
- Its costs, and how far each is offset:
   - The event grows with the channel count even for one crossing (at 32 channels, 32 B + 4 B, padded to 40 B: the size of one per-channel event; at 384, 32 B + 48 B, two; at 10,000, about 32). Offset: a mask is 1 bit per channel, 1/32 of the float32 sample it comes from, so wherever the sample travels (a ring, a recording) the mask adds at most 3%. Remains: when few channels fire per sample, a list is smaller; e.g. 10,000 channels firing at 10 Hz each give about 2.5 crossings per sample at 40 kHz, about 100 B as per-channel events but 1.3 KB as a mask, which a recorder off the hot path can turn into a list before writing.
   - The producer stores its whole mask on every pass with a crossing, even for one channel: at 10,000 channels about 625 small stores, tens of ns (an estimate), against about 1 ns for one per-channel event. That is the price of a worst case that no longer depends on how many channels fire.
   - A consumer that needs channel numbers walks the set bits. Offset: an iterator hides it (`for (u32 channel : spikes.channels)`), and consumers that only combine channels (Trigger, per-tetrode rules) use SIMD on the mask instead.
   - Whatever saves or shows events writes each field by its type through reflection (see **No serialization code**), which turns a mask, an array of 64-bit words, into meaningless numbers. Offset: one rule for the mask type, in one place: a binary recording keeps the raw bits, the same size in every event, and a text log or the UI shows the channel numbers of the set bits.
   - A mask carries no value per channel (e.g. the amplitude at the crossing). Not offset: such values come in sparse events of their own, so two event shapes coexist and an author picks one.
- Rejected:
  - One header per sample and a list of channel numbers (4 B each instead of 40 B). A single crossing stays small and the memory is 10 times smaller, but the push and Trigger's pass stay one per channel (about 0.5 ns each even within L1), and one pass can hold several samples' events, so the buffer would need a header per run of same-sample events.
  - Per-channel events as before, plus an aggregate output on each detector (a mask or a count, on an optional connection) for Trigger, the per-channel events going only to consumers off the hot path. Every detector would gain an aggregate output, which is the mask again, and a per-channel consumer on the same core would still pay.
  - A smaller per-channel event (e.g. the sample number instead of the whole header): about half the memory, the same loops, and the header is kept whole for the arrival time.
- The mask type's interface, by who uses it (names still to decide):
  - A producer (a detector) writes one channel vector's bits at a time, as `store` writes a sample's: 16 bits per vector on AVX512, 8 on AVX2. The type keeps the padding bits 0, so a padding channel can never fire, and tells whether any bit is set, so the producer pushes only an event with a crossing.
  - A combiner (Trigger, per-tetrode rules) uses whole-mask operations, SIMD inside: OR, AND, equality, and the mask with every real channel set.
  - A lister (a logger, a recorder, a peak or mark processor) iterates the channel numbers of the set bits, counts them, or tests one channel.
  - Rejected: the mask as raw words that processors handle themselves, so every author would write bit tricks, the instruction set's width would leak into every processor, nothing would keep the padding bits 0, and reflection couldn't tell a mask from any other array; a fourth kind of connection for masks, which generic consumers (logger, recorder, LatencyBenchmark) couldn't take; a bit stream with a value on every sample, which costs a write and a ring transfer on every pass, where an event skips the passes on which nothing crossed.
- A producer builds its mask, then pushes the event with `push(header, event)`, like any other event. The push copies the event, 4 B of mask at 32 channels and 1.25 KB at 10,000, a few ns even then. Writing the bits straight into the event buffer instead is in **Event rings between cores** in beyond_prototype.md.
- The event types are named in the plural, `Spikes` and `LevelCrossings`, since one event holds every crossing of one sample, and each type's comment says it holds a mask. "A spike" keeps meaning one spike, as in the sparse per-spike events to come (e.g. `GroupSpike`, see **Richer spike events** in beyond_prototype.md). Rejected: a mask suffix (`SpikeMask`), which names how the event is built instead of what it means, and repeats "mask" in `SpikeMask.channels`; the singular names, which read as one spike and clash with `GroupSpike`.
- To decide, one at a time: the rule for when an author uses a mask and when a sparse event; the capacity of a mask producer (1 per pass, or a small fixed number for one that also reports a late peak).
